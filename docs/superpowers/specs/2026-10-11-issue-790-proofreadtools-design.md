# proofreadtoolsを使う変異候補・差分入力探索の評価設計

## 目的と対象Issue

#790の変異候補探索、#776のHypothesisによる差分入力・テスト候補生成、#777のCrossHairによる差分入力探索を、同じ実プロジェクトで評価する。
利用者の2026-10-11の指定によりサンプルはHayaoSuzuki/proofreadtoolsとする。
#763・#764の高次変異、#712の外部変異取込みは今回の対象外と確認済み。
製品化の前に、小規模実験で追加の探索費用に見合うテスト改善が得られるかを判断する。

## 既存実装とサンプルの固定

hoiminの開始点はmainの`e87f2e58c717fd66cc74f149e133dad516b3f2fe`。
作業ブランチは`research/issue-790-proofreadtools`。
proofreadtoolsは調査時mainの`409ed955c0695ec04976842ba9fd22c64c03c33a`を固定する。
サンプル側の本番ソース・既存テストを変更した状態をbaselineにしない。
サンプルを変更してPRを作る場合は、同リポジトリにも専用ブランチを作成する。

第一候補は`src/proofreadtools/checks/_variant_candidates.py`の`_length_ratio_upper_bound(x: str, y: str) -> float`。
式は`2 * min(len(x), len(y)) / (len(x) + len(y))`であり、定数変更以外の式・引数・演算子の探索を評価できる。
入力はまずASCII文字列、各長さ1〜32に限定する。両空文字によるゼロ除算を差分発見に数えない。
既存の`tests/test_variant_candidates.py`には異なる文字列長の具体値テストがあるため、候補がすべてkillされる可能性もある。
この場合は探索失敗を隠さず記録する。

第二候補は`src/proofreadtools/checks/reference_load.py`の`_classify(ref_count, abstract_count, chars)`。
こちらへ進むのは第一候補で有用性を判断できない場合のみとし、関数の追加前に予算配分を記録する。
非負整数、abstract_count <= ref_count、参照語を含められる文字数という実データ由来の制約を定義する。
戻り値のstr/Noneを型付きで比較する。第一候補のfloat比較と混ぜない。

## 比較する方式と選択

1. 既存operatorの固定列挙：既存hoimin plan/verifyによる基準。
2. 同じ制約付きAST編集空間からの無作為生成：候補空間を広げる効果の対照。
3. 同じ空間から実行フィードバックを使う探索：候補選択に探索を加える効果の評価。

Rustのproptestを変異を表す値の生成・縮小に使う方式を第一候補とする。
proptest自体に汎用の適応的探索を期待せず、保持・次候補選択の制御を実験側で明示する。
Python/Hypothesisで変異と入力の両方を生成する方式は試作が容易だが、Rust側との二重実装が生じるため初期の候補生成には選ばない。
高次変異・遺伝的アルゴリズム・汎用plugin基盤は費用が大きく、今回選ばない。

候補は1か所の許可したAST編集に限定する。
既存の式から取り出したオペランドの選択、適合する演算子への置換、許可した引数の選択などを使い、定数の加減だけで完了としない。
互いに独立した複数編集を大きなspanへ隠して一次変異と扱わない。
構文、スコープ、同一候補、無変更を検査してから実行する。
構文的妥当性や型注釈だけで意味上の妥当性を保証しない。

## 実験と製品の境界

実験処理は開発用・明示実行に限定し、通常CLI・plan schema・レポートschema・既定operatorを変更しない。
Rust生成器はtest-onlyの明示実行モジュールを第一候補とし、候補生成のためだけにproptestを製品依存へ移さない。
Python探索は固定サンプル用の開発用実験として閉じ、任意module/strategy/manifestを受ける製品入口を作らない。
具体的なファイル配置と実行経路は、設計承認後の実装計画で確定する。

既存候補の評価は同じ版のhoiminのplan/verifyを使う。
現在PATH上のhoiminは0.1.0であるため、そのまま実験へ流用しない。
既存版を評価する場合はPyPIの版を固定し、未公開の内部接続を評価する場合は作業ツリーをビルドする。
生成候補は既存のCandidateDescriptor検証・WorkerWorkspaceの変異適用経路を再利用するtest-only経路を計画する。
外部manifest取込みを追加してこの接続を代替しない。
単独のPython置換や抽出関数で得た差は探索の補助証拠にとどめ、hoiminの実適用でのkill確認と区別する。
既存機構だけでは接続できない場合、実装計画で不足を示して対象を限定し、未検証の接続を成功と扱わない。

## 入力探索とテスト候補

#776はHypothesisの公開strategy・探索・縮小を利用し、具体入力を固定した通常pytestの候補を作る。
非公開Conjecture APIへ依存しない。
#777は同じ元関数・変異関数・入力領域でCrossHairのdiffbehaviorを一度試し、通常CPython 3.14で差を再確認する。
初期のCrossHair比較は直接CLI方式に絞り、coverとHypothesis backendの網羅比較は行わない。
対応しない依存やPython版で失敗した場合はunsupportedとして記録し、別Pythonへ黙って切り替えない。

元と変異は実source pathを確認した独立環境で観測する。
解析のため抽出・ラップした関数は、その制約を記録し、実モジュールを使った確認を省略しない。
共有import cache、可変入力、グローバル状態による差を成功としない。
第一候補の入力範囲では有限floatの型・値を比較し、NaNや例外をrepr比較して差に数えない。
仕様oracleがない期待値固定はcharacterization候補と明記し、生成だけで人の採用と数えない。

## 探索の評価と縮小

生存だけを最大化しない。暫定候補には検査範囲を付記する。
有望な最終候補は既存テストで生存し、範囲内の有効入力で元コードとの差があり、追加テストでoriginal-pass/mutant-assertion-failを再現するものとする。
差が未発見、等価性未確定、構文不正、import failure、timeout、資源不足、不安定を分ける。
生成・縮小の途中では生存と差分入力の成立を再検査し、条件を失う縮小を採用しない。
縮小の順序は候補の構造を小さくする処理と入力を小さくする処理に分け、終端候補・入力を独立再確認する。
探索の進行を測る安価な指標は、候補の重複を避けた構造の多様性と固定した小さな入力集合での観測差とする。
これらの代理指標を最終的な有用性やkillとみなさない。

## 予算と比較条件

まず候補関数に関係する既存テストを通常実行し、baseline失敗があれば探索前に診断する。
生成テストの最終候補だけ、既存の軽量suiteへの追加でbaselineを確認する。
モデル取得を伴うheavy extraやslowテストは初期範囲外と明記する。
通常の軽量suiteでも時間上限を超える場合は完走と主張しない。

初期探索は各方式につき同じ60秒・同じ候補実行上限32件、seedを事前に固定した3反復を上限とする。
候補生成・評価・差分入力探索・縮小を探索予算へ含める。
固定列挙方式が候補を使い切った場合は実時間と件数を記録し、架空の同件数へ水増ししない。
CrossHair比較は選んだ候補に対しHypothesisとそれぞれ60秒までとし、起動・終了処理を含むwall timeも計測する。
baseline・最終確認・レビュー費用は探索費用と別に計測し、総費用にも含める。
探索中の安価な評価と既存suiteでの最終判定を区別する。

hoiminのplan/verifyはjobs=1、max-workspace-size=8GiB、min-free-space=10GiBを維持する。
ディスク空きが確認できない、10GiB以下、cleanup失敗の場合は新しい探索を始めない。
すべての子プロセスに停止上限を設け、終了・子孫清掃を確認する。
直接の実験プロセスもメモリ・プロセス・出力量の制約を実装計画で具体化し、hoiminの制限が自動的に及ぶと仮定しない。
定期的にcargo cleanを実施する。調査開始時Cドライブ空きは約175.9GiB。

## 証拠と完了条件

- サンプルSHA、source hash、最終replacementとspan、候補identity、具体入力、生成テストhash、oracleの由来、環境・コマンド・ツール版を記録する。
- seedだけを再現性の根拠にせず、最終候補と入力を独立再実行する。
- テスト追加後は新しいfingerprintのplan/runで照合し、古いresumeや結果を再利用しない。
- 成功テストはcollect・非skip・非xfailを確認し、失敗理由が意図したassertionであることを確認する。
- 無作為と誘導探索は同じ候補空間で比較し、既存operator対照との違いを説明する。
- 候補数、差の再現数、実kill、人の採用/却下/未レビュー、重複、未対応・不安定・予算切れ、時間・起動回数・レビュー費用を記録する。
- 採用・対象限定・見送りを結論とする。効果がなければ負の結果を記録して終了できる。

探索結果は通常mutation scoreと分離する。
今回の実験だけで汎用testgen機能の完成や全OS対応を主張しない。
製品化が有用な場合だけ後続の設計・互換性・配布版を判断する。配布契約の変更なら利用者指定の0.4.0方針に従う。
今回の成果物は設計、限定実験コード、証拠、採否報告を作業ブランチへコミットしたPRとする。
実プロジェクトへのテスト採用は候補と根拠をreview可能にして判断し、自動上書き・自動マージしない。

## 設計セルフレビュー

1. 対象範囲を確認した。#790・#776・#777だけを対象とし、高次・外部取込みへの暗黙の拡張を除外した。
2. サンプルの実装とテストを確認した。純粋な小関数と入力領域を具体化し、既存テストが強く追加便益がない結果も認めた。
3. Rust生成・Python入力探索・通常CLIの境界を確認した。開発用依存と製品依存を分け、実適用の証拠を抽出関数の差で代替しないとした。
4. 誤判定条件を確認した。生存だけの最適化、NaN/例外、無効入力、代理指標、縮小時の条件喪失、stale結果の流用を区別した。
5. 費用と再現性を確認した。同一空間・予算・反復の比較、終了・cleanup、レビュー費用、負の結果による終了を明記した。

実装計画・実装・テストの各5回レビューはそれぞれの段階で別途記録する。
この記録は実装・実験の実施証拠ではない。
