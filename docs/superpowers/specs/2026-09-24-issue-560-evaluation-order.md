# Issue 560: builtin resolution in evaluation order

The analyzer must suppress builtin-pair mutations when either spelling has already been bound at the lookup event. Source spans continue to identify candidates, but cannot represent evaluation time. Assignment evaluates its RHS first, then stores targets left to right recursively. Calls evaluate the callable, all positional/starred arguments, then keywords. Augmented assignment evaluates the target before the RHS and stores afterwards.

Introduce a monotonic event counter in NameResolutionBuilder and save the event at each source-indexed occurrence. Binding histories use events rather than source offsets. Explicit statement traversal puts stores at their execution points. Definition names become bound after decorators/defaults/class execution; deferred function bodies retain existing conservative lexical rules. Comprehensions evaluate the first iterable before entering their lexical scope, and outward walrus effects remain conditional. Existing loop-backedge and type-parameter rules remain intact.

Alternatives rejected: invalidating a whole assignment loses valid RHS candidates; inventing source-offset adjustments cannot represent keyword/starred reordering. A full control-flow interpreter is outside this fix: conditional/exception paths continue to join conservatively, so a potentially executed binding prevents a builtin proof. Exceptions may stop before a store; conditional stores must never be upgraded to unconditional certainty across handlers.

Acceptance covers both pair spellings, any/all plus list/tuple and sorted/reversed, nested and starred targets, chained assignment, RHS walrus, starred-before-keyword calls, RHS-before-store positive controls, augassign target-before-RHS controls, caught partial-store exceptions, and existing comprehension/loop/type-parameter regressions. Public plan verifies candidate spans as well as counts, and public run exercises the original reported case.
