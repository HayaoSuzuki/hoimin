# Issue #357 capability-bound cleanup audit

## Result

Ordinary worker cleanup now keeps the temporary-wrapper and worker-root
capabilities open through permission repair and content removal. The cleanup
path no longer changes permissions through an ambient pathname. A process that
replaces an inspected worker entry or wrapper path with an outside-pointing
symlink cannot make the outside object writable.

The Rust adapter matched all four production-correspondence rows generated by
Lean. The fifth row remains model-only. Focused Rust tests also covered an
outside hard link, mode-`0000` nested entries, a failed final removal followed
by retry, non-UTF-8 entries, the 128-level depth bound, reset, and `Drop`.

## Claim and boundary

Claim: cleanup permission effects target an object reached through a retained
capability or through a no-follow lookup beneath an owned directory
capability. They do not change an object outside the temporary workspace.

The claim covers `tempfile`-backed worker cleanup on supported Unix and Windows
targets. It covers permission repair, iterative removal, read-only and
inaccessible entries, links and reparse points, special Unix entries,
non-UTF-8 names, retry, and drop order.

The claim does not promise deletion progress against a process that keeps
creating or renaming entries. It also excludes discovery of a wrapper after a
process renames that wrapper to an unknown path. Managed workers continue to
use `ManagedChild::cleanup`; snapshot directories remain private to
materialization.

Lean proves the abstract transition model described below. It does not prove
the Rust implementation, `cap-primitives`, Rust's standard library, or OS
syscalls.

## Root cause and red evidence

The previous cleanup closed `WorkerRoot`, called `symlink_metadata(path)`, and
later called `set_permissions(path, stale_permissions)`. The second pathname
lookup could resolve a replacement symlink.

The deterministic Rust test paused between those two operations. It replaced
a read-only worker file with a symlink to a read-only outside sentinel. On the
old implementation, the focused run reported:

```text
entry swap:   actual (complete, outside writable=true)
              expected (rejected, outside writable=false)
wrapper swap: actual outside permission changed=true
              expected outside permission changed=false
```

The corpus parser and the stable and pre-existing-link cases passed in the
same red run. The mismatch therefore came from the inspection/replacement
interleaving rather than fixture setup or corpus parsing.

## Rust implementation correspondence

`WorkspacePlan` opens the temporary wrapper immediately after it creates the
pending owner. Local declaration order closes the wrapper handle before
`TempDir` on construction failure. `WorkerWorkspace` stores that handle beside
`WorkerRoot`.

`WorkerRoot::clear_for_cleanup` repairs the root through its open handle,
enumerates direct names relative to a cloned root handle, and sends each name
through the bounded no-follow removal state machine. The remover opens and
identity-checks regular files before unlinking them. When permissions block a
Unix directory open, it repairs that one name beneath the held parent, checks
type plus device/inode again, then opens and checks the resulting handle.
Linux uses the sandboxed `cap-primitives` permission operation. Other Unix
targets use its no-follow `fchmodat` path.

Regular Unix files need no permission change for unlink. Omitting that change
also protects an outside inode that has a hard link inside the worker. Windows
keeps its handle-relative read-only repair and reparse-point removal.

After content removal, `WorkerWorkspace` repairs the wrapper through the
retained handle. It closes both capabilities before final `remove_dir_all`,
which performs deletion only. A failed capability phase retains both handles
for retry. A failed final removal leaves the wrapper handle absent, so retry
does not reopen an ambient permission path. Struct declaration order drops the
two capabilities before the `TempDir` owner even if unwinding interrupts
`Drop`.

## Lean result

The model has four events: `inspect`, `swap`, `bind`, and `effect`. It checks
two strategies:

- `retained` captures the wrapper object before the event schedule.
- `post-inspection` binds a no-follow entry after inspection and rejects a
  replacement link.

`cleanup_never_changes_outside_writability` proves by induction over an
arbitrary event list that the correct transition preserves
`outsideWritable = false`. The bounded runner separately enumerated all traces
through depth 4: 341 raw traces per strategy and 682 strategy/trace pairs.

The broken transition resolves the pathname again at `effect`. Both strategies
reported the same shortest broken witness:

```text
[inspect, swap, bind, effect]
```

The model records repeated-event safety under the arbitrary-trace invariant.
Boundary and precedence sensitivity do not apply to this single-object model.
The changed Lean files contain no `sorry`, `admit`, or `axiom`.

## Generated-case observations

| Case | Mode | Lean expectation | Rust observation | Result |
| --- | --- | --- | --- | --- |
| `stable_entry` | `strict` | complete; outside stays read-only | read-only worker entry removed; outside stayed read-only | match |
| `preexisting_outside_link` | `strict` | complete; outside stays read-only | link removed; outside stayed read-only | match |
| `entry_swap_after_inspection` | `internal-fixture` | rejected; outside stays read-only | no-follow open rejected the replacement; outside stayed read-only | match |
| `entry_swap_after_binding` | `model-only` | complete; outside stays read-only | no production comparison by contract | not compared |
| `retained_wrapper_swap` | `internal-fixture` | capability effect completes; outside unchanged | retained handle changed the moved wrapper; outside fingerprint did not change | match on declared permission observation |

The wrapper fixture uses mode `0300` because macOS rejects renaming a directory
that lacks owner-write permission. The vulnerable helper would add the missing
read bit and change the outside fingerprint. The correspondence row excludes
final deletion completeness, as specified in the design.

Additional Rust checks established these implementation boundaries:

- cleanup unlinked an outside file's hard link without changing the inode's
  mode;
- cleanup removed a two-level mode-`0000` directory containing a mode-`0000`
  file;
- retry removed the wrapper after an injected final-removal permission
  failure, without repeating capability acquisition or repair.

## Counterexample ledger

| Finding | Resolution |
| --- | --- |
| Ambient permission repair follows a replacement symlink | Retain wrapper/root handles and use no-follow, handle-relative removal |
| A read-only regular-file chmod can affect an outside hard link | Unix cleanup now identity-checks and unlinks without chmod; regression added |
| A mode-`0000` directory cannot be opened before repair | Repair one child relative to the held parent, re-stat identity, then open |
| Root directory iteration could share a cursor across retry | Enumerate through a cloned root handle |
| Field declaration order placed `TempDir` before live handles during unwind | Declare root and wrapper capabilities before the owner |
| The initial `stable_entry` adapter left its worker file writable | Set the worker entry to mode `0400` before cleanup |
| A mode-`0500` wrapper could not be renamed by the macOS fixture | Use mode `0300`; preserve a missing-bit permission delta |
| Native executable linking approached or crossed the RSS cap | Use serial `lean --run`; keep the 768 MiB limit |

No semantic mismatch or owner decision remains open.

Two native-link retry attempts reached 787,120 KiB and 810,000 KiB. The guard
stopped both with exit 125. The limit stayed fixed, and no process remained.
A sandboxed guard smoke test returned monitor error 126 because that sandbox
blocked `ps`; the same guard succeeded under the approved process-monitoring
path. Neither infrastructure outcome counts as semantic evidence.

The audit used temporary statistics directories
`/private/tmp/hoimin-357-lean.TxeBn6` and
`/private/tmp/hoimin-357-final.1T9UTS`. Cleanup removed both directories and
the worktree-local Lean `.lake` cache after recording the table. Cargo used the
repository's shared target directory; no worktree-local `target` remains.

No Rust mutation run was needed. The Lean broken transition and deterministic
filesystem race exercise the dangerous stale-path effect, while the focused
tests cover the permission predicates, hard-link alias, retry phase, tree
depth, inaccessible directories, and special entries. A mutation run would
repeat expensive workspace compilation without testing another identified
branch.

## Reproduction

Run each Lean command from `formal/HoiminOracle`, replacing `STAT.json` for
each invocation:

```console
python3 tools/lean_resource_guard.py --timeout-seconds 20 --rss-limit-mib 768 \
  --sample-ms 250 --stats STAT.json -- \
  lake -Kjobs=1 env lean HoiminOracle/CleanupCapabilityProofs.lean
python3 tools/lean_resource_guard.py --timeout-seconds 20 --rss-limit-mib 768 \
  --sample-ms 250 --stats STAT.json -- \
  lake -Kjobs=1 env lean --run CleanupCapabilityAuditMain.lean -- --sensitivity
python3 tools/lean_resource_guard.py --timeout-seconds 20 --rss-limit-mib 768 \
  --sample-ms 250 --stats STAT.json -- \
  lake -Kjobs=1 env lean --run CleanupCapabilityAuditMain.lean -- \
  --check corpus/cleanup-capability.jsonl
```

Run the Rust adapter from the repository root with the shared target:

```console
CARGO_TARGET_DIR=/path/to/hoimin/target \
  cargo test -p hoimin-cli cleanup_capability --lib -- --nocapture
CARGO_TARGET_DIR=/path/to/hoimin/target \
  cargo test -p hoimin-cli --test workspace_handler
```

manual macOS or Windows workflow and does not use it as a condition.
