# Issue #558 review and verification record

## Design self-reviews (before implementation)

1. Semantics: compared the issue's first-evaluation/cache witnesses against
   CPython's official annotation semantics. Found that final-scope-only lookup
   would accept unsafe intermediate evaluations; selected conservative later-write
   rejection and explicitly documented cache/restoration false negatives.
2. Scope/provenance: traced `AnnotationCollector::record`, `resolved_name`,
   `spelling_for`, and #548's `annotation_resolution`. Found that removing an
   unaliased module import can still leave the literal `typing.Sequence` name;
   required an explicit source provenance gate and lexical class visibility.
3. Compatibility: compared #264's eager snapshot contract with PEP 695 and future
   annotations. The analyzer has no target-version selector. Chose a uniform
   conservative contract, retaining source-order facts and stable positives;
   marked historical candidate expectations for explicit updates.

## Plan self-reviews (before implementation)

1. Acceptance mapping: each issue acceptance condition maps to public plans,
   public run, Python evaluation, or timing documentation. Added source/destination
   and class follow-up cases instead of only the minimal source example.
2. Integration: verified the existing scope index already registers annotation
   sites and type-parameter scopes. Reuse avoids a second scope walker; imported
   spellings require their own recorded binding offsets because builtin tracking
   currently ignores these names.
3. Test independence: expected public counts and runtime types come from fixed
   CPython semantics, not the new resolver. Require RED before production edits,
   exact pair/span checks for positives, and score assertions at public run.

## Rulings and limits

- Ruling: runtime annotations use a conservative cross-version policy because
  analysis has no target Python version. Safe eager/cached/restored cases may be
  omitted; unstable imported spellings must not inflate mutation scores.
- Ruling: function-local variable annotations retain source-order candidates,
  because Python does not evaluate them. This improves precision without making
  a deferred-runtime lookup claim.
- Ruling: update the old Lean class fixture's candidate gate while preserving its
  source-order environment. The prior candidate expectation encoded eager
  evaluation and conflicted with CPython 3.14 and the issue's accepted contract.
- External object attribute mutation, custom `__annotate__` implementations and
  arbitrary dynamic namespace mutation are not modeled. Python 3.13 was not
  executed. The Python 3.14 checks and native Rust tests run on macOS arm64.
- The first broad run was intentionally diagnostic and exposed historical
  expectations in analyzer/library/valid-python copies plus the two public Lean
  suites. The dedicated follow-up test was also red during that run. All are
  recorded above; final verification follows below.
