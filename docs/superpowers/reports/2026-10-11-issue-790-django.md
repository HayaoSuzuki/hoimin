# Djangoでの制約付き変異探索

## 調査の終了と保存範囲

2026-10-11、調査結果だけを残して本調査を終了した。
テスト自動生成の成立例は得られたが、誘導探索の優位と継続保守に見合う効果は確認できず、製品機能への採用と追加実験を見送る。
研究用Rust/Pythonコード・契約テスト・CI変更はPRの最終差分から取り除いた。
以下の実装・テスト成功・再実行手順は[実験時点のコミット `93116fe`](https://github.com/HayaoSuzuki/hoimin/tree/93116fed96602628d04a2139645b3dfe1166e168)の記録であり、現在のブランチで使える機能や検証結果ではない。
再実行する場合はその版を別checkoutで利用する。機械可読の証拠・生成テスト例・設計・計画・レビューは調査資料として保存する。

## 結果

Djangoをcloneし、3関数・5 seed・3方式で計71回、異なる候補IDとして35件を評価した。
41回は既存テストのassertionで検出され、30回は別の実行時エラーだった。
既存の関連suiteを通る候補は0件で、入力探索・実module反例照合・生成テスト照合の実行回数も0件だった。
エラーをkillに合算せず、生存候補がないことを等価性の証明とも解釈しない。

生成空間は前の18件から162件へ広がったが、今回も誘導探索の優位を示す結果は得られなかった。
既存suiteの検出力、評価できた候補数、候補の型不整合、workspace復元の費用が次の検討対象となる。
Django全体のmutation scoreや、一般的に生存候補が存在しないという結論ではない。

## 対象と条件

公式repositoryの固定SHA [`dab0a5c47f159eb58472110dcbc10bd4a9b01adb`](https://github.com/django/django/tree/dab0a5c47f159eb58472110dcbc10bd4a9b01adb) を使った。
Windows・CPython 3.14.6、Hypothesis 6.169.0、asgiref 3.12.1、sqlparse 0.6.0、tzdata 2026.5。
Django自体は固定checkoutからimportし、PyPI版のDjangoへ差し替えていない。
ブラウザ、外部DB、ネットワークサービスは使わず、公式runnerのin-memory SQLiteだけを使った。

| 対象 | 既存候補 | 生成候補 | baseline収集 | baseline skip |
| --- | ---: | ---: | ---: | ---: |
| numberformat.format | 100 | 35 | 7 | 0 |
| timesince.timesince | 122 | 97 | 38 | 22 |
| duration.duration_microseconds | 14 | 30 | 17 | 0 |
| 合計 | 236 | 162 | 62 | 22 |

公式の関連テスト群を対象別に実行した。
timesinceの22 skipはWindowsで任意タイムゾーンへ切り替えられない制約によるもので、残る16件は実行された。
各変異で収集数とskip数をbaselineと照合し、テストが消えた結果を生存と数えない。

AST単一編集の生成規則はproofreadtoolsの研究と同じで、既存オペランドへの置換、四則演算の置換、minの引数・maxへの置換を使う。
対象関数の選択だけを引数化し、Proptestでpoolから選ぶ。
全moduleを正規化したASTで比較すると、生成162件は160構造となり、既存候補との重複は28構造、追加は132構造だった。
この比較は構造的重複であり、振る舞いの等価性を意味しない。

無作為と誘導は同じ162候補を使った。
誘導の報酬は暫定probe差とoperator種類の新規性だが、今回は生存候補がなくprobe差の報酬は発生していない。
全ての候補を試し切ったarmはなく、前実験の18候補の飽和は避けられた。

## 測定

全armの設定は候補開始の時間窓30秒、最大12件、各子コマンドは残予算以下かつ最大10秒。
既存ProcessHandlerの1GiB・16プロセス・出力1MiB、workerのコピー8GiB・空き10GiBを維持した。
timeout・出力未完了・清掃失敗では探索を止める。

当初のwall 30秒という目標は、候補処理後の同期reset等によって一部armで超過した。
実時間は28.697〜35.547秒であり、厳密な30秒のhard deadlineを達成したとは扱わない。
各方式には同じ開始判定と子プロセス上限を適用したが、実時間が完全に等しい比較ではない。

fixedは対象別planをnumberformat・timesince・durationの順に結合し、その先頭からrank順の4〜5件を使うため、全てnumberformatに偏った。
無作為は23回・21候補ID、誘導は24回・22候補IDを評価したが、この差を改善効果と判断しない。
対象関数の配分、キャッシュ状態、固定の方式順、少ない評価数があり、統計的な速度・成功率比較には使えない。
小さい契約テストの検証は測定の準備・初期と一部並行しており、専有マシンのbenchmarkでもない。

全armのwall合計は500.270秒、候補行に記録されたwall合計は100.737秒だった。
差の約399.533秒には行の外で実行するreset等を含むが、処理別の内訳は計測していない。
候補評価数を増やすには、次にこの内訳を測る必要がある。
準備と最終清掃を含む実験のwallは604.751秒、ProcessHandlerで起動したroot commandは79回。
79回はgit・baseline・plan・各suiteのroot起動数であり、子孫プロセス総数ではない。
環境導入・実装・レビューのwallは未計測で、総費用削減は主張しない。

## 入力生成と再現性の境界

補助コードは数値整形用の小数文字列と整形引数、timesince用の明示的な2日時とdepth、duration用のmicroseconds整数を固定領域から生成する。
probeの差は暫定結果であり、実moduleを元・変異それぞれ2回独立起動して照合したものだけを検証済み反例と呼ぶ。
各対象最大1件の生存候補について、新しいテストfingerprint・plan・workerで元成功／変異assertion失敗を確認する経路を用意した。
今回は対象となる生存候補がなく、このDjango経路のend-to-end成功を主張しない。
proofreadtoolsでの既存の正例をDjangoの正例へ読み替えない。

独立レビューで、時間予算の前後でHypothesis predicateの結果が変化する境界条件を見つけた。
時計と入力を固定した先行テストでFlakyFailureを再現し、入力ごとの観測をcacheして、予算後の再確認にも同じ結果を返すよう修正した。
最終の期待値もcacheから取得し、実moduleでの再確認はcacheを共有しない別プロセスで行う。
測定の71候補は全て入力探索前に既存suiteで検出またはエラーとなり、補助コードのsearch起動は0回だった。
したがってこの修正は上記15armの結果に影響せず、全実験の再実行は行っていない。

## 採否

#790のAST単一編集・有限探索という研究範囲を維持する。
大規模repositoryから複数関数を選ぶ実行は可能だが、repository規模を増やすだけでは探索効果の検証にならない。
次に進むなら、関数ごとの配分を揃え、復元等の内訳を測り、同じ評価件数で有効な生存候補を得られる対象を選ぶ。
型不整合によるエラーを減らす候補生成も検討対象となる。
今回の結果を根拠にpandas全体やCPython全体の高額な検証へ自動的には広げず、通常CIへ実験を入れない。
#776のテスト生成、#777のCrossHair連携について新たな採用根拠は得られていない。

## 実験コミットでの再実行

repository外に固定SHAのcleanなDjango checkoutを用意する。
Python 3.14の隔離環境へ上記の5依存を導入する（Djangoの全開発依存は不要）。

```powershell
$env:HOIMIN_DJANGO_ROOT = '<clean pinned Django checkout>'
$env:HOIMIN_RESEARCH_PYTHON = '<isolated Python 3.14 executable>'
$env:HOIMIN_RESEARCH_OUTPUT = '<new evidence.json path>'
cargo test --locked -p hoimin-cli --test proofreadtools_search django_experiment -- --ignored --nocapture
```
