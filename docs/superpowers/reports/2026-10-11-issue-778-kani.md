# Kaniによるworkspaceコピー予算契約の実現性調査

## 結論

#778の現行トリアージに従い、Linux手動・実処理1件・資源上限付きで調べた。
Kani 0.68.0で実際のhoimin-coreとharnessのコンパイル・検証開始までは可能だった。
しかし、unwind 8では検証60秒でtimeout、unwind 2への再試行では4GiBの上限でOOM停止した。
契約の証明成功も、契約違反を示す反例も得られていない。
Kaniの導入・CIへの組込みは保留を維持する。

これはKani全般の無効性やhoiminの不具合を示す結果ではない。
今回の契約と入力条件を、既存実装をstubせずに小さい資源上限で検証できるという根拠は得られなかった、という結果である。
上限を増やした実験、Verus・Boleroの導入、別契約への拡張は行わない。
反例がないため、Concrete Playback・通常Rust回帰テスト化・意図的欠陥の検出は未実施であり、Issue起票時の全受け入れ条件を満たしたとは扱わない。

## 対象と入力条件

対象版はhoimin `e87f2e58c717fd66cc74f149e133dad516b3f2fe`。
`crates/hoimin-core/src/budget.rs` の `reserve_workspace_copy` を公開APIから直接呼んだ。
台帳、BTreeMap、予約ID管理、エラー型、整数処理は実コードを使い、別実装への置換やstubを使っていない。
Windowsのソースの改行を含むSHA-256は `1dd41c876692b70b31f81bbb9b5d37084203460942547e9f1ef1e446c3467a2e` で、隔離コピーでも一致した。

- 開始状態は予約・解放履歴が空の台帳。メモリ・プロセス予算は0、コピー予算は任意のu64。
- 1 worker当たりバイト数と申告総量はそれぞれ任意のu64。
- worker数は任意のu8を4で剰余した0〜3。u32全域ではない。
- 予約処理は1回。失敗後のみ0バイト予約を1回試し、予約IDが0のままであることを確認する契約を置いた。
- 正常系のgrant内容、overflow・総量不一致・予算超過のエラー分類、失敗時の使用量とID保持をassert対象にした。
- 期待する積はu128で計算し、実装のchecked_mulをそのまま期待値にしなかった。

unwindは最初8、再試行2。unwinding checksは無効化していない。
contracts featureは無効の通常coreを対象にした。
既存予約がある状態、複数操作列、予約ID枯渇、解放処理、並行実行には範囲を広げていない。
上記は検証しようとした条件であり、確認済みの保証範囲ではない。

## 環境と実行費用

WSL2 Ubuntu 24.04、x86_64 Linux 6.6.87.2、Kani 0.68.0、CBMC 6.11.0、CaDiCaLを使用した。
Kani公式配布物のRustは `nightly-2026-08-21`、rustc `1.100.0-nightly (8925ea358 2026-08-20)`。
製品のRust 1.99・MSRV・Cargo依存・cfg・通常CIは変更していない。
WSLにはRustがなく、専用のCARGO_HOMEとRUSTUP_HOMEへ導入し、シェルprofileと既存PATHは変更しなかった。
固定配布物のSHA-256は `32e2b484d73ede0bbf64a2cf0879c4259422497d8aec4ee67d448de9ae7843d3`。
これは取得物の識別値であり、独立した署名検証を行ったという意味ではない。

systemd user serviceでMemoryMax=4GiB、MemorySwapMax=0、TasksMax=128を設定した。
導入は600秒、最初のコンパイル込み実行は240秒、再試行は120秒の上限とした。
Kaniのharness-timeoutはどちらも60秒。ビルドは2 jobs、検証harnessは1件。
実行前後にディスクを確認した。使用量は約2.78GBまで増えたが、ディスク使用量のhard limitを実装したわけではない。

| 段階 | 結果 | 実測 |
| --- | --- | --- |
| 最初の配布物取得 | 成功したがWSL再起動後に/tmpから消失 | service 9.004秒、取得・展開約619MB |
| /var/tmpでの隔離導入 | 成功 | service 41.371秒、2,285,617,920 bytes |
| CLI指定の診断 | --test未対応、exit 2 | time wall 0.09秒。--testsと単一harness filterへ変更 |
| unwind 8 | resource exhausted: timeout、exit 1 | Kani検証60.042秒、time wall 98.05秒、最大RSS 1,994,856 KiB。service peak表示2.7G |
| unwind 2 | resource exhausted: OOM | service 23.743秒、peak表示4.0G。完了JSONとtime最終値なし |

unwind 2ではsymbolic executionの9.821秒後に、簡約後4,043件のverification conditionが残ったところまで記録された。
unwindを下げても証明成功は得られず、unwind 2が十分だったかも未確認である。
一時serviceはWSLの再起動で失われるため、後でsystemctl showが返す初期値を成功の証拠にしていない。
serviceの終了理由・peakは、実行したsystemd-runの完了出力から転記した[実行記録](issue-778/service-results.txt)による。
setupやレビュー全体の費用、機械全体の最大メモリ、総コスト削減は測っていない。

## 結果の読み方と既存手法との差

Kaniのbaseline JSONにはsummary status=completedとfailed=1があるが、詳細のexit_statusはtimeoutで、checksは空だった。
completedを証明完了、Failureを契約違反と読み替えない。
再試行のOOMでも、反例や未対応機能のエラーが得られたとは扱わない。
ログ中のassume(false)やループ展開表示だけを製品コードの不具合と解釈しない。

既存の `crates/hoimin-core/tests/budget.rs` は、overflow、総量不一致、予算超過、解放時の原子性、予約ID枯渇等の具体例を検証する。
LeanのBudgetModelとRust oracleは、小さい状態空間・ID上限・操作列におけるモデルと実装対応を確認する。
Kaniではu64全域の実ビット幅の計算を実コード上で検証できる可能性を調べたが、追加の保証は得られていない。
coreのproptestは状態機械等にも使われているが、この予算処理専用の既存proptestとの性能比較を行ったわけではない。

既存テストで確認しにくい具体的な契約が生じ、抽象化の仮定や保守費用を説明できるときに再検討する。
この結果だけで製品側のBTreeMapを変更したり、Kani向けのstubやlint除外を追加したりしない。

## 保存と再現

このPRは調査資料だけを追加する。
harnessは[実験用ソース資料](issue-778/harness.rs.txt)として保存し、通常ビルド・CIからは使わない。
明示実行の製品機能や保守対象の検証基盤を追加しない。
導入・初回実行・再試行のshell資料は同じディレクトリに保存した。
絶対パスは今回の隔離環境用であり、再実行時には専用ディレクトリへ変更する。
`source.tar` は上記hoiminコミットを `git archive` で出力したもの。再現時は作り直す。
`run.sh.txt` のCLI指定は診断後の --tests 版。retryはrunの後に実行する。

通常の公式導入は `cargo install --locked kani-verifier --version 0.68.0` と `cargo kani setup` の2段階。
今回は導入費用を抑えるため、公式release bundleのkani-driverを使い、公式setup実装と同じtoolchain symlinkを専用領域に作った。
この手順はPoC用であり、通常の利用手順として推奨・CI化しない。
Concrete Playbackは実験機能で、生成と再生には同じKani版・コンパイル条件が必要である。今回の試行では使用していない。

## 清掃と今回の文書検証

検証子プロセスが残っていないことを確認し、隔離workspaceでcargo cleanを実施した。
930ファイル・322.4MiBを削除し、隔離領域の使用量は2,778,174,988から2,447,088,565 bytesへ減った。
残るtoolchain・取得物・workspaceも、資料保存後に絶対パスを確認して専用ディレクトリだけを削除し、不在を確認した。
通常の開発用Rust環境・共有venvは清掃対象にしない。

今回の製品コードとCIに差分はないため、通常Rustテスト・Clippy・Pythonテストを再実行したという主張はしない。
Kaniが注入するunstable-feature警告をログに保存し、通常のlint設定を緩めていない。
文書の参照・JSON・出典hash・OKF形式・docs外差分・空白を確認した。
各段階5回のセルフレビューは[レビュー記録](../../reviews/2026-10-11-issue-778-kani.md)に残す。
