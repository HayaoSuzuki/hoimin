## 形式モデルの対応表（モデル作成前）

主張: 必須6 SBOMがすべて存在し検証に成功し、余計なアセットがない場合だけchecksum出力へ進む。拒否時は既存checksumを変更しない。

| 前提・観測 | Lean | 実装での設定・観測 | mode |
| --- | --- | --- | --- |
| 必須SBOMの存在 | present(index) | fixtureの6文書をmaskに応じて削除、checksumsを呼ぶ | strict |
| 全文書検証成功 | valid(index) | 正常fixture / 各存在文書のversion改変 | strict（コーパスの一様boolケース） |
| 余計なファイル | extra | unexpected.txtの追加 | strict |
| 検証拒否後のchecksum | writeIfAccepted(old) | 既存SHA256SUMSのbytesを比較 | strict |
| 任意個数nの検証証明 | n / predicate | 本番は6文書固定 | model-only |
| JSON Schemaと外部generatorの正しさ | 抽象validのみ | 個別テストと実ツール試行で確認 | model-only |

有限探索は6bit存在mask × valid 2値 × extra 2値 = 256ケース。状態遷移の深さは1。20秒の外部timeoutを設ける。欠落を無視するbroken gateと検証前書込のbroken transitionを感度検査とする。重複文書は名前集合で表現できないためJSONグラフ側の単体テストで確認する。再実行は同一gateの冪等性を証明する。

## 限界と判断

実target graphの生成はすべてmacOSホスト上の試行であり、Linux/Windowsのnative build成功の証拠ではない。ローカルの補完試行に使ったartifactは検証用bytesであり、実際のreleaseを作成・公開していない。manylinuxコンテナ、Windows native runner、GitHub Actionsからのupload/publishはこのブランチのCI実行で確認する必要がある。workflowには通常のPR/手動経路でこれらを検証する処理を含めた。

LeanはJSON Schema、Cargo resolver、ファイルシステム、ネットワーク、GitHub実行を証明していない。`strict`の照合はcorpusの入力に限り、任意nの定理は`model-only`である。以前の公開済releaseにSBOMを遡及添付しない。外部API送信、Dependency-Track導入、既存auditの置換は行わない。

実装上の判断: generatorのbuild依存を含む範囲を保持して文書化した。これをruntimeだけの完全なbinary inventoryと読むと過大な保証になるため、metadataと利用文書の両方に範囲を記載した。

文書検査: docs/knowledgeの32文書をYAML parserで構造検査し、新規SBOM概念の出典・脚注・リンクを照合した。日本語文書は対象範囲、モデル上の証明、実実装での観測、未実行のnative CIを区別して推敲した。

## 追補: PR #745のCI失敗への対応

[Windows release job](https://github.com/HayaoSuzuki/hoimin/actions/runs/38022400407/job/114126034607)では、CargoのUTF-8出力をPythonがcp1252として読み、byte `0x8f` で失敗した。`capture_sbom.run` に `encoding="utf-8"` を指定した。実際の子プロセスからUTF-8の標準出力・標準エラーを返し、親の既定codecをcp1252へ固定する回帰テストを追加した。終了コード0と7の両方で修正前の `UnicodeDecodeError` を確認し、修正後は出力と失敗時の診断を保持できた。

[Ubuntu Rust job](https://github.com/HayaoSuzuki/hoimin/actions/runs/38022400447/job/114126215949)では、`rollback_contention_marks_root_for_immediate_janitor_recovery` が `reclaimed_roots=0, preserved_roots=1, details=[]` で失敗した。並列テストがforkすると、子がexecするまでleaseのopen file descriptionを共有し、親が所有者をdropしてもflockが残る可能性がある。既存の `live_managed_child_keeps_the_root_lease_after_the_owner_is_dropped` と同じく、対象テストだけを専用プロセスで実行する構成にした。回収処理は変更せず、coordinatorの競合解除後に1回の回収で削除されるというassertを維持した。

Linux amd64コンテナ上の同期付き実験では、親がleaseをcloseした後もforkした子が保持している間はロック取得に失敗し、子終了後には取得できた。ただし、この実験はロック継承の仕組みを確認したものであり、元のCIで発生した競合そのものの再現ではない。CIログにはほかの保存経路も同じ結果を返す余地があり、Rustの原因は推定である。macOSの変更前のCLI単体テストでは再現しなかった。

追加修正のセルフレビューを5回実施した。

1. 必要性と範囲を確認した。Windowsは配布用SBOM生成を停止させる確定不具合である。Rustはテストが仮定するlease解放条件を並列実行から隔離する修正に限定した。
2. 設計を確認した。UTF-8をstdoutとstderrの両方へ適用し、`check=True` とtimeoutを維持する。Rustは既存の隔離方式を採用し、回収の再試行でassertを弱めない。
3. 実装順序と回帰検出を確認した。文字コードの2ケースはRED→GREENを実行した。Rust子プロセスはexact名、単一test thread、完了sentinelを使い、対象テスト0件での偽成功を防ぐ。
4. 異常系を確認した。非ゼロ終了時もUTF-8の診断と終了コード7を保持する。Rust子プロセスは30秒でtimeoutし、キャンセル時はkillされる。
5. 証拠の範囲を確認した。生成テスト、mutation、形式モデルと実装照合を再実行する。Linuxのロック実験、macOSの全体回帰、hosted CIの成否を別の証拠として扱う。

独立レビューではCritical/Important/Minorの指摘はなかった。Rustの原因を断定せず、Ubuntu CIで再確認するという助言を記録へ反映した。

元のPRチェックではmacOS/Linuxのwheel生成、Quality、Lean audit、bounded fuzz、Rust randomized orderは成功しており、失敗は指定された2ジョブだった。Windows失敗に伴い集約validateとpublishは実行されていない。
