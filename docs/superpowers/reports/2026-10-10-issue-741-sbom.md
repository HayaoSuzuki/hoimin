## 形式モデルの対応表（モデル作成前）

主張: 必須6 SBOMがすべて存在し検証に成功し、余計なアセットがない場合だけchecksum出力へ進む。拒否時は既存checksumを変更しない。

| 前提・観測 | Lean | 実装での設定・観測 | mode |
| --- | --- | --- | --- |
| 必須SBOMの存在 | present(index) | fixtureの6文書をmaskに応じて削除、checksumsを呼ぶ | strict |
| 全文書検証成功 | valid(index) | 正常fixture / 各存在文書のversion改変 | strict（コーパスの一様boolケース） |
| 余計なファイル | extra | unexpected.txtの追加 | strict |
| 検証拒否後のchecksum | writeIfAccepted(old) | 既存SHA256SUMSのbytesを比較 | strict |
| 任意個数nの検証証明 | n / predicate | 本番は6文書固定 | model-only |
| JSON Schemaと外部generatorの正しさ | 抽象validのみ | 個別テストと実ツール試行で確認 | model-only |

有限探索は6bit存在mask × valid 2値 × extra 2値 = 256ケース。状態遷移の深さは1。20秒の外部timeoutを設ける。欠落を無視するbroken gateと検証前書込のbroken transitionを感度検査とする。重複文書は名前集合で表現できないためJSONグラフ側の単体テストで確認する。再実行は同一gateの冪等性を証明する。

## 限界と判断

実target graphの生成はすべてmacOSホスト上の試行であり、Linux/Windowsのnative build成功の証拠ではない。ローカルの補完試行に使ったartifactは検証用bytesであり、実際のreleaseを作成・公開していない。manylinuxコンテナ、Windows native runner、GitHub Actionsからのupload/publishはこのブランチのCI実行で確認する必要がある。workflowには通常のPR/手動経路でこれらを検証する処理を含めた。

LeanはJSON Schema、Cargo resolver、ファイルシステム、ネットワーク、GitHub実行を証明していない。`strict`の照合はcorpusの入力に限り、任意nの定理は`model-only`である。以前の公開済releaseにSBOMを遡及添付しない。外部API送信、Dependency-Track導入、既存auditの置換は行わない。

実装上の判断: generatorのbuild依存を含む範囲を保持して文書化した。これをruntimeだけの完全なbinary inventoryと読むと過大な保証になるため、metadataと利用文書の両方に範囲を記載した。

文書検査: docs/knowledgeの32文書をYAML parserで構造検査し、新規SBOM概念の出典・脚注・リンクを照合した。日本語文書は対象範囲、モデル上の証明、実実装での観測、未実行のnative CIを区別して推敲した。
