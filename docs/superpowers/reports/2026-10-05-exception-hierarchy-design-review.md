# 例外階層ミューテーションの原設計レビュー

Issue: #692。作業ブランチ: `investigate/user-defined-exception-mutations`。
原設計は `cae2edf`、実装の確認対象は `db79321`。
今回は原設計、現在の実装、Lean のモデルを照合し、設計の前提から再検討した。
本変更はレビューと設計・計画の訂正であり、以下の未解決事項を実装修正済みとは扱わない。

後続の[別名伝播の形式監査](2026-10-05-exception-alias-lean-audit.md)で、本文の単純な代入別名の反例を修正し、
Lean の到達経路の証明と抽出情報の対応テストを追加した。本文は `db79321` の監査記録として残す。
関数・container 経由の参照、診断と精度、並行 cache などの指摘は引き続き残る。

## 判定

原設計には不足があった。特に、クラスの定義、名前の束縛、実行時の書き換えを分けた契約がなく、
「保守的に除外する」という方針だけでは、誤った候補を防ぐ範囲を定義できていなかった。
修正後の実装にも、代入で作った別名経由の書き換えを検出できない場合が残る。
現状は限定的な静的解析として評価する必要があり、ユーザ定義例外全般の安全な置換を保証しない。

AST のみで解析する方針、組み込み例外とは独立した明示指定の演算子、既存の候補生成処理への統合、
自動 fingerprint は維持する。見直す対象は、入力から候補までの中間表現とその保証、
候補を捨てる理由、キャッシュの利用条件、資源上限の説明である。

| 優先度 | 指摘 | 現状と処置 |
| --- | --- | --- |
| P1 | 定義の同一性と、利用時の名前の同一性を混同しやすい | 実行時と食い違う候補を再現。別名・作用のモデル化は未実装 |
| P1 | Lean に渡す情報を抽出する境界の検証が不足 | 既存の証明は維持。抽出からの対応検証を次の修正の受入条件にする |
| P2 | 候補の過剰除外と、その理由を説明できない診断 | 公開 planner で再現。理由を保持する設計と正例の評価が必要 |
| P2 | 「一度だけ構築」と並行利用の条件が曖昧 | 通常経路の逐次利用と、並行 API の未保証を文書化。競合修正は未実施 |
| P2 | 件数・入力サイズの制限を、全体のメモリ上限と読める | 保証対象を訂正。ピークメモリと時間の測定は未実施 |

P1 は候補の意味と保証に関わる問題、P2 は説明可能性・精度・運用上の契約の問題を表す。
既存のテスト件数や証明数を、これらの解決の根拠にはしない。

## 第1回: 要件と Python の意味からのレビュー

### 定義と利用時の参照先

原設計の「名前ではなく同一性で解決する」は必要だが、それだけでは足りない。
`ClassId = (path, name)` が識別する定義と、別のモジュールが import する時点の属性値は異なる。
さらに、一度作られたクラスの親は、親を公開したモジュールの属性が再代入されても同じクラスを指す。
したがって、継承辺、公開属性、利用箇所の束縛を別々に扱う必要がある。

次の3ファイルを用いた。これは外部パッケージや動的 import hook による変更ではなく、
すべて解析対象のプロジェクト内にあるコードである。

```python
# errors.py
class Root(Exception): pass
class Child(Root): pass
class Sibling(Root): pass

# patcher.py
import errors as e
other = e
other.Root = object

# service.py
from errors import Root, Child, Sibling
def f():
    raise Child("x")
```

現在の公開 planner は `Child → Root` と `Child → Sibling` を出力し、診断を出さない。
一方、別プロセスの Python で `import patcher, service` の順に実行すると、
元の `f()` は `Child` を送出し、`raise Root("x")` に置換した `f()` は `TypeError` を送出する。
`service.Root` は既に `object` なので、置換は例外階層の変更になっていない。
元のコード自体が壊れているだけの例ではないことも、この対照で確認した。

原因は [Escapes](../../../crates/hoimin-cli/src/analyzer/exception_hierarchy.rs) が
import の別名と書き込み先の先頭名を相関させても、`other = e` の参照先を追跡しないことにある。
前回の修正は直接の import 別名を扱ったが、別名の伝播という設計問題は残った。
現行仕様にも未追跡の object/function alias は対象外と書かれている。
ただし、対象外の構文が別ファイルにあることで、対応している構文の候補まで不正確になる点は、
単に「非対応箇所をスキップする」と説明しては伝わらない。

必要な変更は、対応する別名伝播を明示し、追跡できない参照の流出や書き込みを検出した場合に、
どの定義・属性・利用箇所の信頼を失うかを定義することである。任意の関数呼び出しや外部の変更まで
完全に判定するとは約束しない。未追跡の作用がないという前提と、実際に検出できる構文を分けて示す。

### 機能の有用性と除外の粒度

同じ `errors.py` と `service.py` に対し、次の独立した入力を公開 planner で確認した。
`--file service.py` を指定し、追加ファイルは mutation 対象に選ばなかった。

| 入力の変更 | 候補数 | 診断 |
| --- | ---: | --- |
| 追加ファイルなし | 2 | なし |
| `patcher.py` に `import errors as e` と、未呼び出し関数内の `e.Child = object` | 0 | 共通の skipped 診断 |
| `patcher.py` に `import errors as e; e.label = "metadata"` | 0 | 同上 |
| `service.py` が `Child` だけを import | 0 | 同上 |
| `errors.py` が `class Child(Exception): pass` のみ、service も Child のみを import | 0 | 同上 |
| `exports.py` で3クラスを再 export し、service は exports から import | 0 | 同上 |

未呼び出し関数からの作用を考慮すること自体は、実行順を解析しない設計として説明できる。
しかし無関係な `label` 属性への代入まで provider 全体を無効にするため、精度を失っている。
また、関連例外が存在しない正常なゼロ件と、解析に失敗したゼロ件を利用者が区別できない。
`Collector::occurrence` は `replacements.is_empty()` を skipped に集約し、除外理由を保持しない。
原設計にあった「診断で非対応を説明する」という要件を、この実装では十分に満たせていない。

これらは小さな制御例であり、実プロジェクト全体の候補回収率を測定した結果ではない。
次の評価では、対応を約束する正例について期待する候補の組を先に定める。
同じ階層、別ファイル、module alias、relative import、handler と raise を含め、
無関係な属性・モジュールを追加しても期待する候補が残ることを確認する。
再 export や custom constructor による除外は、対応範囲の選択として別に報告する。

## 第2回: 実装構造とライフサイクルからのレビュー

### 除外規則の追加だけでは保守しにくい

現在の `Module.dynamic` と `BindingKind::Unknown` には、異なる原因の情報が集約される。
import 衝突、書き換え、曖昧なモジュール、未対応構文の結果が同じ状態になるため、
後続処理は「なぜ信頼できないのか」と「どこだけを無効にすべきか」を復元できない。
`resolve_relative_imports`、`exclude_submodule_collisions`、`exclude_mutated_imports`、
`exclude_import_cycles` を順に適用する現在の構成では、情報を失う前に何を保存すべきかが重要になる。
前回 import の由来を別に保持し直したことは、この問題の具体例である。

次の実装では、少なくとも次の責務と入出力を分ける。

| 段階 | 保持する情報 | 次段に渡す条件 |
| --- | --- | --- |
| 入力の固定 | prepared path、bytes hash、module origin | hash 不一致を拒否し、欠落 origin を予約する |
| 構文からの抽出 | scope、定義、import、別名代入、属性書き込み、位置 | 不明な作用を消さずに記録する |
| 名前と作用の解決 | 定義 ID、参照先、影響範囲、除外理由 | 曖昧さで特定済みのクラスを捏造しない |
| 階層の判定 | 親辺、constructor 条件、可視性 | handler と raise の条件を分ける |
| 候補と診断 | span、置換先、理由別集計 | 既存の順序・重複排除・上限に従う |

これは責務の提案であり、上記の型への分割が既に実装済みという意味ではない。
まず抽出結果と除外理由を明示し、候補の組が変わらない範囲で分離する。
既存 `rust.rs` にも scope、name mangling、import write の解析がある。
重複は確認できるが、既存解析は用途と実行時点の扱いが異なるため、そのまま流用できるとは未確認である。
共有化は、共通 helper の前提と正例・反例の一致を確認してから行う。

### キャッシュの共有条件

原設計は「一度構築し Arc で共有」としたが、
[ExceptionProject::load](../../../crates/hoimin-cli/src/analyzer/exception_project.rs) は
キャッシュ確認後に mutex を解放し、構築後に無条件で結果を格納する。
そのため、この API 自体は並行呼び出し時の一度だけの構築・公開を保証しない。
同時に開始した構築が、先に公開された Arc を後から別の Arc で置き換える余地がある。

ただし、通常の run は `RunMachine::analyze_next` が1ファイルずつ分析を要求し、
handler も `&mut self` で結果を待つ。plan の discovery もループ前に index を load する。
したがって、本レビューでは通常利用で競合による誤候補が発生するとは確認していない。
キャンセル後の blocking task の寿命も含め、並行利用の安全性を証明したとは扱わない。

現時点の文書は「逐次の成功した load で同じ index を再利用する」と訂正する。
並行分析へ広げる前に、初期化を1回に制限するか、複数構築を許して最初の成功だけを公開するかを選ぶ。
単に mutex を全構築期間保持すると、待機側のキャンセルが遅れるので、それも受入条件に含める。

### 件数の上限とメモリの上限

64 MiB は保持する decoded source の合計上限であり、プロセスのピークメモリではない。
loader は source 一式を保持し、その上で AST と summary を作る。
binding の集計は `Module::parse` 後に行われるため、65536件という制限から
一時的な allocation が常にその件数以下だとは導けない。
入力サイズ、既存の depth guard、個別の entry 制限は有用だが、それぞれ別の制約である。

原計画の「読み込み前の上限が必要」という指摘は正しかった。
ただし、それを parser・summary・alias 展開・全体の時間まで含めた資源契約にしていなかった。
ピークメモリの具体値や時間計算量は、今回測定していない。新しい定量保証は追加しない。

## 第3回: 形式証明・反例・レビュー方法からのレビュー

### Lean を追加するだけでは抽出の欠落を検出できない

[Lean モデル](../../../formal/HoiminOracle/HoiminOracle/ExceptionHierarchyModel.lean) の
`eligible` は `trustedOrigin` を入力で受け取り、`providerTrusted` は別名と書き込みの集合を受け取る。
その前提の下で、到達性や不透明な名前の除外を証明することには意味がある。
一方で、Python の `other = e` を別名の集合へ正しく反映することまでは証明していない。
今回の例が示すのは、この抽出境界の不足であり、既存の Lean 定理の反例ではない。

当初「graph-only proof では足りない」ことを Lean を見送る理由にした判断は不十分だった。
必要だったのは、証明する不変条件と、実装がその前提を満たすかを確かめる方法を、
設計時に対にして決めることである。後から追加した kernel proof と公開 planner の oracle は維持するが、
抽出済みの入力だけを増やすのでは、同種の欠落を防げない。

次の別名対応では、import、alias assignment、attribute write、opaque escape をイベントとして表し、
別名の伝播と無効化をモデル化する。Rust が Python AST から抽出した事実と、モデルの入力を比較する。
その後に公開 planner の候補と、制御した Python プロセスの結果を比較する。
有限の対応テストと、任意のイベント列についての証明は、保証範囲を分けて記載する。
並行 cache の証明は並行処理をモデル化した場合に限り主張し、現在の逐次 trace の定理を流用しない。

### 3回レビューしても取りこぼした理由

初期レビューは、設計に列挙した境界が実装・テストにあるかの照合に偏っていた。
設計自身が列挙していない「同じオブジェクトへの別名」と「import 時に変わる属性値」を、
独立した作用として先に洗い出せていなかった。3回という回数は、この欠落を補わなかった。

今回は観点を変えて実施した。第1回は元の要件に対する有用性と Python の実行結果、
第2回は情報の保持とライフサイクル、第3回は証明の前提と実装への対応を確認した。
第3回の再点検で、最初に使った `other.Child = object` の例は元コードも壊れるため、
指摘の説得力が弱いと判断した。上記の `other.Root = object` へ変え、元コードが Child を送出する
正例を残した。また、cache の問題は API の契約不足として記録し、通常経路の競合バグとは断定しなかった。

## 検証と残作業

確認対象の HEAD から `cargo build -p hoimin-cli --bin hoimin` を実行し、成功した。
各 fixture を別々の一時ディレクトリに置き、次の公開コマンドの JSON を確認した。

```sh
target/debug/hoimin plan --root "$fixture" --file service.py \
  --operators exception_hierarchy --min-free-space 1B \
  --allow-best-effort-memory -- unused-test-command
```

実行時の対照は `.venv/bin/python -B -c` の別プロセスで行い、
`import patcher, service` 後の `service.f()` が送出する型を取得した。
planner 自体は fixture の Python を実行していない。
共通 fixture と各変更は本書のコード・表に残したため、一時ログがなくても再作成できる。

今回は製品コード・Lean・テストを変更していない。workspace 全テストや Lean の再証明は実施しておらず、
以前の成功を今回の設計の正しさの根拠には使わない。
