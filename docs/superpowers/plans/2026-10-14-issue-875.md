# Issue #875: borrowed review ID indexes

This record is for maintainers reviewing candidate joins, error precedence, and evidence. Baseline: main `49a34a63ac4e995bfefb156f85ff3a934b594e6b`. The existing review command is bounded work: retain its behavior while replacing repeated stable-ID scans. The coordinator approved the short design before implementation.

## Goal and architecture

Build borrowed HashMap indexes once per command for checked plan candidates, loaded report mutants, and the loaded review snapshot. Reuse the plan map for report validation and stale filtering. Use the report map for current and stale execution lookup and the snapshot map for current assessment lookup. Keep the original plan-selected and snapshot vectors as the only display-order sources. Every lookup still checks descriptors where the current code does. No artifact repository, generic indexing framework, or source-validation cache is added.

## Design reviews

1. Traced all four repeated joins: report-to-plan in `input::load_report`, selected-to-snapshot in `run`, current/stale-to-report in `execution`, and snapshot-to-plan in `stale_rows`. The single `record_store` membership scan and transactional store lookup are outside this repeated-join change.
2. Compared checked-input duplicate rules: plan header checks ranking and sequences before stable-ID uniqueness, report structure rejects duplicate IDs before review project/identity validation, and SQLite candidate IDs are primary keys with snapshot key/ID cross-checks. Retain those readers and messages; maps must not create new rejection precedence.
3. Confirmed unique-ID invariants at each production boundary: `load_plan` rejects repeated candidate IDs, report structure validation rejects repeated mutant IDs, and validated SQLite snapshots use candidate IDs as primary keys. The final design collects indexes directly from these checked inputs. No map iteration determines display order; stale rows iterate the original snapshot.
4. Traced error order: report decoding precedes project comparison; each mutant checks its stable identity before its matching plan descriptor. Selected rows check stored identity/source before execution descriptors. Stale errors follow snapshot order. Record checks report membership and source freshness before appending; saved-output wrapping remains after commit.
5. Compared complexity and memory: HashMap lookup is expected constant time, not a worst-case guarantee; construction is expected O(P+R+S), with O(P+R+S) borrowed key/value references and bucket overhead. Candidate/history clones already required by rendering remain unchanged. Seven software-design diagnostics can be assessed (8.75/10); the time-investment ratio is unmeasured. Typed local maps and narrow helpers hide repeated join work without a public interface or configurable policy.
