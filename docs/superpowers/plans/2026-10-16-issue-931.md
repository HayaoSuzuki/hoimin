# Issue #931: one candidate per apply request

Approved scope: the synchronous `WorkspaceHandler::handle_apply_mutation(request)`
uses `request.candidate`, as the owned task already does. Remove the separate
candidate argument and caller clones required only by that argument. Keep active
and pending ownership, prepare/execute/accept, recovery and cleanup unchanged.
Base: `0d3fbc1a1821074d6ba8a2a212116241adc85c4e`.

Consulted the issue body, software-design-philosophy skill, development test
structure, OKF workflow and overview, runtime lifecycle concept, synchronous and
owned apply implementations, their callers, and workspace oracle adapter.

## Design reviews

1. Compared synchronous apply with owned `WorkspaceTask::execute`: only the
   synchronous entry point accepts a second candidate, and ignores the request's.
   Use the request as the single source; no new routing policy is needed.
2. Read create/reset shared operation policy and task completion acceptance.
   Apply can retain its existing worker borrow and error mapping; sharing more
   machinery would broaden this change without reducing the redundant input.
3. Searched repository callers: the test-only shell, integration test and Lean
   adapter can all consume the existing request directly. No compatibility
   wrapper or flag is needed under the approved internal API change.
4. Read the conflicting-candidate regression. Replace that intentionally old
   contract with separate success and rejection viewpoints, parameterized over
   a bounded synchronous/owned driver. Observe bytes, IDs, classified failure,
   original source preservation and active/pending retention.
5. Compared runtime knowledge and public signature documentation. Record the
   migration and current contract while preserving #872's historical rationale.
   No new lifecycle transition or formal-model claim is introduced.

Design score: 7.5/10 before this change (six supported diagnostics), 8.75/10 for
the proposed scope (seven supported). The failed diagnostic is implementation
independence: callers must know which of two candidate values each path uses.
Removing the redundant input resolves that leak. The time-investment diagnostic
is unknown: no measurement establishes that 10–20% of time went to design
improvement. Reaching an evidence-backed 10/10 requires that measurement;
the score does not imply another code change is needed.
