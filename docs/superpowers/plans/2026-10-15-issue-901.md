# Issue 901: one cleanup state per owned root

This implementation record helps maintainers inspect the root cleanup representation and reproduce its checks. The approved issue specifies an internal core refactor; it does not claim a cleanup safety improvement or bug fix. The branch starts at Issue 900 commit `13444f3eb3299c840320c83ccc07f7ff5699e1e8` and its PR targets the Issue 900 branch.

## Design

One ordered `Vec<DiskRootEntry>` owns each root ID and its `DiskCleanupState`: `NotRequested`, `Requested`, or `Completed(DiskCleanupOutcome)`. Completion means an outcome was observed; `Deferred` still leaves the cleanup obligation incomplete and blocks lifecycle finish. The snapshot exposes the same typed entries in registration order. Remove the seven former membership arrays and `has_outcome`, with no compatibility views or alias helpers.

Delivery-specific request and finish conditions derive from `DiskRootId::Delivery`. Process/output drain and monitor settlement gates stay in the existing DiskLifecycle. Clean and Failed outcomes still require successful safety components. Retained stays distinct from Clean, and Delivery must be Clean to finish. Delivery cleanup waits for report settlement, including a failed report; lifecycle finish still requires report success. First-stop and complete secondary evidence handling remain unchanged.

The Lean model and its generated corpus express abstract membership lists. The runtime adapter builds typed expected entries from those lists, validates that memberships agree, and compares registered-order entries directly. It does not rebuild seven old views from the production snapshot. The model transition relation and corpus need no change if their accepted/rejected events and semantic memberships still agree. Root-entry snapshots carry full outcome messages; the existing abstract oracle uses its fixed fixture message, with separate generated Rust tests checking arbitrary message retention.

Scoped software-design score: 8.75/10, seven observed diagnostic rows; the design-time percentage is unmeasured. No observed row fails. The single collection hides per-root state coherence, existing lifecycle gates stay centralized, and comments state snapshot/Deferred semantics. Measure time allocation in future work before claiming the eighth row. Documentation evaluation covers this maintainer record, not the whole repository.

### Five design self-review passes

1. State ownership: inspected disk.rs and every old-field reference. A root entry replaces cross-list membership checks; no generic state-machine framework or duplicated cache is needed.
2. Safety: traced request_cleanup and complete_cleanup. Request requires active=0 and settled safety components; destructive outcomes require success. A Requested state records the already-passed barrier and rejects duplicate completion.
3. Delivery: inspected may_finish and report transitions. Request waits for report settlement rather than only success; finish requires success and a Clean Delivery outcome. Derive identity from the enum.
4. Ordering/evidence: registration order is the typed snapshot order. Diagnostic evidence retains its existing chronological order. The full Failed/Deferred payload belongs in the typed outcome and secondary evidence; copying that message is necessary ownership, not another state list.
5. Formal boundary: inspected guard and shutdown adapters. Keep the abstract generated corpus; validate and map expected memberships into typed entries without compatibility fields in production. Document that old cleanup-list event order is no longer an independent snapshot API.
