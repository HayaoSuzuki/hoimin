# SQLite セッションの検証範囲拡張

公開 SessionHandler の永続化と再開先選択を、既存のロック検証から独立した二つの有限モデルで検証する。Quint の履歴を実際の一時 SQLite DB に再生し、各操作の成功・拒否、lookup 結果、再開先と保存状態を比較する。

Lifecycle は一つの run、二つの mutant、七種類の結果、所有権の取得・解放、終了、中断後の reopen を扱う。Killed/Survived は変更できず、他の五種類は置換できる。lookup で読み戻した結果と resume_policy の再利用判定を比較する。close は正常なハンドル破棄であり、プロセス強制終了や電源断の保証ではない。

Selection は二つの run、二種類の fingerprint、二段階の予算で、最新の適合する未完了 run を選ぶ。load に成功すると保存予算が昇格する。操作ごとにハンドルを閉じ、再開選択と予算が DB に永続化されることを確認する。並行 load の競合は今回のモデルの範囲外とする。

テスト用ドライバが要求の構築、DB 観測、独立した履歴規則を隠す。製品の公開 API は変更しない。二つのモデルを一つに結合して状態数を増やさず、対象領域ごとの不変条件を明示する。既存の 20 秒・RSS 2048 MiB の監視を維持し、負例モデルと製品コードの変異で検出能力を確認する。

公開 transition の停止プロトコルも候補として調査したが、今回の完了範囲は上記の実 DB 二領域とする。内部状態を組み立てたテストを公開プロトコルの検証とは扱わない。

## 設計セルフレビュー

- D1: ロック単体との重複を点検し、DB 再オープン後の状態を対象とした。
- D2: 二つの run と二つの mutant の直積を避け、責務別の二モデルに分離した。
- D3: 再利用可否を DB 読み出し成功と区別し、未確定結果も保存・読出し対象とした。
- D4: load の予算昇格が後続の選択に影響するため、履歴に保存予算を含めた。
- D5: close とクラッシュを区別し、未検証の並行性や停電耐性を文書から除外した。
