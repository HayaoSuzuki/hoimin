# 実装計画

1. Lifecycle/Selection の有限モデル、不変条件、負例、重点スケジュールを追加する。
2. 生成 ITF を公開 SessionHandler へ再生するテストと、同じ契約を独立した履歴で確認する PBT を追加する。
3. CI にモデルと Rust テストを追加する。SQLite のディスク I/O を libFuzzer の高速ループへ入れず、PBT により一時 DB の寿命と履歴長を制限する。既存の純粋状態機械 fuzz campaign は維持・実行する。
4. 製品コードの変異、通常・contracts 構成、モデル再生成の再現性、全体の既存試験、lint と文書生成を確認する。
5. 実測値と限界をレビュー記録に残し、作業ブランチへコミットする。

## 計画セルフレビュー

- P1: 既存 Lean セッションオラクルを確認し、別バックエンドの有限全探索と生成履歴の追加に目的を限定した。
- P2: 正常経路だけでは置換拒否を通らないため、重複 persist の重点履歴を計画した。
- P3: fingerprint 不一致・予算不足・完了済み・複数適合を別ケースで確認する。
- P4: PBT は一つのテスト関数で一つの履歴を扱い、ループをドライバに閉じ込める。AAA を明示する。
- P5: ビルド失敗を変異検出と誤認しない。有限全探索の時間切れも合格としない。

software-design-philosophy: 8/8、10/10（計画の責務分割について）。失敗項目なし。既存 runner と ITF reader を再利用し、二重の実行基盤を作らない。
