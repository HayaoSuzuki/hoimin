# ディスク観測と予約台帳のライブ検証

マージ済みの有限TLC・固定ITF・生成履歴・fuzzに、ディスク観測の新モデルと予約台帳のConnect対応を追加する。ユーザー指定に従い2項目を別コミットにする。

ディスク観測はmax_owned=2/min_free=1、代表的な安全・使用量超過・予約領域到達・同時超過・測定時間変更・異なる測定失敗を扱う。最大3入力の有限モデルで、停止理由の完全な証拠（owned/free/測定時間/message）、後続診断の順序と重複排除、停止後のdispatch拒否を観測する。TLCの期待値は仕様で計算し、Connectは公開DiskLifecycleのsnapshotを投影する。実ディスクを埋めたり実測定を故障させたりしない。

台帳は既存モデルを使い、入力をtyped dispatchとして渡す薄いモデルを追加する。Rust側は公開BudgetLedgerの予約一覧・ID・合計・結果を比較する。通常cargo testにNodeの依存を持ち込まない。既存モデルを書き直す案より、遷移を共有するライブ接続を選ぶ。全モデルを一つの状態機械に結合する案は直積とレビュー負担が大きいため採用しない。

20秒/2048MiBのQuint guard、300秒/2048MiBのConnect全体guard、Cargo同時ビルド2、テスト直列を維持する。有限モデルの成功をRustの任意のスレッドinterleavingの証明と呼ばない。ビルドを重ねず、空き容量確認とcargo cleanを検証・コミットの区切りで行う。

| 回 | 設計レビュー | 計画レビュー |
| --- | --- | --- |
| 1 | 既存diskモデルにない観測payloadを対象にする | ディスク観測、台帳の順に独立コミット |
| 2 | primaryとsecondaryの順序を区別する | 失敗を確認してから実装 |
| 3 | 測定時間も同一性に含める | 正モデルと意味的負例を確認 |
| 4 | 既存台帳の遷移を再利用する | 固定履歴、重点履歴、seed PBTを確認 |
| 5 | モデル境界とリソース上限を固定する | 負例はtool errorを除外し、最後にclean |

software-design-philosophy: 境界の8診断は8/8、10/10。失敗項目なし。モデルは期待値、adapterは公開APIへの変換、共通runnerはライブ生成の設定を所有する。設計の採点であり製品の正しさを採点していない。
