# Issue #966: keep one owner for workspace allowance

## Scope and design review

Baseline `229ce38535142958ab75aa1b0462d8be37dbf77e` already validates grants
against the immutable plan allowance. This change removes the second copy of
that allowance in `PlanState.reservation` and its unreachable revalidation.
`Option<ReservationId>` retains only the binding. No runtime defect is claimed.

1. Ownership review: `WorkspacePlan.aggregate_bytes` owns the planned allowance.
   The only production binding write follows validation against that value;
   plan clones copy the immutable value and share the same state.
2. Type review: `Option<ReservationId>` expresses unbound or bound directly.
   Neither a new enum nor a compatibility tuple or adapter adds useful meaning.
3. Validation review: preflight ID, worker range, aggregate allowance and bound
   reservation are checked in that order, before the worker slot is inserted.
   Zero is a valid allowance, not an unbound sentinel.
4. Concurrency review: the existing state mutex still protects first binding,
   worker admission and publication of the first grant. No lock boundary or
   atomic ordering needs to change to remove the duplicate value.
5. Accounting review: `CopyAllowance.granted` publishes the grant to concurrent
   copies; `charged` tracks dynamic usage. These are separate responsibilities
   from the immutable plan and reservation identity, so both remain.

Software-design-philosophy assessment for this scope: seven of eight diagnostic
rows have evidence (8.75/10). The workspace hides grant validation and copy
accounting behind the existing interface; its internal state now represents
only the information it owns. The field comment describes the invariant, and
this review addresses module boundaries and complexity explicitly. The share
of time spent on design improvement is unmeasured; recording that effort would
establish the remaining diagnostic. No additional abstraction is justified.

## Test development

The original copy tests passed before editing production behavior: 24 passed,
one existing ignored. Three new tests then passed against the old tuple
representation. They characterize existing behavior rather than reproduce a bug.

A finite table covers first and subsequent grants with allowances of zero and
positive values. Another table supplies overlapping invalid conditions to check
preflight, worker range, allowance, reservation and occupied-slot precedence,
including unchanged reservation and worker slots after rejection.

The bounded proptest generates zero to 31 requests with four grant kinds and
four worker indices. Each trace fixes the plan aggregate; grant kinds represent
two valid reservations, a mismatched allowance and a mismatched preflight.
An independent history of accepted raw inputs supplies binding, worker-set and
first-acceptance expectations without calling production validation helpers.
All requests are constructed through the public grant API. Default case counts
and shrinking remain enabled. Each test addresses one invariant, with setup,
action and assertions separated; each rejection case starts with fresh state.

A deliberate mutation disabled the reservation mismatch guard. The finite
precedence test failed with `WorkerAlreadyExists` where `ReservationMismatch`
was required. The mutation was restored before refactoring. This demonstrates
test sensitivity, not a defect in the baseline. After refactoring, the copy
filter passed 27 tests with one existing ignored test.

## Implementation review

1. State review: the only production reservation assignment stores an ID.
   Searches and the diff show no retained allowance tuple or fallback path.
2. Rejection review: the first aggregate check still handles every invalid
   allowance. The deleted branch could only reject an allowance differing from
   the previously validated, immutable plan value.
3. Publication review: `WorkspacePlan::accept_grant` still holds the state lock
   while publishing `CopyAllowance.granted`, before another worker may proceed.
   The existing race test checks this order with the test pause hook.
4. Recovery review: failed materialization still removes the worker slot and
   releases partial charges, retaining the reservation binding. Existing tests
   exercise retry with the same grant and rejection of another reservation.
5. Boundary review: worker drop, cleanup reservation return, manifest scanning,
   dynamic copy charging and core grant construction are unchanged. The existing
   concurrent binding test now asserts the ID directly, retaining its one-winner
   and one-worker-slot checks.
