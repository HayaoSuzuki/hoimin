# Single normalized configuration root (Issue #949)

Baseline: `ddb8ed9504beb04c06bfe11821ebcafffa332714`. Scope: normalized run/plan
configuration ownership and its saved formats. The approved design removes the
outer `root` and retains `Selection.root`; standalone target selection already
owns this field. Consumers read `config.selection.root` directly. No accessor,
fallback, alias, canonicalization, or compatibility adapter is introduced.

## Plan

1. Establish failing tests for the single-root saved shape and rejection of the
   removed field, preserving generated path spelling through run/plan conversion.
2. Remove duplicate storage, construction assignments and mismatch validation;
   migrate execution, discovery, analysis, workspace and report consumers.
3. Advance plan schema 8 to 9, report schema 6 to 7 and package floor 0.10.0 to
   0.11.0. Preserve historical fixtures and add current schema-7 goldens. Update
   schemas, current fixture consumers and migration instructions together.
4. Verify focused behavior, full workspace, strict Clippy, formatting and relevant
   Python/schema/documentation checks. Reuse existing Lean oracle comparisons.
5. Record evidence and review the final contracts in the OKF pages.

## Design self-reviews

1. Ownership: inspected raw, prepared and persisted config constructors. Selection
   is independently useful, so deleting its root would relocate ambiguity rather
   than remove it. Direct field access avoids a forwarding-only API.
2. Validation: only root equality becomes unrepresentable. Missing selectors,
   changed/symbol source prerequisites, import roots, commands and limits retain
   their existing validator and precedence.
3. Persistence: both plan and report embed normalized config. Their versions must
   advance together, while session storage does not embed this config shape.
4. Fingerprints: fingerprint inputs retain logical paths/hashes and selection
   semantics. Worker rechecks must substitute the one root in a clone without
   changing prepared configuration; no fingerprint schema change is warranted.
5. Readers and evidence: progress intentionally treats config as opaque; review
   decodes it strictly. Preserve that difference, reject old artifact versions,
   keep historical goldens, and distinguish schema validation from runtime checks.

Design diagnostic: baseline 6.25/10 (5 of 8 rows demonstrated). Module purpose,
interface depth, ownership of design decisions, interface comments and design
review pass. Duplicate root ownership fails implementation independence and
boundary clarity; the change addresses both. The 10–20% investment criterion is
unmeasured, so the post-change maximum supported score is 8.75/10, not 10/10.

## Implementation self-reviews

1. Constructor audit: raw normalization now moves its root once into Selection;
   environment preparation and both run/plan conversions move Selection without
   adding storage. Removed the unused path import and root mismatch error.
2. Consumer audit: source reads, process cwd, workspace, analyzer, metrics-path
   protection and review project matching now read selection.root. The worker
   recheck performs one replacement on its existing clone.
3. Saved-shape audit: plan 9/report 7 and new golden files agree; schema-6 goldens
   remain byte-for-byte historical inputs. The JSON Schema rejects outer root
   and requires selection.root for non-null normalized config.
4. Reader audit: review probes old report versions before typed decoding so old
   root fields cannot hide rerun guidance. Accepted versions still decode the
   original bytes in full and check the parsed version, retaining duplicate-field
   and trailing-data rejection. Progress keeps opaque config handling.
5. Scope audit: no resume, fingerprint, ranking, candidate or path-normalization
   algorithm changed. Only hoimin package entries advance in the five manifests
   and lockfiles; the unrelated proc-macro-utils 0.10.0 dependency stays intact.
6. Test audit: generated roundtrips preserve root spelling, generated discovery
   uses root-relative files after run/plan conversion, and separate worker tests
   cover original divergence, changed worker bytes and prepared-config retention.
   Existing remaining-selection invalid cases and Lean comparisons are retained.

## CI dependency-policy follow-up

The dependency-policy jobs in [PR #953's CI run](https://github.com/HayaoSuzuki/hoimin/actions/runs/38861595219)
reported that hoimin 0.11.0's Elastic-2.0 license was not explicitly allowed.
The package floor changed in `35c21145`, but `deny.toml` still constrained the
own-crate exceptions to `>=0.10.0, <0.11.0`. Local cargo-deny 0.20.2 reproduced
exit 4 for both locked graphs: main rejected hoimin-core and hoimin-cli 0.11.0;
fuzz rejected hoimin-core 0.11.0. Both source checks passed.

Updated only the two own-crate exception ranges to `>=0.11.0, <0.12.0`. The
global license/source allowlists, hoimin-fuzz allowance, and third-party exceptions
remain unchanged. Corrected the dependency guide's stale 0.5-series statement,
refreshed its OKF evidence, and added an explicit Issue #949 supersession notice
to the compatibility concept while preserving historical format descriptions.

Using the existing cargo-deny 0.20.2 binary, both CI-equivalent commands returned
exit 0 and `licenses ok, sources ok` after the change:

```console
cargo deny --manifest-path Cargo.toml --workspace --all-features --locked --config deny.toml check --deny warnings licenses sources
cargo deny --manifest-path fuzz/Cargo.toml --workspace --all-features --locked --config deny.toml check --deny warnings licenses sources
```

Follow-up self-review:

1. Reproduced the actual rejected own-crate versions in both graphs before editing;
   confirmed the source policy was not the cause.
2. Compared the new range with Cargo and Python's 0.11.0 floor; kept the existing
   one-minor-series bound and crate-name scope rather than adding global ELv2.
3. Checked the diff leaves private fuzz and third-party allowances unchanged;
   used the CI-pinned cargo-deny version and identical locked/all-feature options.
4. Corrected current dependency guidance and distinguished current plan 9/report 7/
   floor 0.11 from historical Issue #936/#939 text in the compatibility concept.
5. Reran strict documentation generation and OKF structure/provenance/link checks.
   No Rust implementation changed, so the previously recorded full Rust suites
   were not rerun. Hosted CI success after this follow-up is not claimed.
