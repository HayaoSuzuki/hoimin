# Issue 955: pending-owned output continuations

Scope: output completion ownership at audited base `578b3657e744c1f6d13b57bcb010bd21bde873c2`.
No external event, CLI, saved format or abstract transition rule changes.

## Design and implementation plan

A private pending completion enum distinguishes ordinary completion kinds from
output continuations. Output continuations explicitly cover baseline (no next
work), run start/end, fatal diagnostic, analysis diagnostic, budget warning and
normal/synthetic worker start/end. The output registration boundary accepts the
output and its continuation together. Generic registration checks that each
returned output already has its pending record. ACK and failure consume that
same record. Retirement clears it once. The run-finished stop guard queries the
pending continuation; acknowledged report history remains in report flags.

1. Establish the focused machine baseline; test the new atomic registration API
   before implementation and distinguish compile-red from behavior regression.
2. Replace ownership and migrate all output producers and consumers.
3. Add finite boundary cases and generated ACK/failure/stop schedules, then run
   focused, full workspace, contracts, Clippy, formatting and documentation checks.
4. Record five reviews per stage, refresh only new OKF evidence and commit.

## Design self-review

1. Read all ten output producers. Baseline alone emits output alongside further
   analysis/finalization work and requires an explicit no-continuation variant.
2. Read completion acceptance: retired and duplicate errors precede pending lookup;
   wrong kinds do not consume the record. Keep that ordering and completed ledger.
3. Read run-start ACK and begin_stop: report_started is historical evidence and
   stop_after_run_started controls a replacement start ACK. Neither is an ID cache.
4. Read failure handlers: diagnostic and run-start failure need consumed identity;
   final-report failure must retain its terminal path after pending removal.
   Capture final-report pending status before acceptance/retirement if needed.
5. Read baseline's subsequent analyze_next/finalize_effects and pending queries:
   early output registration must not block work production. Check the output
   registration invariant at the end of transitions rather than silently skipping
   raw output construction. No external continuation payload or generic framework.

Local philosophy assessment: the old boundary leaks pending/action synchronization
and undocumented producer obligations. The proposed boundary addresses information
hiding, interface depth and newcomer comprehension; seven diagnostic rows can be
evidenced (8.75/10). Design-investment time allocation remains unmeasured, so an
asserted 10/10 would require additional evidence.

## Implementation self-review

1. Enumerated all ten EmitOutput construction sites: each registers the payload
   and explicit continuation together. The only raw RunEffect output constructor
   is now inside register_output. Generic registration asserts this invariant.
2. Compared completion acceptance before/after: the retired/duplicate/unknown/
   wrong-kind checks and cleanup reservation comparison keep their order; only
   completion-kind projection changes. ACK dispatch is now one exhaustive match.
3. Compared each worker arm: StartMutant still starts only after ACK;
   FinishMutant resets or drains; synthetic finish records the worker-owned
   outcome only after ACK. No duplicate worker/outcome ownership was introduced.
4. Inspected all pending consumers: candidate admission and worker invariant count
   specific non-output kinds, so registering outputs earlier does not alter those
   decisions. Baseline's analyze/finalize path does not retire pending work.
   The new baseline table checks both successful and failed baseline followup.
5. Compared terminal/failure paths: final-report pending status is captured before
   acceptance so unrelated pending failures retain terminal handling; diagnostic
   and run-start failure use the consumed record. Retirement clears all continuation
   state, while acknowledged report history remains independent. Corrected a test
   fixture to use typed ReportIo: an Other code string does not mark report failure.

New API test initially failed compilation because register_output and
OutputContinuation did not exist. An initial ResourceControl::default fixture
mistake was corrected and the intended two-error compile-red was rerun before
production changes. This is not a reproduced runtime bug. Behavioral additions
characterize existing semantics: baseline ACK (two exit cases), stop before
run-start ACK (three causes), diagnostic failure (Other/ReportIo), and generated
stop prefixes/suffixes around final ACK or ReportIo failure (128 cases). Existing
adversarial scheduling properties exercise normal/synthetic worker output retry,
late ACK and independently classified result summaries.
