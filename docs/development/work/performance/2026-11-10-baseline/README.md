# hoimin 性能の基準測定

2026年11月10日、`c88d581ce17ff52344a0a3399090eeaea3602f3f` の release バイナリを測定した。既存の29入力形状では522回、監視を挟まない直接計測では65ケースを各9回実行した。直接計測での小規模な `plan` は中央値で約7〜12 ms、リポジトリ内の実コードの全候補探索は約14〜16 msだった。

`verify` の64件実行では、テストプロセスの記録時間の合計が監視込みの総時間の約85%を占めた。次の調査では、プロセス起動・待機とワークスペース処理の内訳を測る。今回は製品コードを変更しておらず、高速化の効果を比較する測定ではない。

## 測定条件

macOS 15.7.7、arm64、Rust 1.99.1、Python 3.12.6で実行した。測定前の作業ツリーは変更なし。ビルドコマンドは `cargo build --release --locked -p hoimin-cli`。既存の thin LTO と strip を維持した。バイナリの SHA-256 は [context.json](context.json) に記録した。

[Rust Performance Book の Benchmarking](https://nnethercote.github.io/perf-book/benchmarking.html) にある、複数の負荷と測定指標を用意する方針を参考にした。既存の [入力形状一覧](../../../performance/shapes.json) の N・2N・4N をすべて測り、実コード2ファイルも追加した。実コードはこのリポジトリのツールとテストであり、外部プロジェクトを代表するコーパスではない。

既存の測定では、同じバイナリを `baseline` と `candidate` の両方に指定した。各ラベル3回、各サイズ計6回を実行し、以下では6回を合わせた中央値を示す。ラベルごとの実行順は固定で、同一バイナリでもラベル間の中央値比は0.73〜1.39だった。この差を改善率として扱わない。

既存の監視は25 ms間隔でプロセスツリーのRSSを取得し、起動から終了確認までの時間を記録する。小さい `plan` では時間が約60〜65 msに集中したため、別途 `/usr/bin/time -l` を使った直接計測を行った。直接計測はケースごとに1回のウォームアップを捨て、乱数シードを固定してケース順を変えながら9巡した。`perf_counter_ns` で外側から測った時間には `time` とCLIの起動、JSON生成、ファイル出力を含む。タイムアウト付きのポーリング待機を時間測定に使わず、終了待機と30秒のアラームを使った。

入力生成とビルドは測定の外で行った。測定中にビルドや別のテストは実行していない。OSキャッシュを消去せず、他のアプリケーションから隔離していない。直接計測では `RUST_LOG` を解除した。各実行の候補数・打ち切り状態・終了コードを確認した。テストコマンドは `python3 -c pass` で、実際のテストスイートの実行時間は含まない。

## plan の直接計測

時間は9回の中央値、RSSはDarwinが報告したCLIプロセスの最大常駐量の中央値。`--version` は起動コストを観察するための参考値であり、その時間を `plan` から差し引いていない。

| 入力 | サイズまたは候補上限 | 時間 ms | 最大RSS MiB | 出力候補数 |
| --- | ---: | ---: | ---: | ---: |
| 起動の参考 `--version` | — | 6.950 | 3.94 | — |
| 1行のBoolean列 | 1,000 / 2,000 / 4,000 | 7.922 / 8.803 / 8.900 | 7.75 / 7.84 / 8.33 | 各1、打ち切り |
| 束縛と呼び出し | 1,000 / 2,000 / 4,000 | 8.585 / 9.797 / 11.616 | 8.39 / 9.23 / 11.11 | 各0 |
| fingerprint対象ファイル | 16 / 32 / 64 | 8.345 / 8.785 / 10.713 | 7.48 / 7.44 / 7.56 | 各1 |
| tools/performance_shapes.py | 候補上限1 | 10.182 | 8.77 | 1、打ち切り |
| tools/performance_shapes.py | 候補上限10,000 | 16.276 | 10.89 | 1,422、完了 |
| tests/test_performance_shapes.py | 候補上限1 | 9.486 | 8.47 | 1、打ち切り |
| tests/test_performance_shapes.py | 候補上限10,000 | 14.236 | 9.95 | 1,142、完了 |

実コードのサイズはそれぞれ34,768 bytesと23,792 bytes。全候補探索の最小〜最大時間は、前者で15.775〜21.148 ms、後者で13.434〜16.035 msだった。小さな差の評価には、このばらつきを考慮する必要がある。

`time` が報告する実行命令数も保存した。束縛入力の中央値はサイズ1,000で約4,824万、4,000で約9,816万命令だった。この入力範囲で処理量の増加を確認できるが、起動処理を含む値から漸近計算量を断定しない。命令数とサイクル数はOSの報告値で、個別の校正は行っていない。

## verify と run の監視込み計測

時間は同一バイナリ6回の中央値。入力形状間でサイズの意味が異なるため、行をまたいだ単純な倍率比較は行わない。

| 入力 | N / 2N / 4N | 時間 ms |
| --- | --- | --- |
| verifyで1件だけ実行 | 候補16 / 32 / 64 | 107.5 / 108.0 / 106.0 |
| verifyで全件実行 | 16 / 32 / 64件 | 366.0 / 620.0 / 1,117.0 |
| runで全件実行 | 4 / 8 / 16件 | 148.0 / 231.0 / 368.5 |
| 複数ファイルのverify | 2 / 4 / 8ファイル | 147.5 / 149.5 / 237.5 |
| workspace内のファイル | 4 / 8 / 16ファイル | 128.5 / 147.5 / 148.0 |
| worker数 | 1 / 2 / 4 | 148.5 / 148.5 / 150.0 |

`verify` 全件実行のイベントから、baselineと各mutantの報告時間を合計した。workerは1で、64件の合計中央値は948.900 ms、総時間に対する割合の中央値は84.7%だった。mutant単体の報告時間の中央値は14.445 ms。16件では合計246.019 ms、割合66.9%となった。この割合はイベント内の経過時間と監視込みの総時間の比較であり、CPU使用率や厳密な工程別の時間配分ではない。残りをすべてRustの解析処理と解釈することもできない。

RSSは短時間のプロセスを捕捉できず、522回中9回で未観測だった。観測できても起動途中だけを捕捉する場合がある。監視のサンプル最大値と直接計測のプロセス最大RSSは別の指標として保存した。今回のサンプル値からヒープのピークやメモリ上限を保証しない。

## 次に測る対象

プロセス実行周辺を優先して調べる。空のPythonコマンドの起動・終了だけの対照計測を追加し、workspace作成・reset・出力処理の時間を別に記録する。実際の利用で遅いテストコマンドも対象にすると、hoimin側の改善で短縮できる割合を見積もれる。

解析側を変更する前には、実プロジェクトで負荷を増やし、CPUと割り当てのプロファイルを取る。[同書の Profiling](https://nnethercote.github.io/perf-book/profiling.html) に従い、必要なら行番号のデバッグ情報を有効にした別ビルドを用意する。今回の環境には `samply` がなく、`xcrun` も `xctrace` を見つけられなかったため、関数単位のホットスポットは未特定。現データだけでデータ構造やアロケータの変更を選ばない。

## 保存データと再実行

- [context.json](context.json): リビジョン、ビルド、SHA-256、測定条件、失敗した初回試行の記録。
- [guarded.json](guarded.json): 既存ハーネスによる522回の観測と集計。同一バイナリ間の `comparisons` は測定ノイズの参考値。
- [direct.json](direct.json): 65ケース・585回の直接計測、範囲、入力ハッシュ、命令数。
- [summary.csv](summary.csv): 29形状・87サイズ点の一覧。直接計測の対象は `plan` の20形状・60サイズ点と、実コード4ケース、起動対照1ケース。
- [verify_breakdown.json](verify_breakdown.json): verify全件実行18回のイベント内報告時間。
- [direct_measure.py](direct_measure.py): 今回の直接計測用スクリプト。リポジトリルートから実行する。製品機能やCIには追加していない。

全stdout/stderrと監視記録は `context.json` の `/tmp` パスに残した。このディレクトリには集計元の数値を保存しているが、`/tmp` の全ファイルは複製していない。

```sh
cargo build --release --locked -p hoimin-cli
python3 tools/performance_shapes.py measure \
  --baseline "$PWD/target/release/hoimin" \
  --candidate "$PWD/target/release/hoimin" \
  --repeats 3 --output /tmp/hoimin-baseline-new
python3 docs/development/work/performance/2026-11-10-baseline/direct_measure.py \
  /tmp/hoimin-direct-new
```

出力先は未作成のパスにする。監視付きの測定には `ps` を実行できる環境が必要。直接計測はmacOSの `/usr/bin/time -l` 出力を前提とする。既存ハーネスはレジストリ検証と522回の観測検証を通過し、直接計測も585回の観測検証を通過した。製品コードを変更していないため、製品の全テストスイートは実行していない。
