# AAA test structure

Base: `a7d94ab`; branch: `refactor/aaa-test-structure`.

## Design

Keep inputs and fixtures together, capture the operation under test, then check
its result and related side effects. Blank lines and domain names identify the
phases; phase labels are unnecessary. Split unrelated scenarios, but preserve
ordered operations when their interaction is the behavior under test. Exception
contexts combine execution with the expected exception assertion naturally.
Keep fixture precondition assertions and diagnostic context.

References: [Semaphore](https://semaphore.io/blog/aaa-pattern-test-automation)
and [Alex Nicolas](https://dev.to/alexnicolascode/mastering-unit-testing-the-power-of-the-aaa-arrange-act-assert-oki).

### Design self-reviews

1. Scope: repository-owned Python and Rust tests; exclude vendored parser code.
2. Behavior: change test structure only; retain production APIs and release version.
3. Assertions: related result fields belong together; one assertion is not a rule.
4. Isolation: independent rejection cases must not inherit earlier mutations.
5. Lifecycle: concurrency, retries and persistence need their ordered interaction.

## Implementation plan

Inventory Python test bodies and Rust unit/integration modules. Separate nested
subject calls from assertions where this makes the operation clear. Split mixed
success/rejection tests and give each case a descriptive name. Preserve property
generators, seeds, limits, platform skips and cleanup. Document the convention in
the development guide. Run strict formatting/lint/type checks and both suites.

### Plan self-reviews

1. Baseline: run selected existing tests before edits; distinguish sandbox errors.
2. Coverage: retain every existing expectation and boundary input when splitting.
3. Fixtures: reuse setup helpers without hiding the operation or assertions.
4. Cost: retain build artifacts during checks; clean Cargo after validation.
5. Verification: compare changed tests with the base, then run complete suites.
