# 評価コードと証跡のレビュー

設計・計画の各5回は実行前の [design.md](design.md) にある。
以下は実装とテストを別の観点から各5回見直した記録。
製品コードの実装レビューではなく、今回追加した固定実験コードのレビューである。

## 実装セルフレビュー

1. 対象とコピー境界。実用モジュールはバイト列でコピーし、line範囲の候補pathを検査した。元ソースに変更なし。既存テストはASTで範囲を選び、本体とdecoratorをそのまま抽出した。
2. 比較の公平性。単体テストだけでは見逃す変異を既存集計テストが検出することが分かったため、その比較を追加した。入力増強の狭い領域は9種類しか生成されないので、各条件40ケースへ揃えた。先行測定は圧縮保存して最終結果から分離した。
3. 外部generatorの信頼境界。allpairspyの3-wayが独立検算に失敗した。生データ、14個の欠落射影、決定的補完を保存し、表では「補完済み」と明記した。生の5ケースを正しい3-wayとして扱わない。
4. 実行結果の所有。候補辞書の一致、baseline終了0、完走、選択件数、pytest終了0/1、出力完備を検査した。CLIが主要測定を担当し、一時コピーへの手動適用は失敗原因の確認だけに限定した。
5. 判定の過剰さ。strict fakeは9件検出するが、実Gitで結果が変わらない `--` 削除も拒否する。これを改善と数えない。mockを迂回する変更、既知のfake不適合、実バグ、新規検出力を混同しない記述へ整理した。

## テストセルフレビュー

1. 1ケース1invocation。入力・関係・backendをpytest.param/parametrizeで分離した。新規テストにAAA区分を付け、既存テストの内容は保存した。
2. 生成と再現性。Hypothesisのseed、生成数、固定corpusを保存。比較前に入力を確定し、別seedも用意した。狭い領域の繰り返しを独立標本と誤記しない。
3. 期待値の独立性。合計は整数の逐次加算、cgroupは4条件の必要性、Gitはファイル操作と公式契約から定義。元コードの結果を採録して正解としない。順序差を許容する契約を固定fakeの診断でも保った。
4. 反例の実測。最初に想定した `[1e16, -1e16, 1.0]` はPython 3.14の改善されたsumでは順序反転の反例にならず、監査が失敗した。実測したオーバーフロー例 `[1e308, 1e308, -1e308]` に修正。証跡のJSONには非標準Infinity値を入れずreprとして保存した。
5. 正負の検査。538ケースの元コード成功、19候補の失敗診断再実行を確認。Leanでは6定理の公理依存なしを確認し、壊した2モデルが拒否された。最初の列挙モデルの30秒timeoutを証明成功として扱わず、明示列挙への簡略化後に検証した。

## software-design-philosophy の再評価

初案は5/8、6.25/10。固定実験へ縮小した最終設計は8/8、10/10と評価する。
点数はこの小さい評価コードの責務と境界に限定した自己評価であり、研究の一般的有効性や製品への採用点ではない。

| 診断 | 判定と根拠 |
|---|---|
| 各モジュールを一文で説明できるか | 可。driverは固定比較の再実行、テストは仕様の観測、監査は証跡と失敗理由の確認、Leanは保証の限界の証明 |
| インターフェースが実装より単純か | 可。driverと監査は引数なし。公開の生成器APIや設定方式を追加しない |
| 呼び出し側を変えずに実装を変更できるか | 可。CLI呼び出し・予算・生成はdriver内、fixture詳細はテスト内に収める |
| インターフェースコメントが約束を説明しているか | 可。各ファイル冒頭に用途と非保証を記述 |
| 設計がレビューに含まれるか | 可。事前の設計5回と本表で複雑性と追加機構の必要性を確認 |
| モジュールが重要な判断を隠しているか | 可。対象選択と予算、契約、証跡検査を各所有者に集中 |
| 実装を読まずに境界を理解できるか | 可。README、design、冒頭コメントで再実行と限界を説明 |
| 設計改善へ投資しているか | 可。一般化した生成基盤を縮小し、候補共有と監査を導入してから測定。時間比率そのものは計測していない |

現在不合格の診断項目はない。複数プロジェクト対応へ拡大する場合はこの評価を引き継がず、対象とデータ境界を再設計する。
