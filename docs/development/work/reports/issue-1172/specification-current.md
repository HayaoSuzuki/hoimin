## 状態

**grilling で合意した仕様に、Lean 監査で確認した境界条件の補足を確定した。今回の作業範囲は仕様・設計評価・Lean 証明・実装前オラクルと、その PR 作成まで。製品の `reduce` は未実装。**

従来の「指定された削除案の検証だけを先行する」という提案は採用しない。`hoimin reduce` 自身が削減案を探索・検証する。製品の実装計画と実装開始は、この仕様・形式検証 PR とは別の作業とする。

## 目的と責務（Q1–Q4、Q6–Q10）

- 既存テストの実行と保守の負担を減らす。
- hoimin が残す定義と削減候補を探索し、検証結果を提示する。
- 最適化の目的は、元のコードに対する通常のテストコマンド全体の経過時間。ミューテーション実行時間やテスト数の最小化を目的関数にしない。
- 予算内で検証できた候補の最良案を返す。全組合せに対する最適性は保証しない。
- 削除の採用には、人間または外部エージェントが、要求・回帰事例の記録としての意味を確認する。kill 保存だけで「不要」と判定しない。
- ソースの実際の削除・書き換えは人間または外部エージェントが行う。hoimin は元ファイルに変更を適用しない。
- 利用者の CI gate は導入せず、ローカルでの改善に用いる。

## 対象指定と削減単位（Q5、Q7、Q10、Q16、Q25）

- 任意のテストコマンドに対応し、pytest 専用にはしない。
- 初版の削減単位は、Python ソース上の一つの関数・メソッド定義。
- 対象のテスト集合とミューテーション対象のソース範囲は明示指定を必須とする。テストはファイルと定義名または名前パターンの両方で限定する。
- 保持指定も同じ指定方式を使い、削減対象と重なった場合は保持を優先する。保持した定義を内包する外側の定義の削除も禁止する。除去する半開バイト区間と保持定義の区間が交差する案は棄却し、隣接するだけの区間は交差とみなさない。
- パラメータ化テストは関数ごと全ケースを一括して扱う。動的生成された個別ケースや doctest 内の一例ずつの削減は対象外。
- 同じファイルに同じ修飾名の定義が複数ある場合、当該定義を対象とする指定は曖昧として拒否する。条件分岐内の同名定義や再定義も含む。異なる名前の複数定義を名前パターンで選択することは認める。

## 作業コピーの変更（Q4–Q5）

- decorator を含む定義全体を作業コピーから除去する。
- 除去により空になった構文ブロックだけ `pass` で補い、構文を維持する。
- 関数本体だけをコメントアウト・`pass` 化して、収集・fixture・decorator の処理を残す方式は採用しない。
- 最終 diff は最終検証した状態を再現する。元のファイルには適用しない。

## 検証の基準（Q3、Q12–Q14、Q17、Q23–Q24）

- 保存済み plan と明示的なミュータント選択を受け取り、その集合を探索中ずっと固定する。削減しやすくするために対象を途中で減らさない。
- 元のスイートが選択集合内で一つも kill できない場合、削減探索を開始しない。
- 元スイートと各削減案について、通常テストの成功を確認する。
- 固定集合内の各ミュータントの killed / survived がすべて一致することを要求する。元の kill を失う案だけでなく、元の survivor が新たに kill される案も棄却する。
- 既存 hoimin と同じく、通常テストの成功を前提として、ミュータント実行時の通常の非ゼロ終了を kill とする。timeout、資源制限、実行基盤のエラー、未実行等を保存成功に読み替えない。
- 任意コマンドの終了コードだけでは assertion の失敗と import・収集エラー等を一般には区別できない。この限界を結果に明記し、保存した実行出力を人間・外部エージェントが確認できるようにする。
- plan の mutant timeout が `auto` の場合、元スイートで一度決めた値を全削減案に固定する。明示的な固定値がある場合はその値を使う。
- 初版では、削減対象ファイルが plan の mutation source または明示的 fingerprint 対象と重なった場合は入力エラーとする。該当ファイルと理由を示し、plan の検証条件を暗黙に緩めない。
- 保存した結果は指定範囲・実行条件での観測であり、将来の不具合検出能力や対象外ソースの要求の保存を保証しない。

## 探索と時間評価（Q6、Q8–Q9、Q11、Q15、Q18）

- 一つずつの削減に加え、複数定義をまとめた削減も探索する。まとまった削減を試し、成立しない集合を小さく分けて探索する。
- 採用のたびに残った集合を基準とし、個別に削除可能だった候補を根拠なく同時削除しない。探索順と予算によって結果が変わることを許容する。
- 構文エラーや通常テスト失敗で棄却できる案は早く除外する。有効な候補の通常テスト実行を原則 3 回測定し、中央値で順位づけする。
- 最低短縮率は既定 5% とし、利用者が `0% < p < 100%` の範囲で変更できる。領域外は探索開始前の設定エラーとする。正確な比率で比較し、割引時間を先に丸めたり、固定幅整数の overflow を許したりしない。
- 最終確認は元スイートと削減後を交互に 3 組測定し、各組で最低短縮率を満たすことを要求する。
- この短縮率と反復測定は測定上の採用基準であり、統計的な保証ではない。基準を満たせなければ短縮を確認できた案として扱わない。
- 実際に観測した時間は正でなければならない。ゼロ時間、時計の逆行、時間の取得不能は測定不成立として探索を停止する。自動再試行・予算延長は行わず、以前に最終確認済みの案だけは保持できる。未観測の測定枠をゼロ時間の観測と混同しない。

## 予算・失敗・停止（Q9、Q11–Q12、Q20–Q22）

- 探索全体の制限時間を明示指定必須にする。元スイートの評価、候補探索、反復測定、最終確認をすべて含める。
- 各子プロセスには既存の資源制限も適用する。各試行の予算だけを守って探索全体が無制限になる設計にはしない。
- 最終確認の時間を確保するため探索を早めに打ち切り、全体予算は自動延長しない。
- 全体予算は一つの単調時計の絶対締切とする。必要な証跡すべての完成時刻が厳密に締切より前の場合だけ新しい案を認証する。同時完了は締切到達を優先し、認証済みの過去の案は保持する。停止後に探索を再開しない。
- OS の子プロセス終了・cleanup・結果の物理書込みが同時刻に完了する保証はしない。これらには既存の資源・後始末契約を適用し、新規探索のために締切を延ばさない。
- 候補の通常テスト失敗やミュータント判定の差は、その候補を棄却して別案の探索を続ける。
- 資源制限、実行基盤のエラー、測定不成立、全体予算切れでは探索を停止する。不確定な結果を採用の根拠にしない。
- 有効な探索を行ったが必要な短縮率を満たす案がない場合は、正常な「短縮を確認できた案なし」として終了コード 0 を返す。入力不正、基盤障害、未完了とは区別する。
- 最終確認を完了した案だけを適用用 diff の対象とする。予算切れや障害で最終確認が終わらない候補は JSON に観測を残すが、diff を生成しない。ほかに最終確認済みの案がなければ diff は出さない。

## 成果物（Q19、Q21–Q22）

- 機械可読の JSON と、最終確認済みの削減案を再現する未適用 diff。
- JSON に、対象・保持・削減候補の定義、測定値、ミュータントごとの比較、探索予算と停止理由を含める。
- 対象のミュータント・テスト・ソースと再現条件を識別できる証跡を保持する。比較不能・未確認の範囲を明示する。
- 短縮を確認できた案がなければ JSON のみとし、削減 diff は生成しない。

## 後続の設計・実装で具体化する事項

以下は、上記の製品仕様を変更しない範囲の実装詳細として決める。再び製品判断が必要になった場合は、未合意の拡張を実装に含めない。

- CLI オプションの正確な名前、名前パターンの文法、JSON schema と成果物の保存先。
- AST の削減対象表現、位置・encoding の扱い、作業コピーと既存実行基盤の接続。
- 探索順、同一候補の再利用、最終確認時間を確保する具体的な予算管理。
- 正常な案なしと、入力不正・元 baseline 失敗・不完全・キャンセルを区別する既存終了契約への対応。
- 条件一致、保持指定、同時削減、反復測定、予算停止、未確認 diff の禁止を確かめる検証計画。

## 設計上の責務

source variant の構成が選択・範囲・保持・snapshot・diff を所有し、証跡ポリシーが率・測定・固定条件・認証を所有し、探索 session が全体予算・実行・認証済み best を所有する。時間順だけで細分化した薄い wrapper や、例外的な保持解除・同時完了・ゼロ時間再試行の設定は追加しない。

## 調査時点の背景と現行実装

以下は仕様確定前に確認した研究と現行実装の記録。上記の合意仕様を採用判断とする。


固定したミュータント集合 M に対し、元のテスト集合 T が kill する集合を K_M(T) とする。基本的な削減条件は、T' ⊆ T かつ K_M(T') = K_M(T)。元から生存していたミュータントまで新たに kill する必要はない。

- [Polo Usaola ら、FASE 2012: Reduction of Test Suites Using Mutation](https://alarcos.esi.uclm.es/ALARNET2/FILES/Articulos/2012-LNCS-7212-FASE-Polo.pdf): kill 行列を用いる貪欲な削減を提案し、ベンチマークと実プログラムで評価。削減余地は対象によって異なる。
- [Shi ら、FSE 2014: Balancing Trade-Offs in Test-Suite Reduction](https://users.ece.utexas.edu/~gligoric/papers/ShiETAL14EvolRed.pdf): 文カバレッジ、kill 集合、両方の保存を比較。kill 集合を保存する削減のテスト数削減率中央値は 51.0%。
- [Shi ら、ISSTA 2018: Evaluating Test-Suite Reduction in Real Software Evolution](https://mir.cs.illinois.edu/marinov/publications/ShiETAL18TSRinReal.pdf): 32 プロジェクト、1,478 件の実際の失敗ビルドで評価。同じ kill 集合を保存しても将来の実不具合検出が失われうる。FBDL は失敗ビルド単位の指標であり、個々のバグの見逃し確率ではない。
- [Chen ら、ASE 2020](https://homes.cs.washington.edu/~rjust/publ/mutants_faults_revisited_ase_2020.pdf): 231 件の実不具合を用いた評価では、ミュータントに基づく削減で多くのテスト集合が実不具合検出能力を維持。
- [Nicourt ら、ICST 2024](https://cnandi.com/docs/icst24-cr.pdf): 61 テストから 34 テストに削減。実不具合を持つ 106 コントラクトに対し、元のスイートは 106 件、削減後は 105 件で不具合を検出。

以上は削減の有用性を支持するが、kill 集合の保存から「テストが不要」「将来も同じ不具合を検出する」とは結論できない。Python と hoimin での費用対効果は未測定。

## 現行 hoimin で確認した制約

- 任意のテストコマンドを扱い、テスト単位の ID や kill 行列は現行レポートにない。
- 通常の非ゼロ終了を killed に分類する。削除の根拠に使う場合、実際のテスト失敗と収集・実行基盤の失敗の区別を検討する必要がある。
- `plan` / `verify` / `progress --details` で小範囲のテスト変更の前後比較は可能。テストだけの変更は、明示的な fingerprint 対象でなければ同じ plan を再利用できる。
- `verify` は plan のテストコマンドと資源予算を継承する。argv を変更して除外する方式は、同じ plan の再利用とそのままでは両立しない。
- `progress` は同一 candidate-ID 集合・baseline 成功・完全な結果を要求するが、テスト収集集合やテスト内容の同一性まで比較するものではない。
- 製品方針はローカルの有用なテスト改善。score 最大化や利用者の CI gate は目的に含めない。
