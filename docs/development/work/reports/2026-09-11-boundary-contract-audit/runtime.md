# Runtime boundary, concurrency, lifecycle, and CI audit

Audit target: `623dd808612dbc34775e16814845eec0bc52dff9`, macOS workspace, 2026-09-11. Read-only tracked-tree audit; no issue creation and no stress/OOM/process-exhaustion tests run. Paths below are repository-relative. Existing issue state comes from `/tmp/hoimin-audit-issues-round4.json` supplied to this task.

## Result

No new runtime bug was confirmed by the safe probes. Subsequent static tracing confirmed a Windows user-facing resource-scope contract contradiction: README/CLI promise run-wide caps, but the native backend places the full configured caps on each root and leaves the run job uncapped. No Windows runtime was executed; see the addendum and separate draft. The repository has substantial concrete timeout/cancellation/cleanup coverage, including real child processes and real CLI interrupts. It does **not** establish exhaustive cross-feature or OS coverage. The main material gaps are already partly tracked: full Linux CLI OOM/process-limit propagation (#228/#229/#157), native backend fault injection (#162), and Windows PID recycling (#223). Manual-only non-Linux CI and optional delegated Linux tests leave meaningful assurance gaps even when ordinary PR CI is green.

A code-traced additional test/scope gap is verification preparation before the run shell: manifest decoding, fingerprint processing, and copy-manifest validation are outside the existing rediscovery timeout tests and before normal run supervision. This is not reported here as a new confirmed defect; it needs reconciliation with existing plan/input-scale issues and the intended total-timeout contract.

## Concurrency and cross-feature coverage

1. **Parallel scheduling and bounded task bookkeeping are concretely covered.** `run_e2e.rs:958` generates >=20 mutants, runs jobs=4, and asserts `max_process_tasks <= 4` and completion-in-flight <=5. This is a finite 24-term expression workload, not a source-scale/RSS upper-bound proof. `workspace_heap.rs:52` retains <=2MiB after materializing four workers over eight 512KiB files; baseline measurement occurs after preflight, so it specifically bounds retained worker-copy heap, not peak preflight memory, RSS, or file-count growth.
2. **Interrupt + parallel children + session is already covered.** `run_e2e.rs:2138` uses jobs=4, a SQLite session, tokenized descendants, injected cancellation, and tests incomplete completion or explicit deferred cleanup if quiescence is unproved. `:2362/:2368` first native interrupt and `:2523/:2529` second interrupt with blocked session finish provide Unix/Windows-specific entrypoints. `:2005` total-timeout plus locked session finish is a real subprocess case. Do not file a generic “no cancellation integration tests” issue.
3. **Report backpressure has real and injected coverage.** Unix `run_e2e.rs:130` fills a report transport for JSON and JSONL, sends SIGINT after output begins, and bounds exit. `shell.rs:6967` rejects output acknowledgment after write/delivery-cleanup failures across all formats; `:6917` preserves a replaced delivery root. The real Unix transport case is not Windows stalled-console/pipe coverage. Human formatting is included in injected output-failure tests but not that real filled-transport SIGINT test.
4. **Preflight/cleanup cancellation regressions are represented.** Closed #332, #330, #331, #335, #342 should not be refiled from historical reports. Current shell tests cover paused materialization, queued final report cancellation (`:7520`), cleanup state restoration (`:7688`), original deadline for successful outer close (`:7960`) and metrics (`:8008`). Linux resource internals test mutex release during root/close cleanup (`resource/linux.rs:1784–1991`).
5. **Disk lifecycle has concrete injected runtime coverage.** `shell.rs:5430–5811` covers initial/pre-dispatch/periodic/post-drain stop, including simultaneous process failure retained as secondary. `:6001–6345` covers final scan timeout, unproved reap, deferred cleanup, and retry after inner monitor timeout. These invoke production shell/lifecycle plumbing with controlled fault/pause hooks; they do not create real ENOSPC or kernel OOM.
6. **Linux and Windows concurrent resource scopes differ in the tests.** Linux `process_handler.rs:583` two ~96MiB roots under run max=160MiB expects some OOM, and two root+child pairs under process max=3 expects some process-limit status. Windows `:1534,1563` explicitly expects both roots to succeed, but its helper is stale: the nominal backend constructor values 160MiB/3 are ignored, and each request actually carries 256MiB/8 from `limits()` at `:77`. Windows `:1585` and Linux `:409` test timeout sibling isolation. Subsequent tracing confirms a public contract contradiction: README:127/163 and CLI help promise one run-wide memory/process cap, while Windows applies full configured limits independently to each nested root and sets only kill-on-close on the run job. Existing tests assert a per-root policy without documenting that public change. See addendum.
7. **Verify runtime composition remains thin.** `tests/plan.rs:537` makes analyzer timeout=1ns and confirms no test-command marker, and `src/plan.rs:1074` pauses rediscovery at 20ms and confirms bounded error before baseline. These do not cover cancellation or total timeout during manifest read/decode and fingerprint/copy preparation (`plan.rs:317–390`), which happens before entering normal run shell (`lib.rs:37–38,140–141`). Verify reuses run execution after preparation, but an explicit test should establish inherited jobs/disk/output/timeout behavior and no preflight execution on failure.

## Addendum: confirmed Windows resource-scope contract contradiction (static)

- README:127 says memory/process limits are run-wide and not multiplied by jobs, README:163 repeats one memory limit shared by analyzer/baseline/all workers, and CLI field docs at `cli.rs:166,186` advertise run-wide memory/descendant caps.
- `WindowsBackend::new(_limits)` at `resource/windows.rs:64` ignores RunLimits. `configure_run_job` at `:675` sets only kill-on-job-close. `create_limited_root_job` at `:662` applies memory and active-process flags to each nested root, from its ProcessLimits. The explicit comment at `:540` says the run-wide job intentionally has no memory/process limits.
- `core/src/machine.rs:659–663,1019–1023` passes the full configured memory/process counts to each process request. Consequently the native source implements a per-root budget, not the advertised shared run-wide budget. This is a confirmed static contract mismatch; empirical aggregate consumption on Windows was not measured here.
- Closed #340 explains the attribution motivation for moving limits to nested jobs. Its body does not update or supersede public README/CLI promises. No existing open matching scope issue was found in the supplied inventory.
- A test-specific gap further obscures this: `process_handler.rs:77` always creates ProcessLimits of 256MiB/8. Windows `hard_handler(...,128MiB,3)`/`(...,160MiB,3)` parameters flow to the now-ignored RunLimits constructor. Native tests still classify eventual overflow, but the named/nominal backend limit is not the actual configured per-root limit. Update fixtures to explicitly set per-request caps and check effective scope. This contrasts with Linux, where constructor RunLimits still constrain the aggregate run.

Suggested regression gate: Windows native jobs=2 with a bounded root/child barrier crossing only the documented aggregate limit; assert the selected aggregate/per-root policy explicitly and verify help/README/report agree. Do not infer success from the current stale fixture parameters or use macOS/core passes as Windows execution evidence.
