# 別名伝播修正後の原設計再レビュー

Issue #692。作業ブランチは `investigate/user-defined-exception-mutations`。
原設計 `cae2edf` と、別名伝播修正後の `2f41888` を比較した。
本書は[前回の原設計レビュー](2026-10-05-exception-hierarchy-design-review.md)を補足する。

## 判定と指摘の状態

原設計には、誤った候補を減らす方針に対して、有用な候補を残す基準と、除外を利用者に説明する契約が不足していた。
別名の伝播とその Lean 証明を追加しても、この不足は解消していない。
今回、無関係な関数の引数名を変えただけで候補が消える例と、解析を断念しても診断が出ない例を再現した。

| 指摘 | 状態 | 次の対応 |
| --- | --- | --- |
| 単純な代入別名の書き込みを追跡できない | 前回修正済み。今回は再修正しない | 既存の回帰と証明を維持 |
| 異なる scope の同名の束縛を合流する | 過剰除外を新たに再現 | 書き込みの辺を scope 付き束縛 ID で表す |
| 解析を断念したことと、候補なしを区別できない | 診断の欠落も新たに再現 | 候補と独立した理由付き解析結果を保持 |
| 対応範囲を絞った場合の有用性を評価していない | 依然未評価 | 正例・除外例と、挙動を保つ変更の比較を受入条件にする |
| Lean の入力となる抽象化自体の妥当性 | 抽出対応は改善。scope を捨てる設計判断は残る | モデル・抽出結果・要件の3者を比較 |
| 並行 cache とピークメモリの契約 | 前回から未解決 | 並行利用・定量保証を広げる前に対応 |

今回の再現は過剰除外と診断欠落であり、新たな実行時の誤置換を確認したという報告ではない。
また、前回の別名修正が無意味だったという評価でもない。追跡できる書き込みを増やした成果と、
その追跡に使う名前の粒度が粗い問題を分けて評価する。

## 第1回: 元の要件と有用性

元の要件は、コードベース内の例外クラスと継承関係を利用した mutation である。
静的解析を選び、既に見える名前だけを置換することは、対象コードを実行せずに候補を作るための選択として維持する。
ただし、階層を取得できることと、実際に役立つ候補を生成できることは別の受入条件にする必要があった。

次の source を `service.py` として公開 planner に渡した。

```python
class Root(Exception): pass
class Child(Root): pass

def unrelated(Root):
    other = Root
    other.tag = 1

def target():
    raise Child()
```

引数 `Root` は module の例外クラスとは異なる束縛である。
別プロセスで `unrelated(Unrelated)` に無関係なクラスを渡し、続けて `target()` を実行したところ、
送出された型は `Child` だった。引数名と右辺の参照を `value` に変更した場合も同じ結果になる。
しかし planner の結果は一致しない。

| 条件 | 候補 | 診断 | Python の送出型 |
| --- | --- | --- | --- |
| unrelated 関数なし | `Child → Root` | なし | Child |
| 上記の引数 Root | なし | skipped | Child |
| 引数と参照を value に改名 | `Child → Root` | なし | Child |

`Escapes.assignments` は `(String, String)` の辺を持ち、scope を区別しない。
そのため、関数内の `other → Root` が module の `Root` にも適用され、クラス束縛を Unknown にする。
この挙動は現在の保守的な合流方針に沿うが、有用性を失う具体例である。
「候補を多く除外してもよい」だけでは、どの程度の精度を満たせば実用的と判断するかが決まらない。

追加の確認では、custom constructor を持つ例外の handler は1候補だった。
同じ custom constructor の raise は0候補、tuple handler も0候補だった。
後者は現状の対応範囲による結果であり、自動的にバグと分類しない。
tuple を扱うか、constructor の互換性を広げるかは機能の設計判断として記録する。
今回の小さな fixture の結果を、実プロジェクトの候補回収率とは呼ばない。

## 第2回: 実装構造と診断

候補がない理由を後から候補列だけで推測する API が、診断の不足につながっている。
`ExceptionIndex::replacements` は空の `Vec` を返し、`Collector::occurrence` は通常それを skipped にまとめる。
一方、`self.disabled` の場合は skipped を設定する前に戻る。
解析の停止理由と、正当な候補なしを別々に表現していない。

次の source は動的名前空間操作の可能性として保守的に除外されるが、診断を出さなかった。

```python
class Root(Exception): pass
class Child(Root): pass
def target():
    eval("1")
    raise Child()
```

対照として `class Child(Exception): pass` と `target()` だけを置いた場合、
関連する user-defined 例外がない正常な0候補に skipped 診断が出た。
bare raise の0候補は診断なしだった。したがって、現在は「診断がないから解析できた」とも、
「診断があるから構文を解析できなかった」とも判断できない。
元の「非対応を説明する」という要求を、単一 bool の実装で満たしたと評価した点が不十分だった。

次の設計変更では、内部結果を少なくとも次の3つに分ける。

- 解析でき、置換候補がある。
- 解析できるが、この関係・可視性・constructor 方針では置換候補がない。
- scope の無効化、未解決の束縛、未対応の構文などにより判断を打ち切った。

打ち切り時には理由と発生箇所を、候補生成とは独立して保持する。
外向きの診断は既存の出力構造で件数を制限し、内部の理由を先に捨てない。
理由の追加を外向きの必須 JSON field の追加と混同せず、互換性を維持して段階的に導入する。

scope の精度については、module ごとの文字列集合から、module・scope・正規化名で区別する束縛へ移す。
global/nonlocal、外側の自由変数、class のローカルが method の closure にならないことを解決してから、
別名の辺を張る。単に各関数へ番号を付けるだけでは、正当な跨 scope の参照まで切れてしまう。
既存の scope 解析との共通化は候補だが、そのまま流用できると確認したわけではない。
クラスの定義 ID を全面的に作り直す前に、まず書き込み解析の束縛 ID を分離する。

## 第3回: 証明の前提と完了判定

Lean の別名定理は、与えた辺に沿って書き込みが伝わることを証明する。
今回の Root 引数の例でも、scope を捨てた辺を与えれば、その辺に従って正しく伝播する。
Rust の抽出結果と Lean の期待値が一致しても、scope を捨てた判断が用途に適切かは別に評価する必要がある。
これは既存の定理の反例ではなく、モデルの入力に何を残すべきかという設計問題である。

scope 付き束縛に移行するときは、無関係なローカル名の変更が候補を変えない対照例と、
global/nonlocal を通る実際の書き込みが候補を抑制する反例を、モデル・抽出・公開 planner の各段階に置く。
単に既存の証明数や corpus 件数を増やして完了判定に使わない。

レビュー方法にも改善が必要だった。初期計画は「列挙した非対応をテストしたか」の確認が中心で、
「意味を変えない編集で結果が不当に変わらないか」という比較が欠けていた。
今後は対応範囲ごとに、候補を生成する正例、除外する反例、無関係な変更を加えた対照例を組にする。
仕様上の除外と、解析器の能力不足による除外を分けた状態で、未完了事項を管理する。

## 検証と変更範囲

```sh
  --operators exception_hierarchy --min-free-space 1B \
  --allow-best-effort-memory -- unused-test-command
```

planner 自体は対象の Python を実行していない。

今回は設計レビューと設計書・計画書の更新であり、製品コード・テスト・Lean の変更はない。
workspace テストや Lean の再証明は実施していない。
診断欠落と scope 合流による過剰除外は未修正として残し、次の実装の受入条件を具体化した。
