# Quint による予算台帳の状態遷移検証

## 対象と採用理由

参考は `pytest-allpair/formal/quint/pruning.qnt`。Quint 0.33.1 と TLC による有限状態の全探索、意図的な誤りの検出、Rust 実装との照合を引き継ぐ。hoimin では Lean と Creusot が既に算術を扱うため、最初の対象は公開 API `BudgetLedger::reserve/release` の操作順序とする。

Quint を追加するだけではモデルの正しさしか確認できない。モデルの ITF 履歴を Rust 実装へ再生し、返却値、各種類の予約総量、個々の予約を比較する。PBT と fuzz は、有限探索の範囲を超える操作列と u64 境界を独立した参照台帳と比較する。製品コードへ検証用 API は追加しない。

## 境界と所有権

`formal/quint/budget.qnt` が有限モデル、操作の意味、不変条件を所有する。通常モデルと過剰予約を許す負の対照を同じモジュールの定数で切り替える。容量は各種類2、成功予約は最大2個、種類は3種類、予約量は0〜3、release の ID は0〜2。予約上限後も release と失敗予約を扱う。有限状態の全探索であり、実装全体や無限の操作列の定理証明ではない。u64 の ID 枯渇、OS プロセス、並行実行の正当性は対象外。

Rust のテスト支援モジュールが実装との対応を所有する。ITF の期待状態を計算し直さず読み取る。PBT/fuzz 用の参照モデルはコマンド履歴から状態を計算するため、Quint オラクルの再生とは別経路とする。テスト関数は AAA とし、シナリオ実行の反復・分岐を支援モジュールへ閉じ込める。

検証コマンドは既存のプロセスツリー資源ガードを再利用し、TLC は1 worker・Java heap 1 GiB、各検査は時間・RSS の上限を持つ。ツール未導入や時間切れを成功・反例検出として扱わない。npm lock で Quint を固定する。通常の cargo test はコミット済み履歴を使い Node/Java を要求しない。CI はモデル検査、履歴の再生成差分、通常 Rust テストを接続する。

## 代案

TLA+ を手書きで併設すると同じ遷移を二重管理する。Quint から TLC へ渡す方式を採る。Apalache の symbolic checking backend は初回対象が有限であるため採用しない。Quint から TLA+ への変換には Apalache を使用する。既存 Lean モデルの翻訳だけでは検証手法を増やす効果が小さいため、公開 API に接続できる台帳を選ぶ。
