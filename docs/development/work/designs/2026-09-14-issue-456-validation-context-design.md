# Issue #456: verify のファイル単位の候補検証

## 要求と現状

Issue https://github.com/tokyogas-tech/hoimin/issues/456 を対象とする。基準は origin/main の 165a2d2。`validate_requested_candidates` はファイルbytesを保持しても、候補ごとに `validate_candidate` を呼ぶため、ソース長 S と候補数 C に対して前処理が O(S×C) になる。`CandidateValidationContext` は既存の借用型で、ハッシュ・UTF-8検証・行索引を共有できる。

## 採用する構造

要求された既存候補をパス別の参照リストへまとめる。要求IDの従来の順序で処理し、ファイルへ初めて到達したときだけbytesを読む。そのファイルの要求候補を一つの context で検証し、候補ごとの成功またはエラーを保存する。各候補の結果は元のID順に取り出す。bytes と context は一ファイルの検証後に破棄する。

存在しないID、選択外のパス、ファイル読み取り失敗、descriptor不一致、stable ID不一致の優先順は従来と同じにする。他ファイルのエラーを先に返さない。再発見による照合と、そのタイムアウト・選択・候補上限は変更しない。検証は source/hash/span/original/line/column/operator/stable ID の全項目を維持する。

前処理は要求されたファイルbytesの合計に比例する。候補の参照と結果は O(C)、前処理中のsourceと行索引は最大一ファイル分となる。行内のUnicode列計算は #470 の対象であり、この変更だけで候補検証全体を O(S+C) と断定しない。

## 代替案

全ソースを先に読み借用 context を保持する案は単純だが、無関係な後続ファイルの読み取りエラーが先行候補のエラーより先に出る。core の context を所有型へ変更する案は公開APIへの変更範囲が広い。採用案は結果の一時保持を増やすが、ソース全量の保持を減らし、既存core APIと診断順を維持できる。

## 検証

実際のcontext構築を数えるテスト用観測で、1/2/4ファイルと複数候補について構築数と処理bytesを確認する。valid/改ざん候補は単件検証APIと同じ結果になることを照合し、独立した期待エラーもassertする。エラーのID順、異なるファイル、非UTF-8、空集合を確認する。既存plan/verifyテストとworkspace品質ゲートを実行する。release計測は前処理比較と実CLIを分け、環境・反復回数・入力・未実施条件を残す。

## 設計セルフレビュー

1. Issue の全受け入れ条件を照合。ソース複製を増やさない条件を、一ファイルずつ解放する構造で具体化した。
2. 診断互換性を点検。パス順にまとめて即時エラーを返す案を退け、要求ID順に結果を取り出す設計に修正した。
3. 改訂版を読み直し、列計算の二乗処理を #456 の改善率へ含めない限界と、core APIを変えない条件を明記した。実装・計測の成功はまだ主張しない。
