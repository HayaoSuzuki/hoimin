# Issue #127 Candidate Cursor Design

## Goal

Eliminate the bounded 2 MiB backward read and previous-record JSON parse from each candidate replay while preserving candidate order, record-boundary, corruption, and declared-record-count validation.

## Current Problem

`CandidateStore::replay_one` receives only a byte offset. To determine the sequence expected at that offset, it seeks backward by up to `MAX_SPOOL_RECORD_BYTES + 1`, finds the preceding record, and parses that record solely to calculate `previous.sequence + 1`. Repeating this operation for every candidate causes large redundant reads and parses on the dispatch path.

## Considered Approaches

### Carry an explicit candidate cursor

Represent replay position as both the byte offset and the sequence expected at that offset. The run state owns the cursor, each read effect carries it, and a successful read returns the next cursor. Candidate replay can validate the current record without reading the previous record. Selected because it removes the redundant work entirely and makes the validation input explicit.

### Scan backward only to the preceding newline

Read backward in small blocks until the preceding record boundary is found, then parse the previous record. This bounds working memory and can reduce read amplification for short records, but every replay still performs extra I/O, scans bytes, and parses an unrelated record. Rejected because it leaves the underlying repeated-work problem in place.

### Store an offset-to-sequence index

Build and retain an index for every spool record. This permits direct lookup but adds memory proportional to candidate count and another lifetime-managed data structure when the state machine already advances through candidates in sequence. Rejected as unnecessary complexity.

## Architecture

Introduce `CandidateCursor` in `hoimin-core` with an `offset: u64` and `expected_sequence: u64`. Its initial value is offset zero and expected sequence one. `RunState` stores the cursor instead of a bare candidate offset, and `ReadCandidate` carries the full cursor to the shell.

`CandidateStore::replay_one` accepts the cursor. A successful read returns the candidate and a next cursor whose offset is the end of the current newline-terminated record and whose expected sequence is incremented by one. `CandidateLoaded` returns that next cursor to the state machine, which advances its stored cursor only when it accepts the matching completion.

The existing `RunState::candidate_offset` query remains available and projects the cursor's offset so callers that only observe progress do not need to change. No cursor is written into the candidate spool, and the spool's line-delimited JSON format remains unchanged.

`ReadCandidate` and `CandidateLoaded` are internal orchestration payloads rather than persisted or externally supported wire formats. Their Serde field shape may change with this refactoring; no legacy field alias or migration is required.

## Validation and Error Handling

Replay retains the existing one-byte record-boundary check: a nonzero cursor offset must point immediately after a newline. An offset beyond the file length remains `StoreError::InvalidOffset`.

For a non-EOF cursor, replay parses only the current bounded record and requires its sequence to equal `cursor.expected_sequence`. A mismatch remains `StoreError::InvalidSequence`. A candidate sequence greater than the spool's declared record count remains invalid. Computing the next offset or next expected sequence uses checked arithmetic and reports the existing typed offset or sequence error on overflow.

At EOF, `cursor.expected_sequence - 1` is the number of records already consumed. Replay compares that value with `CandidateSpoolRef::records`: fewer records produces `UnexpectedEof`, equality produces `None`, and more records produces `InvalidSequence`. An expected sequence of zero is invalid rather than being normalized with saturating arithmetic.

The cursor is an internal trusted continuation token generated by successful replay and advanced by the state machine. Supplying an arbitrary boundary and matching sequence can intentionally begin replay at that record; validation does not reconstruct history by rereading earlier records.

## Testing

Store tests will cover initial replay, arbitrary valid cursors, cursor advancement, EOF, invalid offsets, expected-sequence mismatches, truncated spools, excess records, and arithmetic boundaries. A deterministic regression test will corrupt the previous record body while preserving its trailing newline, then replay the following record with a valid cursor. Successful replay proves the implementation neither reads nor JSON-parses the previous record.

State-machine tests will assert that `ReadCandidate` receives the current cursor, accepted `CandidateLoaded` events advance both cursor fields, and rejected or unrelated completions do not advance it. Existing candidate property tests will track cursor values rather than bare offsets and continue checking replay from every recorded boundary.

Focused store and machine tests run first, followed by the complete Rust workspace tests, formatting, Clippy, and contract-feature tests.

## Scope

This change does not alter the spool encoding, candidate schema, CLI surface, spool lifetime, async I/O scheduling, worker materialization, or line indexing. It addresses only Issue #127's repeated derivation of the expected candidate sequence.
