# Issue 470: 候補列番号索引の設計

## 対象と契約

解析器は候補の開始位置をバイトオフセットで受け取り、物理行を1始まり、列を0始まりのUnicode scalar value数で返す。先頭のUTF-8 BOMだけは表示上の列から除外する。LF、CRLF、lone CR、タブ、2～4バイトの文字、2行目以降のU+FEFFについて、既存のバイトspanと列の意味を変えない。

現在は候補ごとに行頭から開始位置まで `chars().count()` で走査するため、一つの長い行に候補がN個あると列計算の総量がO(N²)になる。候補上限は保持数だけを制限し、候補発見時の列計算を省かない。

## 採用する索引

`hoimin-core` に `PythonSourceIndex` を追加する。構築時に物理行の開始位置と、UTF-8の各文字がASCIIより余分に使うバイト数の累積値を保存する。ASCII文字は補助要素を追加しないため、ASCIIだけの入力に対する補助記憶量は行開始配列を除いて一定である。

列照会では、二分探索で行頭を選び、開始位置までのバイト数から同じ行内の余分なUTF-8バイト数を引く。ファイル先頭のBOMを含む位置では、BOMを一文字として数えた結果からさらに1を引く。照会順には依存しない。

解析器の `LineIndex` と `CandidateValidationContext` は同じ索引を使う。公開済みの `python_line_starts` と `python_source_column` は互換性のため残し、後者は単発照会用の契約を維持する。候補スキーマ、検証エラーの順序、stable ID、候補順位、truncationは変更しない。

## 検証

coreのテストでは、改行形式、BOM、ASCII、結合文字、2～4バイト文字、無効なUTF-8境界を独立した期待値で確認する。解析器のテストでは、同じ候補を長い1行と複数行へ配置し、候補の位置と順序を確認する。

テスト専用統計は列照会数と補助索引の二分探索比較数を記録する。長いASCII 1行では候補数を増やしても文字prefixの走査量が増えないことを、経過時間の閾値を使わず確認する。releaseのignored benchmarkは実測値だけを出し、合否条件にはしない。

## 限界と再確認条件

索引はUTF-8ソース全体を一度走査する。解析器全体の時間やAST生成量は制限しない。Ruffのオフセット契約、Pythonの物理行規則、BOMの扱い、候補検証のエラー順序を変更するときは、coreと解析器の位置対応を再確認する。

## 設計セルフレビュー

1. 契約レビューでは、Issue #469で定めたBOM、Unicode scalar value、元バイトspanの条件を採用方式に対応付けた。修正点として、BOMのUTF-8余剰2バイトだけでなく表示上の1文字も除くことを明記した。
2. 境界レビューでは、AST訪問順がオフセット順とは限らないため、直前照会を使う可変キャッシュ案を退けた。任意順の二分探索を採用した。
3. 費用レビューでは、全文字の開始位置を保存する案はASCII入力でO(source bytes)の追加記憶になるため退けた。非ASCII文字だけを表す疎な累積索引と、時間に依存しない比較数検査を選んだ。
