# Issue 564: nullable annotation builtin provenance

Nullable addition must target known builtin scalar names and builtin collection constructors only when the existing annotation-scope resolver proves their provenance. Track str/int/float/bool/bytes alongside list/set/dict, including wildcard and dynamic uncertainty. Module/class annotations account for later bindings; function headers exclude their own runtime locals, while enclosing function locals and type parameters shadow builtins.

Pass AstFacts into nullable eligibility and check builtin provenance separately from supported syntax/import spelling. Check scalar names and builtin constructors throughout the supported annotation, including nested type arguments. Preserve standard-library aliases such as `from typing import Sequence as list`: their resolved constructor is typing.Sequence, not a bare builtin. Leave typing-alias temporal analysis (#558), collection-pair generation (#548), and the disallowed-syntax tuple recursion fix (#565) independent. This change adds only builtin provenance checks to nullable addition; nullable removal retains its existing contract.

Rejected alternatives: spelling-only matching reproduces the bug; runtime lookup uses the wrong evaluation boundary for deferred annotations; rejecting all annotations in a scope loses builtin positives and function-header candidates. Reuse annotation_resolution rather than creating another resolver. This is conservative static analysis, not a proof of arbitrary dynamic builtins modification or Python type semantics.

Verification covers all eight names, prior/later/conditional and dynamic bindings, custom classes with failing metaclass union, module/class/function/type-parameter boundaries, nested arguments, trusted imports with builtin-looking local aliases, and positive builtin controls. Public plan exercises executable CPython 3.14 annotations and candidate spans. Broader tests protect the existing collection and nullable-removal paths.
