# Issue 563: copy-policy resume compatibility

The same source and fingerprint-file bytes can execute differently when worker copying includes or excludes a supporting file. Resume must not reuse determinate results across that change.

## Contract and implementation

Add the normalized RunConfig selection's include and exclude pattern lists to FingerprintInput. Encode each list separately, preserving pattern order and exact spelling: override matching can depend on order, and textual glob equivalence is not safe to infer. Empty lists remain explicit. Schema version becomes 8; version 7 hashes cannot select a version 8 run. Existing SQLite storage needs no migration, and old runs remain readable.

Use length-delimited UTF-8 values and distinct field tags 10 and 11. Keep jobs and max-output excluded from compatibility. Identical policies reuse results. Conservatively starting a new run for equivalent but differently spelled patterns is acceptable; discovering a complete copy manifest or hashing arbitrary auxiliary files is outside this issue.

## Verification

Core tests exercise include/exclude additions, removals, order, list boundaries, and from_config propagation. Existing tests cover jobs/max-output neutrality. Public CLI tests run an incomplete session with a strict.flag-dependent assertion, resume under changed copy policy, and compare with a fresh session under the new policy. Exercise adding/removing excludes and includes, plus unchanged policies. Keep all source/test/flag bytes and explicit fingerprint-file inputs unchanged. Assert baseline success, candidate identity, verdict, process termination, and run identity; a changed policy must execute rather than import an old result.

## Constraints

Rust 1.88 minimum; no new dependencies. Keep tests portable. Session databases reside outside fixture roots. Do not change source selection or copy matching semantics.
