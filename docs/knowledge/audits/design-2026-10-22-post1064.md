# Scope and decisions

This is a fresh static audit of main at `d1bf54987cb196b2bcb497fffe763ab06420fd66`
on 2026-10-22, after PR #1064 merged. Its four preceding findings (#1060–#1063)
are resolved; the findings below concern different consumers. The earlier audit
and its execution evidence remain historical records.[^previous]

The accepted product decisions remain: a local CLI for trusted projects, no
backward-compatibility adapters or saved-format migration, no TOML configuration
expansion, and feature removal eligible for evaluation. Retain review's SQLite
history, progress's multiple-history saturation and existing formal sources.
Malicious-test sandboxing is outside this trust boundary.[^principles][^compatibility]

The grilling decision tree is settled for this audit: product scope, trust
boundary and evidence thresholds were confirmed earlier in the conversation.
Facts were explored in three independent source reviews and challenged by a fresh
reviewer; no new product tradeoff required another user decision. Static repeated
work may justify an Issue with a measurement plan, but performance percentages
require measurements. No builds, behavioral tests, native Windows execution,
large fixtures, sustained writers or benchmarks were run for this audit.

## Source membership and useful private types

`resolve_explicit` scans all source roots for each available Python path at
`target.rs:214`, then repeats membership checks for exact selectors at `:276`.
`is_within` constructs a directory prefix on each comparison; Windows also
rebuilds case keys. With N disjoint sibling source directories and one Python
file per directory, whole-file admission performs N(N+1)/2 comparisons. This is
a derived operation count, not elapsed-time or RSS evidence. The CLI invokes
core resolution after indexed discovery.[^target][^discovery]

A private prepared source-scope owner can index normalized root keys and query a
path's component ancestors. Preserve the ordered source list used by symbol
module lookup. A type or enum is useful only if it distinguishes the actual
semantics: an empty source vector admits no whole-file targets but leaves exact
file/line selectors unrestricted; a normalized `.` root admits the entire root.
Do not conflate them or add public configuration and global cache ownership.

Acceptance must vary distinct root count and file count independently, compare
operation/key construction counts against the old scan, and preserve values,
order, diagnostics, overlaps, component boundaries and Windows case behavior.
Measure both ordinary one-root inputs and many-root inputs before claiming a
speedup; the prepared set adds O(S) keys rather than promising lower memory.

## Finite source and fingerprint I/O

`WorkerRoot::read` uses `read_to_end`; its hash uses
`blake3::Hasher::update_reader`. Both follow EOF without a descriptor-length
budget. The portable reader and plan source owner delegate to these operations;
plan record hashing, descriptor validation and fingerprint exact/glob inputs
reach them. A regular file appended during reading can extend work, and source
read can retain the appended bytes.[^root][^reader][^plan-source][^plan][^fingerprint]

The plan source and preparation paths each own blocking operations. Their async
waiters can stop waiting while started filesystem work retains ownership and
continues. This finding concerns finite bytes and retained blocking work; it
does not claim that the async waiter itself is uncancellable.[^plan-source][^preparation]

Read the initial descriptor length plus at most one growth-probe byte; reject
shrinkage or growth rather than accept a prefix. Preserve stable large files
without a new fixed cap. Share a finite I/O primitive below artifact and workspace
policies if useful; avoid making workspace depend on artifact input policy.
Verify with small deterministic append/truncate fixtures through production
source and fingerprint paths. Preserve no-follow, root-relative and regular-file
rules. This is neither an atomic snapshot nor detection of same-length rewrites,
and does not bound arbitrary filesystem I/O time. No exploit or production
frequency was established; this is a resource-hardening concern in the existing
local trust boundary, separate from #1061's duplicate-report reader.

## Windows state ownership

Every production insertion into `RunState.exited_roots` first removes or drains
the matching `active` registration. Completion already accepts either set
membership or absence from `active`. Consequently set membership adds no fact.
`ActiveRoot.record_exit` only controls this redundant recording, carrying
interest arguments and detach/forget/unregister updates with it.[^windows]

Retain active UUID/PID/owned-handle registrations until a corresponding packet or
confirmed empty run job removes them. A signaled-handle fallback satisfies the
barrier while leaving that registration untouched. Remove the duplicate set and
its interest rules rather than encode them into more variants. Preserve both
notification drains, oldest-matching-PID order, timeout/retry, native empty-job
confirmation and independent nested-limit classification.

This revisits #967 with a complete reader/writer trace: that earlier record
justified replacing an unused signal with notification interest, but the current
interest's only consumer maintains redundant completion membership. It is not a
claim that the earlier PID-generation protections are unnecessary.[^windows-history]

Native Windows backend, process-handler and resource-scope suites are required
for implementation acceptance. Existing representation assertions should become
observable wait/ownership checks. Keep formal sources; their existing models do
not cover all Win32 packet and PID-generation semantics. This audit establishes
neither a native regression nor a measured speed improvement.

indexes; YAML structure and the allowlisted public-site build do not validate
all knowledge references.[^workflow]

# Rejected changes and compatibility checks

- Current strict schema rejection and checked reconstruction are input validation,
  not obsolete compatibility adapters. `ReusedMutationStatus` and
  `ResumeDecision` already distinguish resume evidence; no additional migration
  path is needed.[^compatibility][^resume]
- `DiffPlan::Legacy` names a current route for rename/copy/unmerged or long-path
  cases, not support for an old saved format. No obsolete adapter or feature
  removal was established by this audit.[^history]
- Process reaping, draining, monitoring and cleanup represent independent facts.
  Telemetry totals cross-check independent worker accounting. Collapsing them
  merely because values often correlate would remove checks.[^previous][^telemetry]
- Budget release-history/frontier replacement still lacks benefit: the current
  production flow reserves one workspace grant per run. Dense-ID coupling does
  not become useful just because a different enum is available.[^budget][^machine][^archived-audit]
- Existing iterative exception traversal, reverse alias adjacency and recent
  admission fixes already address known performance shapes. Broad parser caps
  need new evidence before becoming follow-up Issues.[^graph][^aliases][^previous]
- Release-tool exception adapters have current callers; they were not shown to
  be backward-compatibility scaffolding.[^release][^archived-audit]

local path existence inventory and independent challenge. Source hashes below
identify clean bytes at the audited revision. Documentation checks for this
record are recorded in its PR; they do not imply behavioral execution or full
catalog content verification. The new synthesis remains draft.

Recheck these findings when target source semantics, descriptor read policy,
Windows packet/registration ownership or repository source paths change. Keep
implementation measurements and native execution evidence separate from this
static record.
