# #1085 — session hardlinkによる元ファイル変更

既存sessionのpathはcanonicalizeされるが、hardlinkは別のpathのままである。artifact除外もpath単位なので、
project外のDB名が空のsourceと同じinodeを指していても、sourceはcopy manifestへ残る。
preflight後にsessionを開き、空の既存DBを受理・初期化すると、同じ実体のsourceがSQLiteへ変わる。
original検証はその後なので、変更を検出しても元bytesは戻らない。[^session][^schema][^shell][^machine][^manifest][^copy]

現行mainを変更せず、`cargo build --offline --locked -p hoimin-cli` を2 jobs・debug情報なし・incremental無効で
実行した。公開CLIを次の小型fixtureで2回実行し、project内・外の両session aliasで再現を確認した。
この実行はmacOS上のもので、Windows/Linuxでの公開CLI再現は今回行っていない。

- `project/__init__.py` は空。`project/calc.py` は `x = 1 + 2\n`。
- 空の `__init__.py` から別名の `session.sqlite3` をhardlinkする。
- `hoimin run --root PROJECT --source . --session SESSION --allow-best-effort-memory --min-free-space 1B --max-mutants 1 --jobs 1 --total-timeout 5s -- /usr/bin/true`。
- 各subprocessのTMPDIRも専用一時領域に設定し、共有の管理rootをstartup janitorが調べないようにした。

| 保存先 | 変更前source | 変更後source | 結果 |
| --- | ---: | ---: | --- |
| project外のhardlink | 0 bytes | 53,248 bytes | SQLite header、同じinode、link数2、exit2 |
| project内の別名hardlink | 0 bytes | 53,248 bytes | SQLite header、同じinode、link数2、exit2 |

両方の診断は `workspace.original.changed`。baselineはnull、mutantsは0件で、sourceとsession aliasは同じbytesに
なった。専用TMPDIRのjanitor inspected/reclaimedは0件。53,248はこのfixtureでの観測値であり、
変更量の一般値ではない。悪意ある攻撃やsandbox突破を実証した主張でもない。
実行JSONと再現scriptは同worktreeの `.superpowers/audit-post1084/` に残す。

修正案は、既存sessionの開いた通常fileからnative link数を取得し、複数linkをSQLite書込み前に拒否すること。
workerのhardlink拒否は別経路である。小さい共通file情報の取得は再利用できるが、source全体のinode索引や
新しいcacheを追加しない。aliasの切断・削除・自動修復と、空DB受理の全廃も行わない。
[^schema][^root]

合否条件は、現行Rust公開CLIで上記2配置を拒否し、source/aliasのbytes・mode、補助file、テスト未開始を確認すること。
現在形式のsession hardlinkも拒否し、通常の単一リンクDBの新規・空DB・reopen/resumeと既存schema拒否を維持する。
UnixとWindowsのnative検証を要求し、持続writerや時間閾値には依存しない。

# #1086 — 全tokenの参照Vec

Python analyzerはparsed moduleがtoken配列を所有している間に、全token参照を別Vecへcollectする。
後続はiteration、前後のslice、getしか使わず、同じtokenを借用できる。T tokensに対して余分な線形初期化と
`T * size_of::<&Token>()` の参照payloadを持つ。これはコード上の計算であり、RSS/時間の測定値ではない。
候補上限が小さくてもこのVecは作る。[^analyzer][^cli-analyzer][^parser]

Cargo.lockの `littrs-ruff-python-ast 0.6.2` と、インストール済みの当該dependency sourceの
`src/token/tokens.rs` を照合した。`Tokens` は `Deref<Target=[Token]>` を持ち、所有配列のsliceを返す。
既存sliceを借り、前後参照で二重参照を外す `.copied()` を不要にすれば、同じ順序・`Option<&Token>` を使える。
新しいcache、隣接索引、wrapper、dependency更新は不要であり、コードも減る。[^lock][^analyzer]

測定案は1/4/16 KiB程度の有効source。実token view取得・走査のallocatorを観測し、parse/facts/line-indexの生成と
区別する。候補順序、ID、span/replacement、trivia、compound operator、Unicode、f/t string、selection、
truncation、cancellationの既存回帰を維持する。必要なら一時probeを使い、製品APIや合成counterだけで測定を代替しない。
性能測定・回帰REDは今回未実行。

これは#1078の履歴コピー、#1083のID確認だけの一時projectionとは別の最適化である。前の監査で候補所有まで

# 型・enum・状態・互換性で見送った候補

- **新しい状態enumの増設。** WorkerState、SessionMode、RunIdentity、MutationOutcome、checked RunConfig、VerifiedPlanは
  現在必要なcoupled stateとhandoffを既に表す。独立して同時成立するoutcome boolやactive/seen集合を単一enumへ潰さない。
  Reportのmode文字列も実行backendを選ぶ権限は持たず、文字列だからという理由で新しい型を追加しない。
  [^machine][^config][^report][^plan][^resource]
- **run gateとrequest cancellationの同一化。** 同じmoduleに似たAtomicBool/Notify/Mutexの処理があるが、run全体と個別processの
  取消権限が異なり、spawn時に両方をlockする。instanceを統合すると意味やdeadlock条件が変わる。機構だけ共有するhelperも、
  今回具体的な欠陥・変更増幅を示せないため単独Issueにはしない。[^process][^shell]
- **Linuxの登録前cgroup生成。** root登録より前の失敗が疑わしかったが、親runの再帰cleanupが登録有無によらずsubtreeを回収する。
  子spawnもprepare成功後である。registry未登録だけを理由に孤児化と報告しない。[^linux][^process]
- **configとfingerprintの検証重複。** RunConfigは純粋な設定意味を認証し、source freshnessは別責務である。
  PlanConfig/RunConfigDataのfield違い、prepared/observed fingerprint、各境界の再観測を互換処理や不要なcacheと混同しない。
  [^config][^plan][^fingerprint]
- **spoolの二段serializeとreviewの全履歴検証。** counting passはretained payload/record上限を確保前に守る。
  storeの全履歴検証も壊れた非選択履歴を受け入れない条件であり、単にselectedだけ読めばよいとはしない。
  progressの隣接2report保持・複数履歴metadataも必要な停止判定に残す。[^spool][^review-store][^progress]
- **legacy/fallbackの名前。** DiffPlan::Legacyは現在のgit入力、OSのcleanup fallbackとPythonの名前解決fallbackは
  現在の意味に必要。schema/fingerprintの拒否診断は古い形式を受理するadapterではない。
  型・interfaceの範囲では、削除すべき互換adapterは新たに確認しなかった。[^compatibility][^git][^analyzer][^portable][^windows]
- **機能廃止やTOML追加。** review/progressの廃止や利用者向けTOML設定の導入を必要とする新しい根拠はない。
  形式証明の保留Issue、GC等の既存未解決Issueは状態を変えず、重複起票しない。[^principles][^progress]
