# 前提とgrillingの判断

互換reader、alias維持、migrationは不要という合意を引き継ぐ。
既存機能の廃止も検討対象だが、reviewの永続履歴、複数reportからのsaturation、
形式証明の資料は残す。信頼するローカルprojectで使うCLIとして、元ファイル・保存先の
誤更新、入力検証、有限の処理量、配布経路を調べる。悪意あるtestのsandbox、任意の
並行writer/path置換/hot-journal/電源断全般の保証は追加しない。[^principles][^compatibility]

性能は明確な余分な走査・コピー・保持をコードで確認できるものを、測定方法と合否条件を
付けて起票する既存方針を適用する。大規模なベンチマークや全体RSS改善率の推測は行わない。

新しい判断は、**sessionの既存補助ファイルにも複数hardlinkの一律拒否を適用するか**。
本体が新規でも補助ファイルが存在する場合があり、現在形式の既存DBでもWAL/SHMへの
書込みで元sourceが変わる。単一リンクの通常補助ファイルは継続し、自動削除・変換・修復を
追加しない方針を推奨して質問した。回答前のため、この候補の起票は保留している。既に合意済みの性能基準で扱える#1089は独立に起票した。

# session補助ファイルによる元ファイル変更

`schema::open` は既存DB本体を開いたdescriptorのlink数で拒否するが、SQLiteが別名で
開く `-journal` / `-wal` / `-shm` には同じ検査がない。
`prepare_session_artifacts` のliteral exclusionはworkerへコピーするpathを除外するもので、
別名の元sourceと同じ実体を共有していることを禁止しない。整合性検査は変更後のエラーに
なり、元ファイルを復元しない。[^schema][^links][^shell][^session][^companions]

## 公開CLIでの観測

現行worktreeのsourceからCLIだけを `cargo build --offline --locked -p hoimin-cli --bin hoimin`
でビルドした。実行したのはこのbinaryであり、インストール済みCLIは使っていない。
各caseは独立した一時directoryを使い、TMPDIR/TMP/TEMPもfixture内へ隔離した。
sourceは空の `__init__.py` と `calc.py` の `x = 1 + 2`。session補助ファイルを空sourceの
hardlinkにし、`--operators binary_add_sub --max-mutants 1 --jobs 1` で実行した。

| DB状態 | 補助ファイル | sessionの配置 | 元sourceの長さの変化 | exit / baseline |
| --- | --- | --- | --- | --- |
| 新規 | -journal | project内・外 | 0 → 512 bytes | 2 / 未実行 |
| 新規 | -wal | project内・外 | 0 → 32,992 bytes | 2 / 未実行 |
| 新規 | -shm | project内・外 | 0 → 32,768 bytes | 2 / 未実行 |
| 現行DB | -journal | project外 | 0 → 0 bytes、変更なし | 1 / 実行 |
| 現行DB | -wal | project外 | 0 → 24,752 bytes | 2 / 未実行 |
| 現行DB | -shm | project外 | 0 → 32,768 bytes | 2 / 未実行 |

変更した8ケースすべてが、その後 `workspace.original.changed` で終了した。
新規のinside/outside各3ケースと、現行DBのWAL/SHM各1ケースである。
現行DBは同じCLIで正常なsessionを一度作り、closeした後に補助ファイルを置いた。
対照のexit 1はsurvivor1件・complete trueの通常結果であり、起動失敗ではない。
全13最終ケースのjanitor reclaimed_rootsは0。元sourceのpermissionも別途観測した。

対照として、DB本体のhardlinkは変更前の `session.open` で拒否された。
各補助ファイルのsymlinkは元sourceを変更せずSQLiteのopen/beginで拒否された。
したがって「すべてのaliasで元ファイルが変わる」と一般化しない。
現行DBのjournalケースも変更なしなので、再現表と一律拒否という推奨方針を区別する。

証拠と再現scriptはworktree内の `.superpowers/audit-post1088/` に保存した。
`session-sidecars.json` は13ケースの長さ・変更有無・permission・exit・diagnostic・janitor、
`reproduce-session-sidecars.py` は使ったfixture、`build.log` は現行binaryのビルド結果。
最初のfixtureではmax-mutantsによるpartial exit 4とsurvivor exit 1を対照の失敗と
誤判定したため、operatorを1種に絞り、complete true/exit 1を確認する形へ修正して再実行した。
これはCLIの別の不具合としては起票しない。

## 改善の合否条件

既存の補助ファイルが複数hardlinkなら、DB本体が新規・空・現行のいずれでも、file-backed
SQLite接続より前に拒否する。元sourceと補助ファイルのbytes/permission、既存DB本体と他の
補助ファイルを変更せず、新しい補助ファイルやrun lockも作らず、baselineを実行しない。
通常の新規sessionと、単一リンクの空/現行DB・通常補助ファイル・resumeを維持する。
補助ファイルの削除・unlink・journal mode変換は行わない。既存のnative link数取得を再利用し、
project全体のinode索引や互換readerは追加しない。Windows/Linux/macOSでnative回帰が必要。

read-onlyのschema照合やversion拒否にもSQLiteによる補助ファイル操作があり得るため、検査は
任意のfile-backed接続より前に置く。任意の並行writerやpath置換を同期する保証ではない。

# 比較・検証にしか使わないdescriptorの所有コピー

完全なcandidate metadataを表す `CandidateDescriptor` は、候補のIDとsequenceを除外して
source/位置/変異内容を比較する。`From<&MutationCandidate>` はoriginal、replacement、path、
operator、symbol、file_hashをcloneする。現行APIのsource検証もowned descriptorを要求する。
[^candidate]

この所有型はstoreへ保存する際には必要だが、次の経路では比較・検証直後に破棄する。

| 実行経路 | 余分な所有 |
| --- | --- |
| plan.rs:988 | current/plannedの完全一致比較で両側の本文をコピー |
| plan.rs:1057–1059 / workspace/mutation.rs:32 | source検証だけのためにdescriptorをコピー |
| review/input.rs:58–62 | report/planの完全一致比較で両側をコピー |
| review/input.rs:192 | source検証用コピー |
| review/mod.rs:218 | 表示候補とreport実行結果の照合で両側をコピー |

[^plan][^mutation][^review-input][^review]

比較・検証のための共通の借用表現へ変更すれば、所有型を要求するAPIが原因のコピーを除ける。
既存CandidateIdentityRefだけではoriginal/location/symbol等を比較できないので、identityだけの
比較へ弱めない。MutationCandidate全体のEqもID/sequenceを含むため代わりにならない。
`validate_source_state` が検証で返るIDを捨てて再計算する点も、同じ検証境界で戻り値を再利用する。

測定は未実施。copy量は候補本文等の総長に比例し、両側変換ではその2組分となるが、JSON decode、
source取得、再発見が全体peakを決める場合もある。比較/検証の実区間で16/64候補と4/16/64 KiB本文を
使い、descriptor由来の割当増分が消えること、全field比較とsource検証のエラー優先順位を測定する。
全体RSS、処理時間、削減率の数値は今回の監査結果として主張しない。

storeに保存するReviewKeyとdescriptor、stale候補の復元、独立したsource snapshotの所有は残す。
表示用の期待ReviewKeyも同じ借用境界で不要なコピーを消せる場合に限って対象にする。

# 型・enum・状態管理で見送った候補

- **report kind**：既にRunStartedKind enumとString専用deserializeがあり、文字列以外と別tagを拒否する。
  単一variantの外部tag enumをそのまま使わないのも、object表現の受理を防ぐため。[^report-reader]
- **ReviewDocument.command**：static strは唯一の生成元のReviewArgs網羅matchで決まる出力ラベル。

  直積を単一enumへまとめても不正状態が減るとは示せなかった。[^progress-input][^progress-duplicates]
- **WorkerState/RunIdentity/checked RunConfig/VerifiedPlan**：phaseのデータ・所有・handoffを既に型で表す。
  RunFlagsのincomplete/error/interrupt等も同時成立する理由があり、単一phase enumへ置換する根拠はない。
  modelの意味を変える新しい不整合は実証していない。[^machine][^config][^plan]
- **互換性に見える分岐**：DiffPlan::Legacyは現在のrename/unmergedとglobal pairing用。旧Gitの互換readerではない。
  schema/version/fingerprintの拒否は取り違え防止、progressのcontent matchingは比較機能そのもの、
  cgroup/Windowsのfallbackは現在のnative API・cleanupの制約を処理する。名前だけで削除しない。[^git][^progress-compare][^owned]

review履歴、複数reportによるsaturation、形式証明の機能を廃止する新しい根拠はない。
今回検査した境界に、新たに削除すべき旧形式migrationは確認しなかった。

# 他の性能・安全性の検討と限界

previewのcloneはmanifest解放前の一時peakで、API/所有権変更が必要になるため、今回の
descriptor問題と同程度の優先度とは判定しなかった。spoolの二段serializeは事前のrecord/payload上限を
担い、per-record openの最適化も現状は効果未測定なので追加Issueにしない。[^plan][^analyzer-store]

有限readのSnapshotReader、artifactのregular-file/上限検証、workerのmanifest長とhardlink拒否、
metricsのatomic rename先entry保護、literal session artifact除外、reviewの4保存先entryと
protected inputのfile identity照合を確認した。これらは責務が異なり、同じpathを複数回見るだけで
重複状態と判定しない。reviewのDELETE header拒否とprivate初期化後のno-replace公開も残す。
[^finite][^companions][^mutation-root][^manifest][^metrics][^review-input][^store]

配布経路ではreleaseのpull_request_targetがmerged/closedに限定され、write jobがmerge commitを
checkoutすること、PR previewはread tokenであること、PyPIのOIDC publish jobにsource checkoutが
ないことを確認した。新しい実証済み欠陥は確認しなかった。これは実環境のpermission設定、外部依存、
release race全般の安全性の証明ではなく、配布workflowは今回実行していない。[^release][^pypi][^release-tool]
