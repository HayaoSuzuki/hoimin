# 監査・起票時点の既存方針とgrillingのfrontier

互換reader・旧schema alias・migrationは不要。機能廃止も評価対象だが、review履歴、複数reportの
saturation判定、形式証明の資料を残す既存合意は維持する。信頼するローカルprojectのCLIとして、
元ファイルと保存先の誤更新、入力検証、有限の読取り・処理量、配布元を確認する。
任意の悪意あるtest programを隔離するsandboxや、長期のartifact運用は追加しない。
性能はコード上の余分な処理と測定方法を分け、未測定の時間・RSS・改善率を推測しない。[^principles][^compatibility]

未確定のfrontierは前回からのsession補助ファイル保護だけ。
`-journal`／`-wal`／`-shm`に複数hardlinkがあれば、任意のfile-backed SQLite接続前に拒否する方針を推奨して質問した。
単一リンクの通常ファイルとresumeは維持し、自動削除・変換・修復は追加しない。
後続の明示依頼により、不具合の記録として[#1094](https://github.com/HayaoSuzuki/hoimin/issues/1094)を起票した。
修正案は提案として分け、起票依頼を実装方式の最終承認とは扱わない。
それ以外は継続中の製品方針で評価でき、新たにユーザー判断を必要とする機能削除案はなかった。

起票直前のmainは`ee6d6ac9`（#1091のuv更新）。上記4 session関連filesに監査基点からの差分がないことを
再確認し、既存open Issueとの重複も確認した。監査基点とsource hashは`e8f0e7b7`の記録として維持する。

# 互換性・機能廃止

旧schema readerやmigrationを再導入している経路は確認しなかった。current schemaの検証、source freshness、
resumeの同一条件確認、現行wire enumの未知値拒否は、過去版の互換性維持とは区別する。
GitのDiffPlan::Legacyはglobal rename pairingやunmerged等のpatch意味を維持する経路であり、旧Git版の
互換readerではない。progressのcontent fallbackも現在の比較機能である。
`historical diagnostic`やpost-panic挙動維持というcommentだけを根拠に処理を削除しない。
[^git-tracked][^plan][^progress-compare]

review履歴は判断・理由・証拠を次のagent作業へ引き継ぐ役割を持つ。複数reportのsaturation判定も
短い改善ループで価値があるという既存判断を覆す新しい根拠はなかった。形式証明Issue #1019–#1022は
実装へ直ちに着手する対象とはせず、今回closeや削除をしない。

# 性能の見送り根拠

- analyzerのexception indexはArcでcacheされる。targetごとのloadを全project再解析とは数えない。[^analyzer-project]
- progressは隣接する2reportだけを保持し、全reportの本文を保存しない。ID集合はeligibility、content indexはfallbackの別契約を持つ。[^progress][^progress-compare]
- review sourceはpath別にgroup化してfile/contextを一度に読む。#1089のborrowed descriptorとID再利用も維持されている。[^review-input][^candidate]
- review storeは全履歴を検証するが、selected以外のevent全体を保持しない。全検証を除くには破損検知契約の変更が必要。[^review-store]
- workspace resetの比較はtestによる任意変更の検出を担い、未変更fileのrestoreは既に省略する。[^reset]
- analyzer spoolのcounting serializationとencoded Vecは残るが、事前record上限とpayload予約を保証する。#1092のJSON spoolと同一視して事前検証を削除しない。[^analyzer-store]
