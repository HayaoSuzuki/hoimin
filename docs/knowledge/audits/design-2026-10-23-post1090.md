# #1092 — JSON mutant recordの全量buffer

既定JSON経路では、ReportHandlerからJsonReport::recordが呼ばれ、MutantFinishedの出力前に
lifecycleをPoisonedへ変える。write_mutantはseparatorとevent全体を新規Vecへserializeしてから
private spoolへwrite_allし、成功時だけhas_mutantsとlifecycleを更新する。
追加heapはeventのencoded lengthに比例する。候補数全体の履歴はdisk spoolなので、
候補数に比例する保持問題とは区別する。[^report-handler][^report-json][^shell]

## #463の意図を保持する

全量Vecは#463が意図的に導入したものである。serializerの細かなwriteをrecord単位にまとめ、
spoolへの書込みが終わる前にOutputEmittedを返さないためで、persistent BufWriterの遅延error/ackは
却下されている。現在の100小event=100 underlying writes、short writeの完遂、WriteZero/partial failureの
即時ReportIoとpoisonを保護するtestsもある。今回これらのtestsは読取りのみで実行していない。
[^spec-463][^report-tests]

改善候補は、record処理中だけ存在する固定容量bufferを使い、成功時に明示flushしてからackする方式。
失敗時には未送信bytesをDropで再送しない。同じ方針の8 KiB buffer・into_partsがdiagnostic JSONLに
既にある。小recordの1writeを維持し、大recordの複数のまとまったwriteと引き換えに全量encoded bufferを
持たないことを測定する。unbuffered serializationへ戻す変更でも、persistent bufferのack protocol変更でもない。
[^report-jsonl][^report-json]

## 測定と合否条件

- 実ReportHandler::handleに16/64 events、original/replacement各4/16/64 KiBのfinite fixtureを渡す。
  fixture生成・source所有は計測外とし、非収集seekable spool/sink stdoutで全量Vecがpeakを隠さないようにする。
- encoded event長に比例するbuffer由来の割当が消えることをrequested Rust heapで測る。小recordの固定buffer overheadも記録する。
- 100小event=100 underlying writesを維持し、大recordのwrite回数・総bytesも測定する。
  field単位の細かなwriteへ戻る、または必要な既存保証を維持できない方式は採用しない。
- short/Interrupted write、WriteZero、partial failure、即時ReportIo、poison、retry/finalize時の追加writeなしを維持する。
  serialization failureでもpoisonを維持し、has_mutantsを成功前に更新しない。
- comma/order/escapingを含む最終JSONのbytes/schema/event/outcomeを比較する。

大規模benchmark、新しいCLI設定や公開型・状態機械は不要。run/baselineの別保持と、analyzer spoolの
事前上限検証は今回のIssueに混ぜない。今回の改善率・RSS・速度の数値は未測定である。[^report-heap][^analyzer-store]

# 他の性能候補を見送った理由

progressのID集合とcontent indexはeligibilityとduplicate判定で役割が異なり、隣接2reportの保持も必要な
範囲へ限定されている。Gitのinventory/patch/numstatはrename pairingとbinary除外の責務がある。
exception hierarchyのsource取得はbounded indexとfingerprint検証を担う。[^progress-compare][^git][^analyzer]

symbol preflightはbaseline前にmissing-symbolを拒否するため、後続parseとの単純共有はsource/ASTの寿命を
延ばし得る。workerのApplying/Finishing cloneも非同期continuationの証拠を保持するため、削除には所有protocolの
再設計が必要になる。いずれも今回の小さいbuffer改善に混ぜない。[^machine][^analyzer]

表示時の期待ReviewKeyは#1089の時点で認識済みの任意範囲で、保存modelの所有境界を共有する。
同じ残存cloneを新しい指摘として繰り返さない。[^implementation]

SQLiteが書込み、8ケースで元sourceが変更されてからworkspace.original.changedになった。
新規DBのjournal/WAL/SHMはproject内・外の各1ケース、現行DBのWAL/SHMはproject外の各1ケース。
全13最終ケースでjanitor回収0という前回記録を参照する。[^previous]

今回のschema::openも本体descriptorのlink数だけを検査し、companionに相当するadmissionはない。
前回再現時から現在まで、session/schema.rs、session/mod.rs、shell.rs、artifacts/mod.rsには差分がないことを確認した。
今回はnative probeを再実行していないため、新たな実行結果としては数えない。拒否方針に回答が来るまでは、
一律拒否を承認済みとは扱わず、この候補の起票を保留する。[^schema][^session][^shell][^artifacts]

## 新しい欠陥を確認しなかった境界

- reviewはDB本体/journal/WAL/SHMのentryを、plan/report/source/fingerprint入力とopened-file identityで照合してからstoreを開く。
  protected sourceの補助ファイルaliasをsessionと同様の欠落として再起票しない。[^review-input]
- reviewは既存の空fileを初期化せず、regular/size/DELETE headerとapplication ID・schema・project・integrity等を検証する。
  sessionの空Python source初期化をそのまま転用して脆弱性とは扱わない。[^review-store]
- metricsは新規temp fileを保持parent経由でrenameし、既存destの別hardlinkのreferentを書き換えない。
  保存entryの衝突保護と、inode自体を書き換えるsessionの保護を区別する。[^metrics][^metrics-destination]
- artifactはregular descriptorと上限+1 byte、source snapshotはdescriptor観測長+1 byteで有限readを行う。
  同一長のrewrite検知やfilesystem I/O時間の上限は別の保証である。[^artifacts][^finite]
- 配布provenanceはrepo/workflow/source digest/signer/predicate/hosted runnerを束縛し、signatureとSLSA build identityを照合する。
  追加のbypassは確認しなかった。外部サービスの現行設定やworkflow実行を検証したものではない。[^provenance][^release]
