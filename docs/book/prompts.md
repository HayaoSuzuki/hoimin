# コピー用プロンプト

コードブロック内をコピーし、ローカルのファイル編集とコマンド実行ができるAIエージェントへ渡す。
エージェントが開く作業ルートは、教材を展開した `shipping-workshop` とする。
実行前に、使う仮想環境のPythonとhoimin 0.14.0の呼び出し方を伝える。
以下の予算を変更したい場合は、実行を始める前に値を決める。

<a id="investigate"></a>
## 初回の調査

調査と報告までを依頼する。
この段階ではテストを編集させない。

```text
このフォルダはミューテーションテストの学習教材です。
SPEC.md、shipping.py、pytest.ini、tests/ を読み、hoimin 0.14.0でテストの検出力を調査してください。
solutions/ は読まず、通常のテスト実行にも含めないでください。
本番コード、仕様、設定、テストは変更せず、調査と報告まで行ってください。

最初に、OS、Python、pytest、hoiminの版、Pythonの実際のパスを確認してください。
テストには教材の仮想環境のPythonを使い、通常コマンドは python -m pytest -q とします。
このコマンドのベースラインが失敗する場合は、変異を調べず原因を報告してください。

対象は shipping.py のみです。テストファイルは変異させないでください。
hoiminの利用ガイドまたは利用可能な配布スキルを確認してください。
planで計画を保存し、verifyで候補を検証してください。
予算は --jobs 1、--max-mutants 5、--total-timeout 1m、
--max-workspace-size 8GiB、--min-free-space 10GiB です。
この依頼全体で検証を開始する候補は最大5件、verify呼び出しは最大2回とします。
メモリその他の上限は既定値から緩めないでください。
元フォルダと一時領域の双方に10GiBを超える空きがあるか確認してください。
別の変異実行が同じルートを使用している場合は実行しないでください。
macOSやcgroupが使えないLinuxでbest-effortの選択が必要なら、その限界を説明し、
私の選択が得られるまで実行を待ってください。自動でフラグを追加しないでください。
資源制限、測定、後始末の失敗では停止し、黙って上限を変更して再試行しないでください。

計画と構造化報告は作業ルート外の専用一時ディレクトリに保存してください。
初回調査後は同じ候補の再検証に使うため、パスを私に知らせて保持してください。
この一時的な保持だけを配布スキルの即時削除手順より優先してください。
教材コピーやworkerの後始末と、私が再検証に使う計画・報告の保持を区別してください。
キャンセル、失敗、終了時は保持した正確なパスと残るファイルを報告し、親や無関係な領域を削除しないでください。

ベースライン、候補の結果、実行の完了状態を、実際の構造化報告から確認してください。
配布版0.14.0の既定はJSONで、生存がある完了実行は終了コード1になります。
現在の開発版はJSONLで、生存があっても完了実行は終了コード0になります。
版とヘルプを確認し、終了コードだけで「検出できた」「生存がない」と判断しないでください。
timeout、error、cancelled、not-runなどの結果を生存や意図した検出に読み替えないでください。

生存した候補から最大3件について、次を日本語で報告してください。
1. 候補ID、変更箇所、元コードと変異後の差分。
2. 実際に確認したベースラインと候補の結果。
3. 元と変異後を区別する入力、および両者の結果。未実行の計算は推論と明記。
4. SPEC.mdのどの規則に反するか、または仕様がその差を許すか。
5. テスト不足、仕様上許容、等価の疑い、未解決の判断と根拠。
6. 追加テストの案。ただし、まだ編集しない。

全体について、実際のコマンド、候補の選択方法、実行件数、未実行と未解決の範囲、
使用した版、計画と報告のパスを示してください。
生存候補がなくても調査範囲だけを報告し、追加実行を繰り返さないでください。
検出割合の最大化を目標にせず、現実装だけを仕様の根拠にしないでください。
```

<a id="improve"></a>
## 選んだ候補の改善

`選択した候補ID` を、初回報告から自分で選んだIDに置き換える。
仕様の根拠に同意できない場合は、先に質問する。

```text
選択した候補ID: ここに候補IDを記入

この候補について、先ほど示したSPEC.mdの根拠に基づくテスト改善を行ってください。
shipping.py、SPEC.md、pytest.ini、requirements.txt、solutions/ は変更しないでください。
tests/ に、小さく読みやすい振る舞いのテストを追加してください。
元の弱いテストを消して結果を作らないでください。
期待値は仕様から導き、実装の出力や式をそのまま正解にしないでください。

通常テストを実行し、初回の同じ計画と同じ候補IDを使ってverifyしてください。
予算と実行条件は初回から変えず、この依頼でのverifyは最大1回とします。
比較のため、本番コード、候補の選択、hoiminの版、テストコマンドを保ってください。
テストは追加のfingerprint対象にしない前提です。
計画が無効になった場合は、黙って作り直して同一条件の比較とせず、理由を報告してください。

次を日本語で報告してください。
- 追加したテストの差分と、その期待値を導く仕様。
- 元コードで通常テストと新しいベースラインが成功した証拠。
- 同じ候補の改善前と改善後の結果。
- どのテストのどのアサーションが、どの値の違いで失敗したか。
- 実行エラー、タイムアウト、収集失敗などではないこと。
- 未検証の範囲、未解決点、残している計画と報告の正確なパス。

候補が生存しても検証を無制限に繰り返さず、原因を説明してください。
資源や後始末の失敗では停止してください。
報告後、計画と報告は私の確認用に保持してください。
```

<a id="refocus"></a>
## 対象を絞った再調査

初回に生存候補がなく、別の小さな調査を始める場合に使う。

```text
初回の候補集合では教材全体の十分性は判断できないため、別の小さな調査を行います。
shipping_fee内の送料無料条件の境界に対象を絞り、実際の演算子と候補をplanで確認してください。
>= 5000 を > 5000 に変える候補があれば、最大1件だけverifyしてください。
存在しなければその事実を報告し、似た別候補を実行したことにしないでください。
その場合は教科書の手作業の実験へ戻れるよう、差を説明してください。
初回の資源方針を保ち、--jobs 1、--max-mutants 1、--total-timeout 1m としてください。
初回の調査結果と混ぜず、新しい計画、実行条件、結果、保存先を報告してください。
テストや本番コードはまだ編集しないでください。
```

<a id="finish"></a>
## 報告の保存と実習の終了

```text
実習を終了します。計画、改善前後の構造化報告、コマンド、版情報、テスト差分、判断根拠を、
教材フォルダの reports/ に保存してください。
reports/を作成してから、まだ変異の追加実行はしないでください。
報告に絶対パスや環境情報が含まれる場合は、共有前に私が確認できるよう知らせてください。
保存先とコピー内容を検証したあと、この実習用に作った一時ディレクトリだけを、
解決済みの正確な絶対パスを確認して削除してください。
親ディレクトリや別の実習のファイルは削除しないでください。
workerや一時領域の削除に失敗した場合は、残った正確なパスと未完了の後始末を報告してください。
```

<a id="project"></a>
## 既存プロジェクトへの適用

空欄を埋め、初回調査用プロンプトの対象指定と通常コマンドを置き換える。

```text
対象ファイルまたは関数:
通常のテストコマンドとPythonのパス:
独立した仕様資料と該当箇所:
特に確かめたい振る舞い:
OSとメモリ制御の方針:
調査全体の候補数、検証回数、時間予算:
触れてよいテスト:
触れないファイル、外部サービスへの制約:
結果と未解決点の保存先:

最初は調査だけを行い、テスト編集は提案を私が確認してから行ってください。
仕様の判断が必要なら、具体的な入力と複数の振る舞いを示して質問してください。
現在の実装の動作だけを理由に期待値を固定しないでください。
```
