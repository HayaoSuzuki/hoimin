# 第1章 高いカバレッジと見逃されるバグ

送料無料の境界を5000円に定めた関数があるとする。
次の実装は、その規則をそのまま表している。

```python
def delivery_fee(subtotal):
    if subtotal >= 5000:
        return 0
    return 500
```

既存のテストは1000円と6000円の注文を確かめている。

```python
def test_paid_delivery():
    assert delivery_fee(1000) == 500


def test_free_delivery():
    assert delivery_fee(6000) == 0
```

どちらの戻り値も実行され、条件分岐も真と偽の両方を通る。
それでも、`>=` を `>` に書き換えた不具合は、この二つのテストを通過する。
1000円と6000円については、二つの条件式が同じ真偽値になるためである。
違いが現れる5000円が選ばれていない。

## 行と分岐が記録するもの

**行カバレッジ**は、測定対象の実行可能な行のうち、テスト実行中に通過した行の割合である。
**分岐カバレッジ**は、分岐から進める先のうち、どこを実行したかを測る。
coverage.pyは、行から次の行への遷移を使って分岐を測定する。
詳しくは[coverage.pyの公式説明](https://coverage.readthedocs.io/en/latest/branch.html)を参照してほしい。

この記録は、未実行のコードを見つけるのに役立つ。
一方、実行した際に戻り値を検査したか、境界値を入力したかは、その割合だけではわからない。
先ほどの例では、真になる入力も偽になる入力もあるが、境界での包含関係は検査できていない。

分岐カバレッジ100%でも、条件の全組み合わせや全経路を通ったとは限らない。
たとえば複数の条件が一つの式に入っている場合、式全体の真と偽だけでは、各条件の働きを切り分けられないことがある。
測定ツールが何を数えるかと、仕様が何を要求するかを別々に確認する必要がある。

## 同じ実行範囲でも異なる検出力

次のテストも、関数を実行する。

```python
def test_delivery_returns_a_fee():
    assert delivery_fee(1000) >= 0
```

500円を返しても、0円や1000円を返しても、このアサーションは成功する。
「金額が負でない」という性質は確認できるが、「この注文では500円」という規則までは確認できない。
行を追加で通過させなくても、期待値を具体化すれば検出できる誤りを増やせる。

ただし、すべてのアサーションを厳しくすればよいわけでもない。
仕様が複数の結果を許す場合、一つの結果だけを正解に固定すると、正当な実装変更を妨げる。
何を受け入れ、何を拒むかを仕様から決める必要がある。

## 境界を検査するテスト

送料無料の境界を確かめるなら、次のテストを追加できる。

```python
def test_free_delivery_at_threshold():
    assert delivery_fee(5000) == 0
```

元の実装では成功し、`>` に変更した実装では500円を返して失敗する。
追加前後でカバレッジの割合が変わらなくても、境界での誤りを検出する力は変わった。
この差を実験するために、次章以降ではコードの小さな変更を利用する。

## 演習1

冒頭の関数とテストを一つの `test_delivery.py` に保存し、`python -m pytest -q test_delivery.py` で実行する。
続いて `>=` を `>` に変え、初期の二つのテストが成功することを確かめる。
境界のテストを追加し、変更した実装で失敗することを確かめたら、実装を元に戻す。
このテスト追加で新しく検査できた仕様を、一文で説明してほしい。
