# 第11章 調査結果の評価

同じ教材でも、エージェントが選ぶ候補や提案するテストは異なる。
ある読者は重量の境界を調べ、別の読者は会員割引を調べるかもしれない。
候補IDや検出件数を解答例に一致させる必要はない。
自分の改善が何を守るか、その効果を確かめられたかで評価する。

## 一つの改善を評価する

調査した候補ごとに、次の四点が揃っているかを点検する。

1. 変異によって変わる振る舞いを、入力と結果で説明できる。
2. その差を拒む理由を、仕様から説明できる。
3. 追加テストが元コードで成功し、同じ変異で意図した理由により失敗する。
4. 未実行、判定不能、未解決を、確認済みの結果と区別している。

たとえば「5000円の注文は無料」という根拠と、500円を返す変異での失敗が揃えば、境界の検出力を改善した証拠になる。
「スコアが上がった」だけでは、どの振る舞いを確かめたかわからない。

## 解答例との比較

自分の実習を終えたら、`solutions/test_shipping_improved.py` を読む。
初期テストと解答例を一緒に実行する場合は次を使う。

```console
python -m pytest -q tests solutions
```

配布した初期状態に解答例を加えると27件が成功する。
自分で追加したテストがあれば件数は増える。
この実行は、解答例が元コードで成功する確認であり、すべての変異を検出したという確認ではない。

解答例には、送料無料と重量の境界、会員と遠隔地の組み合わせ、片方だけ0の入力を含めている。
これは仕様を読むための例であり、唯一の正しいテスト構成でも、完全な検証でもない。
各ケースの期待値を、実装を見ずに仕様から説明できるか試してほしい。

## テストを追加しない判断

生存候補が例外メッセージの変更で、仕様が文言を指定していなければ、その文言を固定するテストは追加しない。
この判断にも、候補の差分と仕様の根拠を残す。
単に面倒だから未対応にした場合や、分析が不足している場合と区別できるためである。

等価の疑いがある候補については、エージェントの断定より根拠を読む。
「多数の入力で成功した」だけなら、試した範囲の記録として受け取り、一般の等価性は保留にする。

## 読みやすさと保守費用

テスト追加によって、失敗時に何を直すべきか理解しやすくなったかも確かめる。
実装と同じ式を複製した期待値、内部変数への依存、既存ケースとの重複は保守を難しくする。
一つのテストが複数の変異を検出してもよい。
変異ごとに似たテストを作る必要はない。

初期のカバレッジは100%だったので、改善後も100%のままになりうる。
報告には、境界値や料金の組み合わせを新しく確かめられるようになったことを示す。

## 演習11

自分の結果を、候補、判断、仕様根拠、変更したテスト、改善前後の証拠、残る疑問の六項目で一枚にまとめる。
テストを追加しなかった候補があれば、その理由も含めてほしい。
