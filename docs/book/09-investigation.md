# 第9章 AIエージェントへの調査依頼

エージェントに「生存した変異を全部なくして」と依頼すると、仕様が許す変更まで拒むテストを作る余地がある。
依頼の対象は、少数の変異についての調査と、その根拠の報告に絞る。
最初の実行ではテストも実装も編集させず、読者が判断するための材料を受け取る。

## 作業ルートと実行条件

エージェントが開いているフォルダを `shipping-workshop` に合わせる。
端末で有効にした仮想環境が、エージェントの実行環境に引き継がれるとは限らない。
仮想環境のPythonのパス、hoiminの呼び出し方、OSを最初に伝える。

[調査用プロンプト](prompts.md#investigate)をコピーして依頼する。
プロンプトは、対象を `shipping.py` に限定し、通常テスト、計画作成、最大5候補の検証という順序を指定している。
生存候補のうち、読者に報告するのは最大3件とする。
残りを調査済みと扱わないよう、実行範囲も報告させる。

## エージェントが行う実験

hoiminの `plan` は変異候補を発見し、JSONの計画を作る。
この段階ではテストを実行しない。
`verify` は保存した計画から選んだ候補を検証し、その都度、新しいベースラインを実行する。
実行結果は構造化報告として保存される。
本書で固定した配布版0.14.0は既定で一つのJSON文書を返し、現在の開発版はJSONLのイベント列を返す。
エージェントは実際の版とヘルプを確認して読み取る。

読者がこれらを手入力する必要はないが、何を依頼したかを把握するため、形を示す。
次はWindowsまたは利用可能なcgroupがあるLinux向けの概念例であり、`PLAN_PATH` と `BEFORE_PATH` はエージェントが作る一時領域内のパスに置き換える。

```console
hoimin plan --root . --file shipping.py --jobs 1 --max-mutants 5 --total-timeout 1m --max-workspace-size 8GiB --min-free-space 10GiB -- python -m pytest -q
```

標準出力を `PLAN_PATH` に保存し、計画から選んだ候補IDで検証する。

```console
hoimin verify PLAN_PATH --candidate CANDIDATE_ID
```

`CANDIDATE_ID` は実際の計画にあるIDに置き換える。
標準出力を `BEFORE_PATH` に保存する。
macOSなどでは、事前に人間が選んだメモリ方針を `plan` に反映する必要がある。
PowerShellではUTF-8で保存するためPowerShell 7を使う。
実習では、コマンド全文と実際のパスをエージェントの報告に残す。

## 受け取る報告

「境界値のテストが不足しています」だけでは、どの変更に対する説明かがわからない。
候補ごとに、少なくとも次の証拠を求める。

| 項目 | 確認する内容 |
| --- | --- |
| 候補IDと差分 | 実際に検証した変更か |
| 実行結果 | ベースライン成功と、その候補の生存が確認できるか |
| 区別する入力 | 元と変異後でどんな違いが現れるか |
| 仕様の根拠 | その違いを拒む要求がどこにあるか |
| 判断 | テスト不足、仕様上許容、等価の疑い、未解決のどれか |

表は報告の形式であって、内容の正しさを保証しない。
候補IDが計画にあるか、実行結果が不完全ではないかの確認はエージェントに依頼し、読者は仕様と差分を照合する。

## 結果が期待と違う場合

生存候補がなければ、検証した少数の候補がすべて既存テストで検出された可能性がある。
「この教材に不足がない」と結論しない。
選んだ範囲を報告してもらい、[再調査用プロンプト](prompts.md#refocus)で送料無料の境界などへ対象を絞る。
予算を使い切った場合は、その回の実習を終了し、次の調査を別の予算として計画する。

エラー、タイムアウト、資源停止、後始末の失敗なら、生存候補として扱わない。
報告を保存して原因を調べる。
エージェントが結果を説明できない場合も、未検証として残せる。

## 演習9

生存候補を一つ選び、エージェントの判断を読む前に、自分で区別する入力と仕様の根拠を書いてみる。
候補が得られなかった場合は、調査範囲と判定できなかった事項を記録する。
