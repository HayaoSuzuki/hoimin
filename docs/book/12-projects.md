# 第12章 既存プロジェクトへの適用

教材には明文化した短い仕様があった。
既存プロジェクトでは、仕様が利用者向け文書、過去の不具合報告、呼び出し側の前提などへ分散している。
変異の実行範囲を広げる前に、何を根拠にテストを改善できるかを調べる。

## 最初の対象

最初は、通常のテストが安定して成功する小さな関数やモジュールを選ぶ。
入力と観測対象が明確で、実行時間が短く、期待結果の根拠を探せる対象が扱いやすい。
変更したばかりの料金判定、日付の境界、権限条件など、見逃すと困る振る舞いから選んでもよい。

システム全体へ一度に適用すると、外部サービス、データ準備、実行時間、結果の解釈が混ざる。
小さな範囲で一つの改善を完了させ、その費用を見て次の対象を決める。
hoiminはローカルでのテスト改善を目的とし、利用者のCIにスコア閾値を設定する運用を前提にしていない。

## 調査前の合意

[既存プロジェクト用プロンプト](prompts.md#project)に、対象、通常テストのコマンド、仕様資料、予算を記入する。
テストが使う外部サービスや認証、作成するデータも先に把握する。
元コードのテストが失敗する状態や、失敗理由が不安定な状態では、変異の評価を進めない。

仕様が曖昧なら、エージェントに現在の実装を正解として固定させない。
「5000円ちょうどを含むか」「同時に複数条件を満たす場合はどちらを優先するか」のように、具体的な入力と選択肢を伴う質問へ整理する。
決定した内容を仕様やテストの根拠として残す。

## テスト層を選ぶ

単体テストで変異を検出できれば、短時間で局所的な期待を確認できる。
しかし、呼び出し側との契約やデータ変換を含む問題は、結合テストでしか観測できない場合がある。
同じ候補を調べる場合も、どのテストコマンドを使ったかを記録する。
コマンドを変えた結果を、テスト追加だけの効果として比較しない。

プロパティベーステストを利用する場合は、生成する入力の領域と、検査する性質を検討する。
入力を大量に生成しても、弱いオラクルでは誤りを受け入れることがある。
乱数や探索条件によって結果が変わる場合は、再現に必要な情報も残す。

## 小さな調査の記録

調査を終えたら、テスト差分と一緒に次の記録を残す。

```text
対象と元コードの版:
仕様の根拠:
hoiminの版、OS、Python、テストコマンド:
候補の選択方法と検証したID:
実行予算と実際に完了した範囲:
追加したテストと改善前後の証拠:
追加しなかった理由:
未解決点と次に必要な判断:
```

すべての生存候補に結論を出す必要はない。
未調査と、調べたうえで追加不要と判断したものを区別すれば、次の担当者が続きを判断できる。

## 調査費用の振り返り

実行に使った時間に加え、仕様確認とレビューに要した時間も数える。
似た境界の不足が繰り返し見つかるなら、テスト設計時のチェック項目へ取り込める。
反対に、仕様根拠が得られず改善につながらない候補が多ければ、対象や演算子、調査範囲を見直す。

教材では、100%という同じ割合の内側で、検査する振る舞いを増やした。
実務でも、数値を変えた量に加え、どの要求を守れるようになったかを成果として説明できる。
