# 第6章 スコアと調査範囲

100件のうち90件を検出したという結果と、10件のうち9件を検出したという結果は、どちらも90%になる。
それでも、対象の関数、変更の種類、未実行の範囲が違えば、同じテスト品質を意味しない。

## 分母の定義

**ミューテーションスコア**は、対象とした変異のうちテストが検出した割合を表す指標である。
ただし、等価と判断したものや判定不能なものをどう扱うかによって定義が変わる。
本書で説明用に割合を計算するときは、確定結果の `killed` と `survived` だけを用い、次の式とする。

```text
検出割合 = killed / (killed + survived)
```

分母が0なら、割合は定義できない。
タイムアウト、エラー、中止、未実行を分母から除いた場合も、その件数は別に示す。
たとえば10件中、検出1、生存1、タイムアウト8なら、確定した2件の割合は50%だが、大半の結果は不明である。
50%という数値だけを報告すると、その不明範囲が消えてしまう。

## 対象による偏り

境界の比較だけを変える実験と、戻り値や定数まで変える実験では、テストに投げかける問いが異なる。
ファイル、関数、変異演算子、候補の選択方法が変われば、数値の意味も変わる。
少数の候補を順位に従って選んだ結果を、プログラム全体から無作為に選んだ標本として扱うこともできない。

調査結果には、どこを、どの変更で、どのテストコマンドを使って調べたかを添える。
調査できなかった範囲を明示すれば、小さい実験でも次の判断に利用できる。

## 改善前後の比較

テスト追加の効果を確かめるには、同じ元コードと同じ候補を、追加前後のテストで検証する。
元コード自体を変えたり、候補の選択を変えたりすると、違いの原因を切り分けにくい。
hoiminの実習では保存した計画と候補IDを使い、同じ候補を再検証する。

たとえば、境界の候補が追加前には生存し、追加後には期待したアサーションによって検出されたなら、そのテストが当該変更を検出する証拠になる。
これによって、未知のバグすべてを検出できるとまではいえない。
改善した範囲を、実験した変更と仕様に結びつけて記録する。

## 調査の終了条件

生存変異をすべてなくすことを終了条件にすると、等価な変更や仕様が許す変更まで拒むテストを作りやすい。
実務では、対象の重要度と使える時間から調査範囲を決める。
次のいずれかに達したら、結果と未解決点を報告して一区切りにできる。

- 合意した仕様や対象の調査を終えた。
- 合意した候補数または時間の予算を使い切った。
- 残った候補について、追加すべきテストの根拠が得られなかった。

資源制限や後始末の失敗による停止は、調査完了とは区別する。
制限を黙って緩めて再試行せず、原因を調べる。

## 演習6

検出8、生存2、タイムアウト5、未実行5という報告について、本書の式による割合を求める。
その結果を「調査対象の80%を検証できた」と説明してよいか考える。
さらに、この報告だけでは判断できないことを二つ挙げてほしい。
