# 第2章 入力と期待結果

5000円を入力に選んでも、その結果を検査しなければ境界の誤りは検出できない。
テストには、違いを生じさせる入力と、その違いを判定する期待結果の両方が必要である。

## 何を正解とするか

**テストオラクル**とは、観測した結果が正しいかを判断する基準や仕組みである。
送料の例なら、料金規則から求めた「5000円の注文では送料0円」が判定の根拠になる。
期待値の数値だけでなく、その数値がどこから来たかを説明できる必要がある。

次のテストは、関数の計算を期待値側にも書いている。

```python
expected = 0 if subtotal >= 5000 else 500
assert delivery_fee(subtotal) == expected
```

この式は短いが、実装と同じ誤解を両方へ写す余地がある。
5000円を含むかどうかを誤読し、実装と期待値を両方 `>` にすると、テストはその誤解を検出できない。
仕様の表から選んだ具体例と期待値を使えば、少なくとも実装の式をそのまま複製せずに済む。

仕様の表自体が誤っている可能性は残る。
ミューテーションテストは、事業上の要求を自動的に確定する手法ではない。
仕様とテストの食い違いを見つけたら、要求を決められる人に確認する。

## 入力の分類と境界

送料無料の規則なら、入力を「5000円未満」と「5000円以上」に分類できる。
その各領域から代表値を選ぶだけでは、包含関係の誤りが残りうる。
境界の直前、境界そのもの、直後を選ぶと、その違いを確かめやすい。

| 商品合計額 | 期待する送料 | 確かめること |
| --- | --- | --- |
| 4999円 | 500円 | 境界の直前では有料 |
| 5000円 | 0円 | 境界を無料に含める |
| 5001円 | 0円 | 境界の直後でも無料 |

整数の金額なので、直前と直後は1円差で表せる。
日付や浮動小数点数を扱う場合は、型と業務上の単位に応じて「隣」を定める必要がある。

## 具体例と性質

「送料が負でない」は、多くの入力に共通する性質である。
一方、「会員で遠隔地なら700円」は、特定の条件における具体的な期待結果である。
両者は補い合う。
具体例だけでは広い入力範囲を調べにくく、弱い性質だけでは正しい金額を絞り込めない。

AIエージェントが性質を提案した場合も、その性質が仕様から導けるかを確認する。
「購入額を増やしても送料は上がらない」は、ほかの入力を固定し、比較する両方の注文が空注文でない範囲なら検討できる。
重量や配送先まで同時に変えた二つの注文には、そのまま適用できない。
また、重量0gで購入額を0円から1円にすると、空注文の例外から通常料金へ切り替わるため、送料は0円から500円に増える。

## 実装の観測と要求の区別

既存の実装から取得した出力を保存するテストは、振る舞いの変更を検知するのに使える。
しかし、現在の出力が要求を満たすという根拠は、別に必要である。
そのまま期待値に採用すると、既存のバグを守るテストにもなる。

テスト案を読むときは、入力、期待結果、根拠の三つを並べるとよい。
どれかが欠けていれば、成功するテストが増えても、守るべき振る舞いは明確にならない。
