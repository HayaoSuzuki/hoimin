# 第10章 テスト改善と再検証

生存した変更に仕様違反があると判断できたら、その振る舞いを守るテストを追加する。
ここでは、送料無料の条件を `>= 5000` から `> 5000` に変えた候補を例にする。
実際の候補が別の変更なら、同じ判断の順序をその変更に適用する。

## 仕様から期待値を導く

商品合計額5000円、重量1000g、非会員、通常地域を選ぶ。
仕様によれば5000円ちょうどは無料であり、遠隔地加算もないので、期待値は0円になる。
変異後の条件は偽になり、500円を返す。

この計算を説明できたら、エージェントへ選んだ候補IDを伝え、[改善用プロンプト](prompts.md#improve)でテスト追加と再検証を依頼する。
典型的なテストは次のようになる。

```python
def test_free_delivery_at_threshold():
    fee = shipping_fee(5000, 1000, member=False, remote=False)

    assert fee == 0
```

金額0円の根拠は仕様にある。
現在の実装を呼び、その戻り値をコピーして期待値にしたのではない。
また、関数内部の変数や条件式の構造も固定していない。

## 同じ候補での再検証

改善前の計画、候補ID、元コード、テストコマンドを保ち、追加後のテストで同じ候補を検証する。
hoiminは各検証でベースラインを取り直すため、元コードで新しいテストが成功することも確認される。
通常テストも別に実行し、ほかのテストが壊れていないか確認する。

テストだけを変更し、そのファイルを追加のfingerprint対象にしていなければ、同じ計画を再利用できる。
元コードや、計画に記録した設定、追加のfingerprint対象を変えた場合は計画を作り直す必要がある。
その場合、元の計画による単純な比較として報告しない。

候補の選択を増減した場合も、同じ集合を比較したことにはならない。
最初は一つの候補について、改善前後の証拠を揃える方が判断しやすい。

## 失敗理由の確認

望ましい報告では、元コードでは成功し、対象の変異では `assert fee == 0` が実際の500円を拒んだことがわかる。
インポート失敗、構文エラー、タイムアウトによる失敗なら、この境界テストの効果を確かめたことにはならない。
終了コードや `killed` のラベルだけで済ませず、失敗したテストとその理由を示してもらう。

逆に、追加後も生存した場合は、入力の選び方、期待値、収集対象、実際の変異を調べる。
新しいテストがテストコマンドに収集されていないだけかもしれない。
失敗しないからといって、元コードを変えて合わせない。

## 複数のケースへの拡張

境界の直前と直後も、仕様に沿う期待値で追加できる。

```python
import pytest


@pytest.mark.parametrize("subtotal, expected", [(4999, 500), (5000, 0), (5001, 0)])
def test_free_delivery_boundary(subtotal, expected):
    assert shipping_fee(subtotal, 1000, member=False, remote=False) == expected
```

これらは同じ種類の境界を説明するまとまりである。
関係のない仕様を巨大な表に詰め込むより、失敗時に何の要求が壊れたか読める単位で整理する。
表の使い方は[pytestのパラメータ化の説明](https://docs.pytest.org/en/stable/how-to/parametrize.html)も参照できる。

## 演習10

選んだ候補について、改善前の生存、追加テストの仕様上の根拠、改善後の元コード成功、同じ変異での意図した失敗を記録する。
比較できなかった条件があれば、何を変えたためかを併記してほしい。
