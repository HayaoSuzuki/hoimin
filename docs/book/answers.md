# 演習の解答例

ここに示すのは、仕様と検証条件から判断する例である。
AIエージェントの文章、候補ID、検出件数を一致させる必要はない。

<a id="exercise-1"></a>
## 演習1 境界の検出

初期テストは、1000円では500円、6000円では0円を期待する。
`>= 5000` でも `> 5000` でも、この二つの入力の結果は一致する。
5000円の入力では、元コードは0円、変異後は500円を返す。
追加したテストは「送料無料の対象に5000円ちょうどを含む」という要求を確かめる。

<a id="exercise-2"></a>
## 演習2 重量の境界

1999gと2000gでは加算0円、2001gでは加算300円となる。
`>= 2000` に変えた誤りは2000gで300円を加算するが、非負という検査には通る。
加算額を301円に変えた誤りも、その検査だけでは拒めない。

<a id="exercise-3"></a>
## 演習3 入力による差

`5 + 0` も `5 - 0` も5なので、`add(5, 0) == 5` では検出できない。
`0 + 5` は5、`0 - 5` は-5なので、`add(0, 5) == 5` は検出できる。
引数が同じ型であっても、誤りに対する役割は同じとは限らない。

<a id="exercise-4"></a>
## 演習4 伝播しない差

3000gでは重量加算に到達し、加算後は800円と801円になる。
到達と状態の差は成立するが、6000円の無料化で両方とも0円に上書きされるため、戻り値まで差が伝播しない。
商品合計額1000円、重量3000gで800円を期待すれば、差が残り、801円を返す変異を検出できる。

<a id="exercise-5"></a>
## 演習5 生存理由

1. 整数を入力領域とするなら等価である。`>= 5000` を満たす最小の整数は5000で、`> 4999` を満たす最小の整数も5000になる。
2. 観測可能な文字列の差はあるが、仕様が許す変更である。例外型だけが契約なら、その文言を拒むテストの根拠はない。
3. 試した100入力については差がなかったといえる。入力領域全体を覆った証拠や別の論証がなければ、等価性は未確定である。

<a id="exercise-6"></a>
## 演習6 分母と不明範囲

確定した結果については `8 / (8 + 2) = 0.8`、すなわち80%となる。
20件のうち確定結果が得られたのは10件であり、「調査対象の80%を検証できた」という説明は、この式の意味と異なる。
対象の選び方、変異の種類、タイムアウトの原因、仕様に反する変更がいくつあるかなどは、この件数だけでは判断できない。

<a id="exercise-7"></a>
## 演習7 実行環境

`python --version`、`python -m pytest --version`、`python -m coverage --version`、`hoimin --version` で版を確認する。
Pythonのパスは `python -c "import sys; print(sys.executable)"` で確認できる。
エージェントにも同じ確認を依頼し、別のPythonや古いhoiminを呼んでいないかを照合する。
hoiminをuvxで呼ぶ場合は、その呼び出し全体も記録する。

<a id="exercise-8"></a>
## 演習8 100%でも見逃す条件

初期テストでは、通常注文の合計額に1000円と6000円を使っている。
5000円ちょうどを入力していないため、`>=` と `>` で条件の真偽値が変わらない。
さらに通常料金は非負かどうかしか検査しないため、仮に5000円のケースを追加しても、`fee >= 0` だけなら0円と500円を区別できない。
入力と期待結果の両方を改善する必要がある。

<a id="exercise-9"></a>
## 演習9 調査の根拠

送料無料境界の候補なら、次のように整理できる。

| 項目 | 記載例 |
| --- | --- |
| 変更 | `subtotal >= 5000` から `subtotal > 5000` |
| 入力 | 合計5000円、1000g、非会員、通常地域 |
| 元と変異後 | 0円と500円 |
| 仕様 | 5000円以上は通常送料を無料にする |
| 判断 | 境界の仕様違反をテストが見逃す |

この候補が実際に実行されていなければ、実行結果としては書かない。
推論例と、計画および構造化報告で確認した結果を分ける。

<a id="exercise-10"></a>
## 演習10 改善前後の証拠

境界のテストを追加したら、元コードでは0円で成功し、同じ候補では500円でアサーションが失敗することを確認する。
候補IDが一致するだけでなく、元コード、版、コマンド、計画も同じかを確認する。
テスト収集の失敗や、計画の入力不一致で実行されなかった場合は、テスト改善の効果を確認できたことにはならない。

解答例の `solutions/test_shipping_improved.py` には、追加テストの一例を用意した。
全候補を検出するための完成形ではなく、複数の仕様を具体値で検査するための例である。

<a id="exercise-11"></a>
## 演習11 報告の評価

次のような記録なら、判断と実行の証拠を追える。
山括弧などの仮のIDを実際に検証したIDとして提出しない。

```text
候補: 実際の計画に記録されたIDと、送料無料条件の差分
判断: 5000円ちょうどを無料に含める要求へのテスト不足
仕様根拠: SPEC.mdの送料無料条件
変更: tests/ に境界値で0円を期待するテストを追加
証拠: 初回生存、追加後の元成功、同候補で期待0円/実際500円の失敗
残る疑問: 未選択の変異、重量や会員の組み合わせはこの調査では未確認
```

仕様が許すメッセージ変更なら、文言を固定しなかった理由を記録する。
等価性の判断が未確定なら、そのまま未解決として提出してよい。

<a id="exercise-12"></a>
## 演習12 実務の調査計画

たとえば、割引クーポンの有効期限判定を対象にし、日付の境界を調べる計画が考えられる。
仕様にタイムゾーンや期限当日を含むかの記述がなければ、先にそれを質問する。
質問には「期限日当日の23時に、この地域から利用する場合」のような具体例を添える。
現在のコードが受け入れるという理由だけでは、期待する動作は確定しない。

仕様、通常テスト、予算、対象、保存先が決まったら、[既存プロジェクト用プロンプト](prompts.md#project)を使う。
