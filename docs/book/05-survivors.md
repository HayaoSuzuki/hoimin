# 第5章 生存理由と等価性

生存した変異を見つけたら、まず元コードと変異後で、仕様上区別すべき振る舞いがあるかを考える。
差があり、既存のテストが見逃しているなら、テストを改善する手がかりになる。
一方、どんな有効入力でも同じ振る舞いになる変更を、テストで区別することはできない。

## テスト不足と仕様上許される差

「5000円以上で無料」を `> 5000` に変えた場合、5000円の入力で仕様違反が生じる。
境界のテストがなく生存したなら、追加すべきテストを仕様から導ける。

これに対し、例外メッセージを別の文言に変えても、仕様が例外型しか定めていなければ、変更後も仕様を満たしうる。
この場合、観測可能な文字列は異なるため、単に等価とは呼べない。
テストで区別することはできるが、その区別を要求する根拠がないのである。

仕様の不足もありうる。
利用者向けに表示する文言なら、メッセージが契約に含まれるか確認する必要がある。
実装に書かれているという理由だけで、現在の文言を固定しない。

## 等価ミュータント

指定した入力領域と観測対象について、元コードと同じ振る舞いになるものを**等価ミュータント**と呼ぶ。
たとえば、整数の `subtotal` に対して `subtotal >= 5000` と `subtotal > 4999` は同じ真偽値になる。
この説明は整数という前提に依存する。
小数を許せば、4999.5で二つの式は異なる。

送料計算には `max(0, fee - 200)` という式がある。
到達時点の `fee` が500円または800円に限られるなら、下限の0を除いても結果は変わらない。
これはその地点に到達する状態の制約から説明できる。
そのような変異が実際に生成されるかどうかは、ツールと演算子による。

有限個の入力で差が見つからないことは、すべての有効入力での等価性の証明にはならない。
AIエージェントが「等価」と報告したときも、入力領域、観測対象、根拠を確認する。
根拠が不足する場合は「等価の疑い」または「未解決」として残す。

## 実行結果と調査判断

実行結果としての生存と、その理由についての判断は別に記録する。
次の表の右側は、テストを動かしただけでは自動的に決まらない。

| 実行結果 | 調査後にありうる判断 | 次の行動 |
| --- | --- | --- |
| 生存 | 仕様違反を見逃す | 仕様に基づくテストを追加する |
| 生存 | 差はあるが仕様が許す | その差を拒むテストは追加しない |
| 生存 | 等価の根拠がある | 根拠と適用範囲を記録する |
| 生存 | 仕様または分析が不足する | 質問や未解決点を残す |
| エラー、タイムアウトなど | 判定不能 | 実行条件を調べる |

等価の疑いがある変異を、都合のよいスコアにするため機械的に除外すると、調査の不確実性が隠れる。
観測結果を保存し、判断の理由をその隣に残す方が、あとから見直しやすい。

## 演習5

次の三つを分類する。
分類だけでなく、仕様と入力領域を根拠にして説明してほしい。

1. 整数入力に対し、`subtotal >= 5000` を `subtotal > 4999` に変える。
2. 例外型だけが指定された関数で、例外メッセージを変える。
3. 100個の入力で同じ結果だったという理由で、エージェントが等価と報告する。
