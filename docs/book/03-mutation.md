# 第3章 ミューテーションテストの原理

境界のテストを加えた効果は、`>=` を `>` に変える実験で確かめられた。
このように、プログラムへ小さな変更を加え、テストが検出できるか調べるのがミューテーションテストである。

## 元コードとミュータント

変更前のプログラムを元コード、変更を加えたプログラムを**ミュータント**と呼ぶ。
変更規則は**変異演算子**と呼ぶ。
比較演算子の置換、算術演算子の置換、定数や戻り値の変更などが例に挙がる。

```python
# 元コード
return left + right

# ミュータント
return left - right
```

これは実際のバグ分布をそのまま再現したものではない。
選んだ変更に対して、テストが反応するかを調べる実験である。
生成しない種類の誤りについて、この実験だけから検出力は判断できない。

## 検出と生存

元コードで成功するテストが、ミュータントでは変更の影響によって失敗した場合、その変異を**検出した**と考える。
ツールでは `killed` と表記されることがある。
実行を完了してもテストが成功する場合は**生存**と呼び、`survived` と表記される。

足し算に対する `add(0, 0) == 0` というテストは、引き算でも成功する。
一方、`add(2, 3) == 5` なら、引き算が返す `-1` を拒める。
同じ演算子の変更でも、入力によって検出できるかが変わる。

実行中のタイムアウト、依存関係の不足、テスト収集の失敗は、これらとは分けて扱う。
ツールが `killed` と分類しても、その原因が要求違反を表すアサーションなのか、変更による別の失敗なのかを確認する。
テスト改善の証拠として使うなら、失敗した理由が必要である。

## ベースライン

ミュータントを試す前に、同じ条件で元コードのテストが成功することを確認する。
この確認を**ベースライン**と呼ぶ。
元コードでも失敗するテストでは、その失敗を変異によるものと判断できない。

たまたま成功しただけの不安定なテストにも注意が必要である。
時刻、乱数、外部サービス、実行順序が原因で結果が揺れるなら、変異の効果と分離しにくい。
通常のテストを安定させてから変異を調べる。

## 手作業からツールへ

最初は、一箇所を変更してテストを動かすだけで原理を学べる。
対象が増えると、変異の生成、元コードとの分離、実行、結果の記録に手間がかかる。
hoiminはこの実験をAIエージェントから進めるために使う。
hoimin自体が仕様を理解したり、LLMとしてテスト案を生成したりするわけではない。

なお、ミュータントを検出するためだけに本番コードを書き換えると、調べる対象が変わってしまう。
実際の不具合を見つけた場合は、再現テストと修正を別の作業として記録する。
