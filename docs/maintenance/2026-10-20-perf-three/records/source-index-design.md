## Recommendation

Delay **only validation location-index materialization** inside `CandidateValidationContext`; keep eager raw/decoded length validation, decoding classification, and raw-source hash. The context already binds immutable raw bytes and decoded facts in private fields. A private lazy cell can derive its index exclusively from those fields without introducing a public source/index pair. Existing CLI plan/run analysis returns and drops its local index before converting candidates, so delayed validation eliminates concurrent duplicate Unicode indexes without changing analyzer APIs. The successful Unicode file still builds two indexes sequentially: do not call this a build-count reduction or predict a time speedup.

Use this design if issue acceptance is explicitly either sharing OR no simultaneous duplication, as the parent task states. If acceptance requires exactly one build per successfully analyzed source, use the shared owning-source alternative below instead. Do not add both implementations or a compatibility path.

A plain CLI move of `CandidateValidationContext::new` after analysis is inferior: it needs another decoding owner during analysis, can duplicate Latin-1 text/mapping, and changes error ordering unless construction is split. Central lazy materialization solves the actual retention problem with the existing source owner.

## Alternatives and lifetime tradeoffs

| Design | Same-source simultaneous Unicode index | Builds for successful UTF-8 file | Pairing / complexity |
| --- | --- | --- | --- |
| Current eager context + analyzer | 2 | 2 | Context safe internally; analyzer independently builds |
| Lazy validation location index | 1 in existing CLI flow | 2 sequential | Existing private source owner; small localized change |
| Move full context construction after analyzer | 1 if carefully scoped | 2 | Risks second decode and altered errors; avoid |
| Pass source and unrelated `&PythonSourceIndex` to analyzer | 1 | 1 | Reject: public contract permits wrong pairing |
| Source-bound shared immutable owner | 1 | 1 | Safe but broader ownership/API migration |

For lazy materialization, prefer `OnceLock` over `RefCell`/`OnceCell` if retaining current production Send/Sync properties matters. Existing `PythonSourceIndex` test-only Cells make test builds special; do not infer production thread traits solely from tests. Initialize lazily only at location validation, after all earlier errors. Both raw and successfully decoded lengths must still be checked in `new`; source invalidity stays stored so original-mismatch precedence remains unchanged. Make the private initialization operation derive solely from `self.source` and `self.decoded`; do not expose a setter or initializer accepting another source. A checked private constructor can make initialization infallible after prechecked lengths, with a documented invariant. Alternatively cache a Result and clone its error; avoid silently moving SourceTooLarge detection to the first candidate. Keep the exact checked-length logic in one private helper rather than duplicating it across branches.

Lazy storage guarantees an index belongs to its context, but does not type-enforce that arbitrary external callers never validate before separately analyzing the text. The concrete CLI ordering plus a heap regression gate supplies that guarantee for the affected paths. If broader globally enforced reuse is required, choose sharing.

For actual sharing, use a source-owning abstraction with private text and index fields, e.g. an indexed UTF-8 source containing `Cow<'source,str>` and a lazy index, nested in DecodedPythonSource. The analyzer receives a reference to this **single source-bound value**, derives its text and index internally, and returns owned candidates. Candidate validation borrows that same inner index for UTF-8/ASCII and keeps the existing raw Latin-1 line starts. Standalone analyzer callers construct the same source type from a string. Migrate call sites directly; no legacy wrappers solely for compatibility. Do not make a self-referential `DecodedPythonSource { owned String, index borrowing that String }`; moving the String owner invalidates an ordinary Rust self-reference design. An index containing only offsets avoids that issue. Arc alone around an existing index neither binds it to a source nor prevents an independent second build. A private-field borrowed source/index view is safe only when its constructor is available exclusively from the bound owner; an unrestricted `(text,index)` constructor recreates the bug class.

## Five distinct design review passes

### Pass 1 — allocation and peak lifetime

Observed overlap exists for the whole analyzer call, including parsed AST/facts and token collection. With lazy context, analyzer-local index drops before validation initialization. No analyzer output retains references to LineIndex: candidates and diagnostics are owned. Successful validation reuses its once-created context index for later candidates. Failure/invalid syntax/no candidates avoids that second build entirely. A `max_candidates=0` analyzer can still build its own index; do not claim zero analysis work. Index memory is distinct from payload budget, which charges logical candidate payload rather than every source allocation.

Decision: lazy context is enough for the stated duplicate-live-index acceptance; build-count tests must expect two sequential builds, not one. Heap must be tested across context construction + analysis + conversion, not only during standalone context creation.

### Pass 2 — ownership and API safety

No changed public parameter list is necessary for lazy design. The existing immutable raw borrow prevents mutation while context facts are live, and the context owns Latin-1 decoding. Private lazy initialization cannot mismatch source. Sharing would need an actual source-bound owner or restricted view, not independent `&str,&Index` args. It introduces changes across core/python/CLI/fuzz/tests and must earn that cost through a one-build requirement or measured CPU benefit.

Decision: reject public separate index argument, self-references, global content caches, and source clone/Arc solutions that retain duplicate payload.

### Pass 3 — encoding, metadata, and writeback

UTF-8 and BOM offsets refer to unchanged original bytes; BOM is discounted only at first-line column. Unicode scalar count, including combining sequences and emoji, is not display width. LF, CRLF, lone CR must retain their current physical-line semantics. Latin-1 has different raw and decoded byte offsets; its validation line starts deliberately use raw bytes, while analysis indexes decoded UTF-8. Existing expanded-coordinate vector must remain available through conversion. Hash stays raw source hash, stable ID remains based on existing descriptor inputs, and replacement is re-encoded during writeback.

Decision: preserve Latin1 branch; do not replace it blindly with shared Unicode offsets. Functional matrix needs raw-span/column/ID/hash/writeback checks, not just candidate count.

### Pass 4 — failures, cancellation, and bounded resources

Constructor raw+decoded limits currently precede candidate checks and analyzer errors. Preserve this. Invalid source is retained by context because strict validation prioritizes original mismatch over encoding failure. CLI source_validation explicitly promotes decoding failure early; preserve both entry-point contracts. Cancellation checks surround reading/analysis/conversion; index builds themselves are currently synchronous and uninterruptible. Moving one build to conversion shifts work after existing cancellation check but need not introduce new unchecked loops; document and measure this rather than advertising stronger cancellation. Metadata and scratch budget admission precede strict validation in mutation_candidate, so lazy indexing should not happen before these admissions. Zero-candidate and rejected-metadata cases should never materialize validation locations.

Decision: do not defer hashing/decoding or reorder scratch reservations. Reuse payload exact-limit and cancellation tests; add a focused early-error/index-not-built case.

### Pass 5 — evidence and small-input performance

Historical 4/8/16 MiB combined index peaks versus 2/4/8 MiB single-index peaks are issue evidence only, not measurements of this checkout. A sparse/ASCII file already has zero Unicode correction entries; a OnceLock read adds a small validation cost. Need actual small-ASCII timing and aggregate CLI measurements before declaring no regression. Large-constant heap/time wins do not change O(N) construction complexity. Sharing can reduce scans but carries migration cost; lazy design must explicitly report unchanged two-build count for successful candidates.

Decision: deterministic retention/materialization gates plus fresh paired release measurements. Do not fail ordinary tests on wall-time ratios. Full CLI RSS is not heap, nor does a public analyzer-only allocator test establish full CLI memory.

## Settled choice and fallibility/counter details (parent clarification)

Parent confirmed acceptance is reduced simultaneous retention, not one build. Choose **lazy context-local index**; no user permission or new analyzer API is necessary.

For minimal implementation risk, `OnceLock<Result<CandidateSourceIndex, CandidateValidationError>>` is defensible: keep eager raw/decoded length checks in `new`, then use `get_or_init(|| CandidateSourceIndex::new(self.source, decoded))` at the existing location-check site and propagate/clone the cached error. This reuses the fallible constructor without introducing an `expect`/panic or changing error precedence. The Result state is defensive because successful eager checks make SourceTooLarge unreachable for immutable inputs. Its small fixed-size overhead should be measured in the ASCII control. An infallible private factory is reasonable only if its checked preconditions are structurally enforced and documented; avoid a new panic merely to save a Result discriminant. Do not use unstable get_or_try_init without confirming the project toolchain. OnceLock uses interior initialization but does not permit source mutation; production Send/Sync must be preserved. Add a compile-time trait assertion for `CandidateValidationContext<'_>` in an integration test, where the core dependency is built without its internal cfg(test) Cell lookup instrumentation. A core unit-test Sync assertion could falsely fail because existing lookup_stats Cells already change the test-only type.

Expected CPU tradeoff: baseline and lazy successful Unicode paths both scan/build twice and hash/decode once; lazy may save cache initialization for early rejection, syntax error, no candidates, and payload admission failure. It adds a small once-cell access per validated candidate. Sharing would save one construction scan/allocation but requires a source-bound owning abstraction and migration. Do not promise equal or better whole-time solely from two equal scan counts: cache locality, allocator reuse, and live-memory pressure change observed cost. Measure both dense Unicode and small ASCII independently, with fixed candidate count and repeated samples.

For deterministic evidence, a core-private test counter can count CandidateSourceIndex materialization (0 after new, 1 after first eligible validation, unchanged after repeat). A core-private PythonSourceIndex constructor counter can establish independent construction behavior in its own unit tests. `cfg(test)` counters in hoimin-core are NOT available automatically to a hoimin-cli integration test: dependencies compile without that cfg. Do not add public instrumentation access just to bridge this. Use the actual CLI/discovery allocator integration gate to enforce no simultaneous duplicate peak. It must execute source_validation -> actual analyzer -> actual conversion through `discover_targets` or `run_with_writers`, assert one boolean candidate and stable output, and have a slope/absolute bound that the old eager path demonstrably violates. Given fixed-candidate/two-line fixtures, comparing peak growth between N and 2N separates the retained file buffer from the second 8-byte-per-scalar index; calibrate the allowed single-index growth on measured baseline/candidate source-buffer capacity and retain sensitivity control. Do not choose an arbitrary bound generous enough for both implementations.

For requested full build/live-count measurements across crates, use a temporary instrumentation patch applied to separately built benchmark copies (or an already existing project test instrumentation facility if found), record it as evidence, and keep it out of production APIs. Thread-local construction/live counters are sufficient only for a single source analyzed on one blocking thread; thread hops and parallel files require attribution rather than one global total. Track actual construction/drop boundaries if claiming maximum live indexes; incrementing expected phase counts is not evidence. The unmodified release binary supplies whole-time results; instrumented runs supply counts/heap. A real CLI heap gate plus local materialization tests is sufficient regression coverage without permanent cross-crate hooks.
