# Python 3.15 fuzzing対応の検証

既存PR #1109の専用worktree/branchで、runtimeのparserやmutation処理を変更せずに入力生成を更新する。
実装前は制御scriptと生成・compile選別が3.14のみだった。今回も制御scriptのsetupは3.14を維持し、uv呼び出しが両minor版を選ぶ。

## 調査・設計・計画のセルフレビュー

1. bounded CIとscheduled workflowの両方が同じci_fuzz.pyを使い、変更が両方へ届くことを確認した。
2. Rustのfuzz処理はPython runtimeに依存しないため、matrixでbuild/runを重複する案より、一つのcampaignへ両版の入力を合流する構成を選んだ。
3. 専用venvをTemporaryDirectory配下へ分け、開発venv・report・corpusを環境配置先にしない。
4. 11分/600秒、60分/3300秒、2 jobs、4096 bytes、5秒、RSS1024MiBと既存の失敗/timeout扱いを維持する。
5. 仮説的な互換性だけでなく、両実コンパイラの生成と3.15専用の構造化生成・seed検証、Linux CIの実行を計画へ含めた。WindowsのPOSIX検証範囲は明記する。

## 実装のセルフレビュー

1. 両版argv・環境分離・3.14での専用strategy拒否の3テストは旧実装で失敗した。3.15専用testも旧module snapshotへ差し替えて失敗を再現し、その後に新実装で成功した。
2. Campaign.runは子プロセスへだけ環境overlayを渡す。親環境は維持され、ログには指定したselectorだけが残ることを実子プロセスで確認した。
3. 通常の環境cleanupテストはmock境界でsentinelを実際に作り、campaign終了後に両環境が消えていることを確認する。
4. 3.15テンプレート11種と同数のseedをUnicode識別子でcompile検証する。構造化生成の値・識別子を変えてもsourceを実行しない。従来のhash名・サイズ上限・既存ファイル保持を維持する。
5. Rust buildは1回、7 targetは1回ずつ。Pythonの各stageはversion suffixを持ち、sync/runへ同じminor版と同じ専用環境を渡す。予算とfailure契約を変えていない。


## ローカル検証のセルフレビュー

1. 3.14.9と3.15.1でfuzz runner・generator・CI/workflow契約の関連テストが各233成功・5 skip。skipは主にPOSIX process group/fake executableと、実行版に合わないstrategy境界である。3.14側の1 SyntaxWarningは既存の生成コードcompileに由来し、入力を実行したものではない。
2. seed20261024、max_examples50で、3.14 grammar44/libcst28、3.15 grammar40/libcst21/python31545の新規入力を生成した。全5 reportでinvalid0、実Python版がそれぞれ3.14.9/3.15.1であることを照合した。
3. 生成ファイルのSHA-256名と1..4096 bytesの境界を照合した。重複は既存corpusとして扱い、sourceを実行せずにcompile選別している。
4. 3.15専用の11テンプレート・11固定seedをcompileし、構造化生成の50例もinvalid0だった。3.14で専用strategyを要求した場合は環境作成前に明示拒否する。
5. Ruffとtyが成功した。Rust runtime・Cargo manifests/lockfiles・既存resource limitsを変更していないため、大規模Rust全体テストとwheel再構築は反復しない。Linuxの実libFuzzer実行とPOSIXの成功は、このWindows結果から推定しない。


## 独立レビュー修正のセルフレビュー

1. fresh contextの独立レビューを1回実施し、3.15の新テストが任意のhypothesmith依存を無条件に要求するP2指摘を受けた。それ以外の実行版選択・環境破棄・予算・7対象の制御には修正指摘なし。
2. fuzz groupを入れない3.15.1の通常dev環境を専用ディレクトリへ作り、ModuleNotFoundErrorを実際に再現した。CI全体で失敗したという推測へは広げない。
3. template/seed compileを常時実行するテストと、optional依存をimportorskipする生成テストへ分離した。同じ通常dev環境で37成功・9 skipになり、必須のseed検証はskipしないことを個別にも確認した。
4. fuzz依存ありの修正後のrunner/generator関連テストは3.14.9が40成功・6 skip、3.15.1が41成功・5 skip、両コマンドexit 0。最初の広いworkflow検証233件ずつと今回の修正後の範囲を区別する。
5. 修正はテストのみで、検証済みの生成器・campaign・seed・resource limitsを変えていない。通常venvへfuzz依存を追加する回避策は採らず、独立レビューの未解決指摘はない。

## 文書・送信準備のセルフレビュー

1. canonical development guideに両版の生成、明示的uv selector、一時venvの破棄、共通corpusと一度だけのRust実行を記載した。driver setup3.14と生成器のminor版を区別した。
2. fuzzing-adoptionとdesign catalogを更新し、新しい5 source recordsは実装コミットのGit blobで固定した。過去の研究結果・source refsは書き換えない。
3. ソースはcompileだけで実行しないこと、coverage/mutation runtime semanticsの主張ではないこと、Windowsで未実行のPOSIX/sanitizer範囲を明示した。
4. reference/conceptの構成・根拠・手順・用語・リンク・範囲・時点・重複・簡潔さ・未検証条件の10項目を点検し10/10。文書ビルド、Ruff、ty、source pins・OKF構造を確認した。
5. 新しい一時venv2つと少量の生成corpusは検証後に専用タスク配下から削除し、小さいJSON/ログは保持する。Rustコード/lockfileは不変で、この段階のcargo cleanやwheel再構築は不要。送信先は既存PR #1109、Linux bounded fuzzの実行結果を送信後に別途確認する。
