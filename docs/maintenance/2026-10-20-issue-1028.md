## Current contract

JSON progress output uses schema 3 with required nullable `details`. Null means
no details request. A requested object retains the existing fields, including
`available: false` for an unusable final adjacent pair. The canonical definition
is `docs/json-schema/progress-result.schema.json`; the separate v2 file is removed.
Comparison, details collection, input readers and exit-policy code are unchanged.

The release floor remains 0.14.0 after the owner's policy clarification.
The initially proposed 0.15.0 increase was reverted; both manifests and all
three lockfiles match the original base. Report/event 9,
plan 10, session 5, fingerprint 13, ranking 4, candidate 1 and mutant-ID v1 remain
unchanged. Usage, generated help, developer guidance, distributed agent

The initial reviews and validation below record the earlier 0.15.0 proposal;

## Design reviews

1. **Request versus availability:** chose required null for an absent request;
   an unavailable requested comparison remains an object. This distinguishes the
   two states without a second version or new CLI option.
2. **Responsibility boundary:** limited production changes to the renderer's
   version selection and serialization attribute, plus obsolete help wording.
   Comparison and details-limit algorithms need no changes.
3. **Schema ownership:** retained the canonical unversioned path and copied the
   existing details/transition definitions into it. Superseded versions and a
   missing details key must fail current validation.
4. **Input boundary:** current report validation rejects repeated stable IDs
   mapped to different candidate sequences. Keep that public rejection and the
   internal duplicate-set comparison regression; do not weaken the reader to
   manufacture a detailed output case.
5. **Initial release scope, superseded below:** under the previous policy,
   a progress output incompatibility required floor 0.15.0;
   it does not require changing saved-plan, run-report or session versions.
   Document reader migration and preserve historical audit provenance.

## Git cancellation fixture startup allowance

Temporary instrumentation captured the CLI output and request trace when the
helper-start marker failed to arrive. Twenty isolated runs of the four-case
contracts test passed. Running four copies of that test binary concurrently,
with no injected delays, reproduced seven failures among sixteen cases. Each
failed case had no request trace and an already-exited CLI with code 4, empty
stderr, and a JSON report containing `complete: false`, `baseline: null`, and no
mutants. The interrupt cases reached their helper handshakes in 0.397–2.925
seconds. The one-second total deadline could therefore expire before the helper
recorded its first request; waiting ten seconds for its marker could not recover
that setup failure. These observations identify the deadline/handshake race,
without attributing it to a particular scheduler or preparation operation.

The final test-only change gives timeout cases a five-second total deadline and
allows ten seconds for CLI exit. The helper still blocks for thirty seconds, so
its natural completion cannot satisfy the exit bound. The ten-second marker
bound, interrupt deadline, required handshake, exit-code assertions, helper PID
liveness check, cleanup, and request-count assertion remain unchanged. Production
code has no changes for this stabilization. Temporary diagnostics remain only
in ignored local artifacts.
