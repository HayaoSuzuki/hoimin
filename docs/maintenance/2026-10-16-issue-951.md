# Issue #951: request-derived worker dispatch implementation plan

**Goal:** Remove independently supplied worker and baseline arguments from shell process dispatch while retaining completion accounting.

**Architecture:** A private `PreparedWorkerProcess` owns the common runner request and `WorkerProcessContext::Baseline(worker)` or `Mutant(worker)`. Conversion derives this context from the typed request once. Shell completions retain it through acceptance, failure and shutdown drain; the runner remains unchanged.

**Tech stack:** Rust, Tokio JoinSet, existing metrics collector, proptest and Lean correspondence integration tests.

**Spec:** [Issue #951](https://github.com/HayaoSuzuki/hoimin/issues/951), reviewed against base `ddb8ed9504beb04c06bfe11821ebcafffa332714`.

## Scope and plan

- [x] Add parameterized success/failure/drain tests for Baseline and Mutant requests in `crates/hoimin-cli/src/shell.rs`; observe the expected compile failure for the new private API before implementing it.
- [x] Add the prepared request and explicit worker context, adapt preparation and both production spawn calls, then migrate completion accounting without changing admission or transition order.
- [x] Exercise generated completion sequences through the actual drain accounting consumer; verify each outstanding mutant closes once and baseline contributes no metric.
- [x] Run focused and workspace tests, formatting, strict all-target/all-feature Clippy and existing shutdown/disk/workspace Lean correspondence tests.
- [x] Update `docs/knowledge/design/runtime-lifecycle.md`, check OKF structure/references, record concrete reviews and verification, and commit only this branch.

No CLI, report format, cancellation, task ownership, in-flight count, admission gate, or process/output-drain evidence contract changes are intended. Probe has no implementation of the local workspace-only preparation trait. No new Lean model is needed because no state transition rule changes.

## Design self-review (five passes)

1. Read both production callers: baseline currently supplies `true`, mutant `false`; neither is a reported runtime mismatch. Removing their independent arguments is the goal, rather than claiming an existing functional defect.
2. Read `WorkspaceProcessContext` and the runner's private `ExecutionContext`: only Baseline/Mutant implement the workspace trait. A shell-only prepared wrapper preserves that exclusion without genericizing `ProcessHandler::run`.
3. Read normal and retired completion handling: `EffectFailed` lacks usable worker/role information, so completion must carry request-derived context even when core rejects the payload.
4. Read `accept_drained_completion`: only mutants finish worker metrics; baseline still consumes one in-flight completion. Preserve both facts using explicit context variants.
5. Read dispatch and join ordering: metadata conversion happens during existing preparation; gate acquisition, process-start metrics, spawning and in-flight increments remain in their existing positions. Existing process/output evidence remains independent.

Design-philosophy assessment: before this change, five of eight local-boundary diagnostics have evidence (6.25/10). Information hiding and newcomer understanding fail because callers must reconstruct identity after lowering the request; design-investment time allocation is unmeasured. The wrapper removes this duplicated knowledge and documents why completion metadata survives, bringing the local boundary to seven evidenced diagnostics (8.75/10). Reaching an evidenced 10/10 would also require measuring the design-investment allocation. This score concerns the changed boundary, not the whole shell module.

## Implementation self-review

1. Compared both `spawn_process` calls with the base: removed only duplicate worker/baseline arguments; the baseline worker local was no longer needed. Mutant retains its local for pre-dispatch metric admission and environment-failure queue cancellation.
2. Traced `PreparedWorkerProcess::from`: context is read before the typed request is moved into the runner representation. Environment, cancellation and start gate are then attached to that same owned request.
3. Compared `CompletionSource` matching before/after: the enum still identifies process tasks independently of event acceptance, in-flight decrement, normal join and failed-event drain. Mutant metrics retain `accepted_mutant` as their executed flag.
4. Inspected every `ShellCompletion::Process` consumer, including post-drain disk-stop replacement. That special path previously closed metrics for either role; it still does. Ordinary and shutdown-drain accounting remain mutant-only. No incidental metrics-warning behavior change is bundled.
5. Reviewed test fixtures against `MetricsCollector::finish`: workers with no executed process are omitted, so drained failure expects empty worker output and successful finalization, not a zero-count worker row. The property checks every remaining in-flight count, absence of warnings and closure of all started mutant metrics across shuffled completion delivery.

The new finite cases exercise both roles using distinct worker IDs (baseline 4, mutant 7). Success invokes the current Rust test executable with a nonexistent exact test filter; failure invokes a missing executable. Neither depends on Python or a shell. Generated drain tests are bounded to at most 31 completions and make no OS subprocesses.
