# Issue #960: collector sink and error ownership

## Scope and design review

At baseline `30d158c7ead3252c5c0aa398e8ab1819ffa9d75b`, the collector already
preserved the first error, dropped a failed sink and drained through EOF. This
change keeps its incoming `io::Result<S>` during reception instead of splitting
it into two optional values. It changes internal state representation without
changing output retention, public interfaces or shutdown policy.

1. State review: `Ok(sink)` and `Err(error)` represent the two reception states;
   they require no independent error-presence check or synchronized assignment.
2. Lifetime review: replacing `Ok` with `Err` drops the owned sink at the failed
   write, before the collector waits for another chunk. Later chunks cannot
   reach writing or finalization through that result.
3. EOF review: spool creation and write errors remain values during reception.
   Error propagation occurs after `receiver.recv()` returns `None`.
4. Accounting review: observation precedes the write branch on each chunk and
   still uses saturating addition. Ring position and retention helpers remain
   unchanged, including zero capacity and oversized chunks.
5. Boundary review: successful EOF extracts the sink and finalizes once. A
   finalize error propagates from this boundary. Existing ordered-stream oracle
   inputs remain suitable; no transition rule requires another Lean model.

Software-design-philosophy assessment: 7 of 8 diagnostic rows have evidence
(8.75/10). The module owns output collection, hides file retention and keeps the
same interface; the comment explains the EOF boundary and this review checks
complexity. The design-time percentage is unmeasured. Measuring design effort
would establish the remaining diagnostic; extra abstraction would not.

## Test development

The baseline command passed all 13 `process::output::` tests before edits. Two
new tests then passed against the original implementation, bringing this filter
to 15 tests. These characterize preserved behavior; they do not reproduce a
previous runtime bug or require a private type layout.

The sink-lifetime test observes calls and a drop notification for failures on
write 1 and write 2. It keeps the sender open until the drop notification,
sends another 32 chunks through the eight-chunk channel, and checks EOF
completion, the first error, the exact write count and absent finalization.
The fault sink succeeds on later writes, so repeated calls cannot hide behind
repeated identical errors. The other test writes two chunks successfully and
checks that one failed finalize determines the result.

Two temporary mutations checked sensitivity before the refactor:

- Retaining the failed sink instead of clearing it failed the lifetime test at
  `failed sink drops before EOF: Elapsed(())`.
- Discarding the finalize error failed the finalize test at `unwrap_err()` with
  an unexpected successful `OutputSpoolRef`.

Both mutations were deliberate faults and were restored. Their failures provide
test-sensitivity evidence, not evidence that either fault existed at baseline.
The final collector then passed all 15 focused tests.

## Implementation review

1. Assignment review: the write-error arm performs one `spool = Err(error)`;
   no optional sink/error pair, new enum or adapter remains in production.
2. Reception review: both the initial error and write error paths retain the
   receiver until EOF; no `?` appears in or before the reception loop.
3. Resource review: result assignment releases the failed sink within that
   iteration. The new test waits for destruction before closing its sender.
4. Finalization review: one finalization call follows successful extraction at
   EOF. An errored result bypasses that call; finalize failure propagates once.
5. Regression review: ring writes, marker insertion, byte-count saturation,
   truncation thresholds and output construction keep their previous formulas.
   Existing oracle cases provide the independent byte/count expectations.
