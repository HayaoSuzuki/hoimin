# Issue #967: explicit Windows exit-notification interest

## Scope and design review

Baseline `229ce38535142958ab75aa1b0462d8be37dbf77e` has no writer for
`RootSignal.violations`. The run-wide job owns cleanup, while each nested root
job owns its memory and process caps and completion port. This change removes
the unused signal and its arguments without changing either job's policy.

1. State review: `ActiveRoot` needs only a boolean to distinguish whether an
   exit must be recorded for a supervisor. A second shared object, weak pointer
   or compatibility adapter adds no information.
2. Lifetime review: clearing interest does not remove the root ID, PID or owned
   process handle. An assigned process whose attachment fails and a detached
   root still occupy their generation until notification evidence releases it.
3. Wait review: clone the process handle under the registry mutex, release the
   mutex before waiting, then drain notifications again. Queued exit evidence
   wins over a signaled-handle fallback; the fallback detaches rather than
   forgetting the generation. Errors and timeouts preserve registration.
4. Notification review: an `ACTIVE_PROCESS_ZERO` packet only clears roots after
   a native accounting query confirms the job is empty. Only interested roots
   enter `exited_roots`. PID lookup consumes the oldest registered generation.
5. Classification review: run-wide limit packets cannot identify an offender
   and are ignored explicitly. Nested completion ports retain memory-before-
   process priority; normal sibling roots receive no shared violation state.

The change is a representation refactor, not a reproduced Windows defect.
`software-design-philosophy` assessment for this scope is 8.75/10: seven of
eight diagnostics have direct evidence. The Windows module retains job/handle
ownership behind the existing resource API; internal signal knowledge no longer
crosses attachment and exit waiting. Comments explain notification interest and
generation retention. The remaining diagnostic is the unmeasured percentage of
development time spent on design; another abstraction would not resolve it.

## Test design review

1. Baseline review: the existing Windows native unit filter passes all 25 tests
   under normal host permissions. In the restricted sandbox, two Python
   readiness fixtures fail before publishing their files; those failures are
   recorded separately from normal-host results.
2. Finite-case review: normal/abnormal exit and interest form four cases;
   empty/nonempty job and interest form another four. Literal expected IDs
   establish both completion membership and retained generations.
3. Isolation review: both run-wide limit messages leave active and completed
   roots intact. Actual nested completion ports exercise no packet, each limit
   independently, and both packet orders with literal expected terminations.
4. Sequence review: a bounded proptest interleaves normal exit, abnormal exit,
   stale empty-job packets and both run-wide limit packets for a reused PID.
   Expected generations come from counting input exit packets, independent of
   production transition helpers. The unrelated sibling remains registered.
5. Failure review: the existing timeout and mutex-release/handle-ownership tests
   remain. A separate injected wait-error test checks that the same registration
   remains available for retry. Each added test follows AAA and one invariant.

The five new notification tests passed against the original representation.
A temporary mutation then made `detach_root_generation` remove the active
generation immediately. The property test failed and shrank to an empty event
list: it observed roots 2 and 3 instead of roots 1, 2 and 3. This demonstrates
sensitivity to losing a detached generation before any notification. The
mutation and its generated regression seed were removed. After refactoring,
the complete Windows backend filter passed 30 tests, including the separate
wait-error test. These observations do not claim an original production bug.

## Implementation review

Five self-review passes checked the implementation after the sensitivity fault
was restored:

1. Removal review: `RootSignal`, its field/arguments, signal weak pointers and
   `mark_active` have no remaining backend references. `AtomicU8` is test-only
   for the unrelated close-failure injection. Shared job and process-handle
   ownership still use `Arc` where ownership requires it.
2. Registration review: successful attachment requests exit recording. Nested
   assignment/resume failures request none. Exit-handle reopening failure
   retains the original owned process handle with recording disabled.
3. Wait review: diff comparison preserves both notification drains and the
   owned handle outside the registry lock. The helper now returns `Result<()>`
   and takes no termination or signal; it only establishes exit evidence.
4. Transition review: queued notification consumption forgets the generation;
   the signaled fallback only disables recording. Detach and failed waits
   retain generation identity, and removal continues preserving vector order.
5. Classification review: nested notification bits start at zero locally and
   keep the original precedence. The ignored non-exit packet arm explains why
   assigning those packets to individual roots would be invalid.

An independent read-only reviewer inspected the diff, new tests and CI filter.
It reported no actionable critical, important or minor findings, with readiness
conditional on completing and recording verification. The reviewer ran no tests
and did not edit the checkout.

## Formal-model correspondence

The existing [shutdown oracle](../../crates/hoimin-cli/tests/lean_shutdown_oracle.rs)
compares abstract stop, reap, drain and finalization observations with the
[shutdown model](../../formal/HoiminOracle/HoiminOracle/ShutdownModel.lean).
Its subprocess adapter is Unix-only; running its schema checks on Windows does
not establish that adapter's runtime correspondence. The
[process-output oracle](../../crates/hoimin-core/tests/lean_process_output_oracle.rs)
checks classification of supplied process/output outcomes, including resource
terminations, after the backend supplies them. The
[resource cleanup model](../../formal/HoiminOracle/HoiminOracle/ResourceCleanupModel.lean)
describes cleanup reservation and registry release, not Windows completion
packets or PID generations.

None models Win32 notification delivery, synchronizable process handles or
nested Job Object cap enforcement. The transition rules are preserved, so this
change introduces no new Lean model or proof. Native tests and bounded sequence
tests establish separate, limited execution evidence; they are not a proof of
all OS schedules.
