# Worker workspace ownership registry (Issue #942)

Base: `465ff928c1f2ceb9f9b8f8084465475e45799ee8`.
Branch: `refactor/issue-942-worker-registry`.

## Scope and design

`WorkspaceHandler` now registers each worker ID once, with a `WorkerSlot` that
owns either an active workspace or a workspace awaiting cleanup. Completion
payloads carry `WorkspaceOwnership::Active`, `PendingCleanup`, or `None`.
Independent active/pending maps and independent completion options are removed.
A failed Apply returns active ownership; event success does not determine the
ownership state. A completion returning any already-registered worker ID is
rejected without replacing its first owner.

The private producers already returned at most one workspace per worker. The
cross-state duplicate tests inject a conflicting completion at the acceptance
boundary; they do not demonstrate a scheduler producing that conflict in a real
run. Scheduler in-flight tracking and managed-root lifecycle remain separate.
There is no public API, CLI, report, or saved-format migration.

Create still rejects active workers before transferring pending ownership and
validates the grant before attempting pending cleanup. Apply and Reset take only
active slots; rejected admission leaves a pending slot untouched. Cleanup and
close attempt both classes and retain the registry on failure. Their first-error
order remains active workers followed by pending workers, each by worker ID.
Janitor transfer visits both classes. Existing copy-slot release and reset error
policy remain in the workspace operation and ownership implementations.

## Scope/design self-review

1. Traced every registry insertion, removal and lookup and every completion
   producer. Create/Reset return active, pending or absent; Apply always returns
   active; Verify returns absent. No legitimate dual ownership was found.
2. Compared a single map with a separate registry wrapper. A private enum plus
   the existing handler is sufficient; another forwarding module would expose
   more interfaces without hiding a new decision.
3. Checked active-only admission and command environment lookup. Removal must
   follow the active-state check so rejected operations cannot drop pending
   directories or their copy allowance.
4. Checked grant validation, reset/discard policy and copy accounting against
   `operation.rs`. Representation does not justify changing operation order,
   error precedence, reservation binding or retry eligibility.
5. Compared cleanup traversal with the original two-map implementation. A plain
   worker-ID traversal would change first-error priority when a pending ID sorts
   before an active ID. Retained the original order and added a filesystem table
   for both cleanup entry points. The bounded design scores 8.75/10 under
   software-design-philosophy: seven diagnostics pass. The design-improvement
   time allocation diagnostic remains unmeasured; reaching 10/10 requires
   recording task and design-review time and checking the 10–20% allocation.
   This measurement gap does not justify another abstraction.

## Implementation self-review

1. Checked all completion constructors, including failed Apply and both Verify
   outcomes. No independent ownership options remain. Acceptance checks a single
   map entry before insertion and retains the registered workspace on rejection.
2. Checked synchronous Create/Apply/Reset against owned prepare/execute/accept.
   `take_active` centralizes non-destructive admission; Create transfers a slot
   only after rejecting Active and finding its plan.
3. Checked cleanup failure and retry behavior. `handle_cleanup` validates its
   reservation then uses `close`; `close` visits both states before returning the
   first error and clears the map and plan only after all cleanup succeeds.
4. Compared copy allowance and janitor code. `operation.rs`, workspace Drop,
   reservation accounting and managed-root transitions are unchanged; janitor
   transfer reaches every slot through its retained workspace.
5. Checked the existing Lean adapter. Only representation projections changed:
   active, pending and task-owned roots still map to the same corpus slots.
   The corpus and formal model are unchanged, with no new proof claim.
