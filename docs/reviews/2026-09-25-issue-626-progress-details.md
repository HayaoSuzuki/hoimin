# Issue 626 review and verification

The optional `--details` view reports bounded, identifiable improvements/regressions in the final input adjacency. Default human/JSON schema v1 and comparison decisions remain unchanged. Explicit JSON details select closed schema v2; no external files are written.

Design and plan were committed before implementation as `4391163` after rebasing the documentation-only branch onto main `bf09c91`. Both documents contain three substantive review passes. The design chooses final-pair scope, default limit 100, zero-cap support, original zero-based input indices, and separate `omitted` / `unidentified` counts.

## Implementation self-reviews

1. **Identity and aggregate correspondence.** Traced collector invocation through the real comparison: ambiguous keys and nonconclusive statuses return before observation. Equal IDs must also be unique in both inputs; content-only fallback with different IDs increments unidentified instead. Added direct internal regressions for duplicate IDs with distinct content, ambiguous content with otherwise matching IDs, and all five inconclusive statuses. Simplified killed/survived count increments using boolean conversion to keep the comparison within the repository function-length lint; the existing oracle still checks the full aggregate contract.
2. **Adjacency, output and error flow.** Confirmed collection runs only at the final original input index and an unusable final pair produces unavailable details. It cannot expose an earlier comparison as latest. Default serialization skips the optional field and retains schema v1; v2 has a separate closed schema. Human output quotes ID/path/operator and includes previous positions. Input parsing and fingerprint warnings still finish before rendering. Moved README documentation into the existing progress section and matched its English prose. Direct callers with an empty report vector retain their previous behavior through saturating final-index arithmetic.
3. **Ordering and allocations.** BTreeMap keeps only the smallest N borrowed IDs; cap checks precede insertion, and eviction precedes replacement so retained slots never exceed N. Only selected ID/path/operator metadata are owned at finish; source bodies, process output and prior reports are not cloned. Duplicate detection borrows IDs and runs only when details are requested. The full history still retains only the previous/current reports plus existing compact aggregate/input records.

## Test self-reviews

1. **RED sensitivity and fixture validity.** Three new public tests failed because `--details` did not exist, then passed after implementation. An initial fixture-only failure used a survived status with Exit(1); corrected the fixture to Exit(0), reran and recorded the expected unknown-option RED before implementation. JSONL parity initially omitted mutant-start events; repaired the fixture using the existing event constructor without changing production parsing. The public real-run regression test uses unedited strong/weak run reports and now asserts actual candidate ID, source location, and both transition directions.
2. **Negative boundaries and schema.** Tests cover zero/one/default100 caps, lexical IDs `10`, `2`, `a`, reversed input event order, full aggregate counts, content-only unequal IDs, partial candidate sets, malformed limit use, unusable middle/trailing reports, quoted newline/quote paths, and JSON/JSONL equivalence. The v2 validator accepts output and rejects unknown detail/transition fields and invalid statuses; v1 rejects opt-in v2. Default output fields are compared against a normal invocation. Internal comparison tests cover invalid-for-public-reader status/duplicate fixtures without weakening the reader.
3. **Memory and model limitations.** A single-test allocator measures total allocations for identical public reads with details off/on, preventing large parser peaks from hiding detail clones. At 32-byte and 256-KiB candidate bodies, observed additional allocation was 3,796 bytes in both cases. A temporary real `original.clone()` in the collector produced 3,149,524 extra bytes for large bodies and failed the 64-KiB bound; removing it restored GREEN. Existing history heap checks now also exercise details with 16 inputs and retain the same 512-KiB overhead bound. These allocator tests do not claim RSS limits or arbitrary metadata-length bounds. Lean uses candidate roles 0/1; general lexical ordering is covered by Rust tests, not proved by the finite numeric model.

## Lean model and implementation correspondence

Extended the existing `ProgressDecisionModel`, cases and generator. Corpus schema is now 2 and includes latest-pair detail expectations with cap 1. The committed corpus was generated by Lean, not hand-edited. A deliberately empty transition model failed a native example (RED); the implemented model passes equal-ID changes, content-only exclusion, duplicate and inconclusive exclusion, cap and trailing-unusable examples. Broken witnesses distinguish ignoring identity, ignoring the limit, and filtering unusable inputs before selecting adjacency.

The existing 24 cases remain: 17 strict public CLI cases, six internal comparison fixtures, one duplicate-ID model fixture now additionally observed through the internal detail comparison test. The real public CLI adapter invokes `--details --details-limit 1`, compares generated identities/statuses/classifications/omissions/indices, and rechecks all existing aggregate expectations. Internal adapters compare generated detail expectations without claiming those injected reports pass the public parser.

Existing exhaustive decision bounds are unchanged: report domain 50, 2,500 pairs, history depth 4, patience 1..3, 2,343 history checks. New detail checks are finite examples and these 24 corpus cases, not an exhaustive proof of arbitrary reports. Parsing, I/O, allocator behavior, full Unicode ordering and rendering are outside the Lean model. No unresolved semantic mismatch or infrastructure failure remains.
