# Kani調査のセルフレビュー

## 設計の5回

1. 範囲: Issue本文の現行トリアージを優先し、ユーザーが承認した1関数・Linux手動試行に限定した。
2. 追加価値: overflow拒否の具体例が既にあり、単なる同一例の再実行を価値としない。実ビット幅の網羅検証の可否を評価した。
3. 実装対応: 実hoimin-coreを依存として使用し、写した予算計算やstubを検証対象にしなかった。
4. 保証条件: 空台帳・worker数0〜3・1予約を明示した。u64値は全域だが任意状態の台帳まで含めない。
5. 採否: proof、counterexample、unsupported、resource exhaustedを区別する。導入成功だけで製品採用としない。

## 計画の5回

1. ブランチ: 最新origin/mainから専用research/issue-778-kaniを作成し、origin/mainへの追跡を解除した。
2. 隔離: 既存Rust・MSRV・PATHを変更せず、WSLの専用CARGO_HOME/RUSTUP_HOMEとarchiveコピーを使った。
3. 予算: setup600秒、初回240秒、再試行120秒、harness60秒、4GiB・swap0・128tasksで打ち切る。
4. 反例: 正常系が検証可能になってから意図的欠陥とPlaybackを試す順とした。資源不足なら未実施を明記する。
5. 保存: 製品用harnessやCIを先に追加せず、試行用ソース・ログ・結果を調査資料として残す。

## 実験実装の5回

1. Oracle: 期待する積はu128で計算し、対象のchecked_mulの結果を期待値へ転用しなかった。
2. エラー: overflow、総量不一致、予算超過を区別し、誤ったエラー分類も契約違反として検査するharnessにした。
3. 状態: 失敗後の使用量0と次の予約ID0をassert対象に含め、外から観測できる状態保持を検査しようとした。
4. 費用: unwindを8から2へ下げてもunwinding checksは保持した。資源上限の引き上げやBTreeMapの置換はしなかった。
5. 診断: WSL再起動で/tmpが消えたため/var/tmpへ移した。Kani非対応の--testは--testsとexact harness filterへ変更した。

## 検証の5回

1. 実コード: 元とarchiveのbudget.rsのSHA-256が一致し、元workspaceに製品コード差分がないことを確認した。
2. 初回: Kani JSONのchecks空・exit_status=timeoutとログを照合した。summary completed/Failureを成功/反例と誤解しない。
3. 再試行: systemd-runのoom-kill・4.0Gを確認した。失われたtransient unitへ後から問い合わせた初期値を証拠にしない。
4. 未検証: 証明成功・意図的欠陥の検出・Concrete Playback・通常回帰テスト化・unwindの十分性を未検証として残した。
5. 保存と清掃: 終了子プロセス不在、隔離cargo clean、専用環境削除、資料の参照・JSON・出典hash・形式・docs限定差分を確認した。

この調査で製品の欠陥は確認されていない。追加の保証も得られていない。
通常の品質ゲートや依存を変更せず、資源不足の結果を残して調査段階を終了する。
